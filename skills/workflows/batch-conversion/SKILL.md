# 批量转换工作流

用于**一次提交包含多项转换任务**的批次调度。项目冻结基线是一次提交**不少于 40 项**、**允许排队**、**自动完成逐任务评测**；不要求 40 路并发，也不要求这批任务全部是长文件。

本 Skill 只负责**批次层**的规则：冻结、排队、限流、逐项推进、状态持久化、中断恢复、失败处理和批次汇总。以下内容不在本文件内重复，按需加载：

| 问题 | 由谁负责 |
|---|---|
| 某项任务怎么转换、保留什么行为 | 语言方向 Skill + 场景 Skill + 系统方向 Skill（[根入口](../../../SKILL.md)） |
| 单个长文件如何防语义漂移 | [长单文件转换工作流](../long-file-conversion/SKILL.md) |
| 单项任务的阶段门槛、自修次数上限与失败分流 | [转换—自审—第三方评估闭环](../../../references/workflow/conversion-evaluation-loop.md) |
| 单项任务的产物集合、目录布局与 manifest 字段 | [转换交付与移交契约](../../../references/framework/delivery-handoff-contract.md) |
| 提交、轮询与取证的接口形态 | [远端 Controller 适配](../../../references/adapter/controller/remote-controller-adapter.md) |

**边界声明（不得省略）**：本 Skill 是过程约束，**不是批量能力已达标的证据**。写出本文件不代表已经提交过任何批次、不代表队列可恢复、不代表任一项编译或行为通过。批次能力只能由**实际批次记录**证明：提交批次 → 逐项进入有证据的终态 → 无无声丢失与重复执行 → 批次结果可复核。

## 0. 准入与边界

- **任务清单由调用方提供**：本工作流不生成源码、不选取样例、不为凑够 40 项而拆分或复制任务。批次里每一项都必须**已有冻结任务契约**（`case.md` 或等价契约）；仍是候选 stub、源文件缺失或契约未冻结的项**不得进入批次**。
- 一项任务只计一个源→目标方向。同一批次可复用同源到多个方向，但不得把同一个源文件冒充不同源语言的任务。
- 单一批次内的规模是**排队深度**，不是并发要求。不因批次大而降低任何单项的准入、安全或证据门槛。
- 遵守[安全边界](../../../references/framework/safety-boundary.md)：批量调度本身不是执行授权；**用户已明确给出的批次级隔离 VM 运行授权可复用，无须逐项重复询问**。本机只读写与审阅文本，不编译、不运行源/目标代码或构建脚本；编译与运行只发生在获批隔离环境。逐项仍要核对真实入口、数据与网络目的地；`READY`/快照回滚不证明 VM 与公网、生产网隔离。批次的“编译授权”不自动包含运行授权。
- 测试用例有源码即可进入契约冻结；许可正文、版本号、上游 commit、仓库 URL 不作冻结或提交校验。逐项仍须核对源快照、方向、执行环境、命令形态及安全边界；待确认的 OS 可以按契约决策冻结，但须保留不确定性，不能写成源码自证。
- **冻结与执行分层**：三台 runner 的 Ruby 基础能力已登记并有最小实测证据，见[Runner 能力矩阵](../../../references/adapter/controller/runner-capability-matrix.md)；实际提交 Ruby job 前仍须复核所选 runner 的实时 `ruby`、READY 与污染状态。具体 gem、framework 入口与源码行为不随基础工具链证据自动通过。
- **源侧问题分层**：源码只缺 `main`/脚本调用入口或最小工程外壳时，Agent 可按逐例契约补写中性启动文件/驱动，记录其内容与哈希，不把“无入口”直接判成源代码失败。使用 `dotnet build` 的单文件 C# 源树若缺 `.csproj`，先按冻结的 .NET 版本补最小中性工程文件，冻结内容与哈希，再取源侧真实诊断；工程文件只定义构建上下文，不补造原仓库缺失的命名空间、类型或实现（batch-01 B13/B14 首提 `MSB1003`，补工程后才暴露 `SharpUp.*` 缺失）。缺失真实框架类型、第三方实现或源代码本身不能构建时，保持原样并在真实评估回传后归因；同批其余任务继续。失败案例后续统一重选，不在本批静默替换。

## 1. 批次冻结

在提交第一项之前，为整个批次建立一份冻结记录，至少包含：

| 字段 | 内容 |
|---|---|
| 批次 ID | 稳定、唯一、可引用（如 `batch-01`）；同一批次 ID 不复用于不同清单 |
| 任务清单 | 逐项 `taskId` + `direction` + 契约路径 + 源快照哈希；`taskId` 在批次内外都稳定，不随重排改变 |
| 方向与规模 | 逐项源/目标语言、源/目标 OS 与架构；批次总项数与实际覆盖的方向集合分别记录 |
| 环境与工具链 | 逐项目标工具链及命令形态、源/目标 runner、`executionStrategy`；目标配置与 [Runner 能力矩阵](../../../references/adapter/controller/runner-capability-matrix.md) 的实时实测状态分列 |
| 模型与知识快照 | `.env` 的非敏感模型标识、温度与请求参数、RAG 开关、所选 Skill 的内容快照 |
| 验收依据 | 本批次取哪些证据（当前阶段：目标侧 **build** 证据）、哪些结论**不在**本批次范围内 |
| 隔离与授权 | 隔离范围、外联限制、逐例安全约束；凭据不入库 |

**冻结后不得静默变更**：批次内更换模型、编译器/SDK、工具链或方向，或改写已冻结契约，都不属于同条件重试，必须**另起批次 ID** 并在新冻结记录中说明差异。批次记录不得改写任何 `case.md`；逐例契约以各方向目录内的 `case.md` 为唯一真源。

**提交前静态核对**：逐项确认契约路径和源码文件存在、快照哈希匹配；从契约读取源/目标 runner 与同台/异台策略，不靠登记表的 OS 缩写推断。数据集的 `source/` 可能被 Git 忽略，不能假定仓库检出后源码仍在；组装 capsule 时必须从实际工作区读取源码并再次核对冻结哈希。再读取 Controller 当前 `GET /api/runners`，核对两侧语言、OS、架构、READY、污染状态和所需工具链；环境尚未适配的项记录为待环境，不发送必然失败的 job。登记页与契约冲突时先更正登记页；契约自身冲突时修订契约并重新冻结批次。

## 2. 排队与限额

- **默认串行 1 路**：同一时刻只推进一项任务，一次只占用一个模型请求位和一个评估 job 位。本工作流不引入并发调度规则；若调用方明确要求并发，须先冻结并发上限与状态互斥写法，并另记该批次为并发批次，不得与串行批次混算。
- **模型请求与评估 job 分别限流**：两者是不同资源（外部模型服务 vs 隔离 VM/Controller 容量），分别记录并发上限、当前占用与排队位置；模型侧限流不得被评估侧占用阻塞拖垮，反亦然。并发上限不是总请求数或 token 预算。
- **逐项修订次数沿用单项闭环**：单任务自修 ≤2 轮、评估后 repair ≤2 轮，按**每项任务**计；这是防止无证据的无限修订，不是费用或 token 上限。批次层另行冻结：单项墙钟超时、批次总时限与轮询间隔。
- **只记录消耗，不设批次预算**：不为后续批次设置模型请求总数、token、费用或 Controller job 总数的派发上限。按 API 返回的 `usage.total_tokens` 对**每一次已发请求**累计，包含截断、解析失败与重复尝试；`prompt_tokens`、`completion_tokens` 和 `reasoning_tokens` 分列，不把 reasoning 再加到 `total_tokens`。返回后立即持久化实际用量。批次关闭前从逐次响应元数据按响应哈希去重重算请求数与 token 总量，并与 `batch.json`、事件日志核对；差异作为事后审计追加记录，不能静默改写原关闭事件。`batch-01` 冻结过 4M 上限及其超额记录是历史事实，不作为后续批次规则。
- 不做 40 路并发，也不把"排队完成"当作"并发能力"或"性能指标"。

## 3. 逐项调度

按冻结顺序逐项推进；每项的推进方式**完全复用单项闭环**，本工作流不重设阶段门槛：

1. 为该项加载匹配的语言方向、场景、系统 Skill；任务模式为**长单文件**时额外加载[长单文件工作流](../long-file-conversion/SKILL.md)，并先完成全文件地图与语义分段。
2. 由 `.env` 配置模型生成目标代码 → 结构化自审 → 有限自修 → 预检可交评估，按[转换—自审—第三方评估闭环](../../../references/workflow/conversion-evaluation-loop.md)门槛执行。运行安全阻断只影响第三方提交，不自动把自修轮次改为 0；若某项确实未处理自审中可定位的转换引入问题，保留稿件并标 `SELF_REVIEW_UNRESOLVED`/部分交付，不写成预检通过。
3. 预检和逐例运行安全门槛均通过后组装 comparison capsule 并**直接提交**获批隔离环境（远端 Controller/隔离 VM 恒就绪且已授权，不逐次确认可达性、不逐项询问是否评估）；轮询到终态后回传并保存证据。安全门槛未通过的项按下文记录并继续队列。
4. 按[交付与移交契约](../../../references/framework/delivery-handoff-contract.md)落盘该项产物与 `result.md`，并把该项状态写入批次记录。

**本批运行驱动口径**：Controller 要求双侧 `runCommand`。驱动须在合成数据、一次性目录、loopback 或与公网/生产网断开的封闭实验网内实际调用对应源/目标程序；不因攻击标签、文件名或默认入口敏感而自动跳过，先判断该入口能否在已确认的隔离环境中真实运行。execution/comparison 回传可保存以供后续诊断，但当前阶段不计功能正确率。不能用只输出固定文本的空跑驱动冒充程序已运行。若实际入口仍会越出网络/数据边界、所需依赖缺失或无法建立可观察运行条件，记录该项为 `UNVERIFIED` 并写明 `RUN_SAFETY_NOT_READY` 或源侧原因，继续其余项；不把阻断误记为代码编译失败或基础设施故障。

**批次层的职责只有三件**：决定推进顺序、控制并发与超时、在每项进入终态后**立即持久化**该项状态。批次层不得代替单项门槛判定，也不得把"批次排到了这一项"表述为该任务已转换或已通过。

## 4. 状态持久化与恢复

批次状态必须**可被他人复核、可在中断后原样续跑**。每批次一个目录（放在数据集区，与逐例契约并列，不复用 `case.md`），最小文件集合：

| 文件 | 作用 |
|---|---|
| `batch.json` | 批次冻结记录 + 逐项索引（`taskId`、方向、契约路径、当前状态、最新产物版本、最新 job ID） |
| `items/<task-id>.json` | 单项状态：阶段、产物版本与哈希、模型调用摘要、job ID、诊断与证据路径、重试计数 |
| `events.jsonl` | 追加式事件日志：入队 / 开始 / 模型请求 / 提交 job / 终态 / 阻断 / 重提，带时间戳与原因 |
| `summary.md` | 批次汇总（按 §6 生成），面向复核者 |

**恢复流程（中断后必须按序执行）**：

1. 读 `batch.json`、`items/*.json` 和 `events.jsonl`，列出已完成、进行中、未开始三类项；先核对冻结任务数、任务 ID 唯一性和状态文件一致性。
2. 对"已提交 job 但状态未收尾"的项，**先用已记录的 job ID 查询** `GET /api/jobs/{jobId}`，按返回结果补记终态并取证；**不得**直接重新提交。若提交请求已发出而 job ID 未持久化，先按稳定 task/capsule 标识向 Controller 核查是否已接收；无法证明未接收时暂停该项并人工核对，不盲目重提。
3. 对"已生成但未提交"的项，从上一阶段继续，不重跑已完成的模型调用。
4. 只对确认为 `INFRA_ERROR` 且环境已恢复的项，按 §5 重提。
5. 续跑前后各记一条事件，说明恢复依据。

**防重复与防丢失**：提交前先持久化待提交事件和 capsule 哈希，取得 job ID 后立即持久化回执；同一 `taskId` 的同一 capsule 哈希不无故重复提交。重复提交必须能在 `events.jsonl` 中读出理由（通常只有环境故障恢复）。每项必须在终态收尾后才算离开队列，禁止用"批次已跑完"掩盖未收尾项。恢复时若发现记录与实际产物不一致，以 Controller 回执及证据文件核对并登记差异，不静默覆盖。

## 5. 失败处理

逐项判定终态，**不同失败不得混算**：

| 终态 | 判据 | 批次层动作 |
|---|---|---|
| `DONE` | 该项已完成本阶段允许的证据收集（当前阶段：目标侧 build 证据） | 记结论并继续下一项 |
| `FAILED_CODE` | 代码相关失败（编译失败、预检后仍有可定位缺陷、达到自修次数上限） | 原样保存诊断与版本，**继续处理其余项**；不中断批次、不改判为通过 |
| `FAILED_BEHAVIOR` | 取得行为证据且与冻结 oracle 有差异 | 只在实际覆盖范围内记录差异；本阶段不计入功能率 |
| `BLOCKED_ENV` | Controller/runner/工具链/清理等**基础设施**故障 | **暂停受影响项**而非整批宣称失败；环境恢复后按 §4 重提同条件任务 |
| `UNVERIFIED` | 未取得对应证据，或证据不足 | 明确写未验证；**不得**因批次完成而升级为通过 |

- **单代码项失败不阻塞批次**：除非失败原因指向公共环境（如工具链整体不可用、版本不符），否则其余项继续。
- **公共环境故障暂停相关队列**：不得让模型反复修改代码去"绕过"基础设施故障；也不得改用本机编译或边界外运行。
- **读诊断再归因**：Controller 总类目即使写 `CODE_RESULT`，也要检查两侧 build 命令与完整 stderr。若失败发生在编译器处理源码前的 runner 路径、权限或缓存初始化（batch-01 B20：当时 Go 默认缓存 `/home/d9lab` 不可写），项目侧记 `BLOCKED_ENV`，保留 Controller 原分类并记录分歧；不得把它记作转换代码失败。B20 临时 `GOCACHE` 绕行是历史 job 证据；2026-10-05 Linux runner 已另在 R12 基线完成平台修复与无害 Go 验证，不能把后者倒填为 B20 原始目标的行为证据。
- **区分失败与未评估**：未提交、未取证、未收尾的项一律 `UNVERIFIED`，不得计入通过，也不得计入失败率。
- 重提必须复用**同一冻结契约与同一 capsule**；环境恢复后的重提不计为新任务、不改变 `taskId`。

## 6. 批次收尾

批次结束条件：清单中每一项都处于明确终态，且**任务数核对一致**。

1. **清单核对**：逐项比对提交清单与实际记录，确认无遗漏、无重复执行；差异须逐条说明原因（合并、撤回、重复提交等）。
2. **分层汇总**，四类结论**分开列**，不得合并成单一"通过率"：
   - 调度完成度：入队/开始/终态项数、重试次数、超时与阻断项数；
   - 编译结果：逐项目标侧 build 结论（PASS / FAIL / 未提交 / 环境失败）；
   - 行为结果：实际取得的 oracle 覆盖与差异；本阶段未做则整列写 `UNVERIFIED`；
   - 覆盖统计：本批次实际覆盖的方向 / OS / 战术集合。
3. **覆盖不得外推**：40 项批次可能覆盖的方向少于 42 个方向；"覆盖方向数 = 该批次含契约的方向数"，不等于"42 方向已覆盖"，也不等于这些方向可靠。同一方向的重复案例不增加覆盖。
4. **结论分层**：`编译 PASS` 只认对应最终交付版本的第三方目标 build 证据；批次完成、队列无积压、模型自评均不能作为语法或行为结论。
5. 汇总写入 `summary.md`；若项目另有批次/契约状态登记页（如数据集内的冻结登记文档），只向其回填**真实终态与证据路径**，未取得回传前一律 `UNVERIFIED`，不预填 job ID 或结论。

## 7. 如实报告

交付批次说明时，明确区分并分别陈述：

- 本批次**实际提交**了什么（批次数、项数、方向集合、是否真实提交到隔离环境）；
- 队列与恢复的真实情况（是否发生过中断、如何恢复、有无重复提交）；
- 逐项证据等级：文本审阅 / 编译证据 / 行为证据，以及缺失部分；
- **未验证部分**：未取证项、未覆盖方向/OS/战术、未执行的行为 oracle。

不得用"批量调度已完成"替代转换效果，不得用批次规模、Skill 文件数量或队列状态暗示质量达标。若批次尚未真实提交或尚无回传证据，直接写"未提交/未验证"，不预填 job ID 或结论。
