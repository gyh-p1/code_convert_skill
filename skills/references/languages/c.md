# C 语言共性语义（ISO C11）

> **用途**：供以 C 为源语言或目标语言的方向 Skill 按需读取；本页仅保存该语言的跨方向事实与风险，不指定任何源→目标映射。
> **知识与证据边界**：由原[七语言共性索引](../seven-language-common-semantics.md)的七个机制表逐行迁入；原有版本/官方依据随条目保留。静态事实不代表目标工具链已部署，也不代表任一方向的编译或行为已验收。
> **分类**：`[语言规范保证]`、`[指定运行时的实现相关事实]`、`[待专题核验，不可用于确定转换规则]` 的含义见[共性索引](../seven-language-common-semantics.md)。具体任务仍须冻结版本、运行时、OS、架构和 ABI。

## 一、值、引用、别名与可变性

- **语言规范保证**：`[语言规范保证]` 默认纯值传递；指针传递指针值；`const` 仅声明只读视窗，不保证对象物理不可变；严格别名规则（Strict Aliasing）：不同类型指针强转互解引用属于未定义行为（UB）（`char*` 除外）。
- **实现相关 / 运行时优化行为**：`[指定运行时的实现相关事实]` 变量物理分配位置（寄存器/栈/静态区/堆）由编译器优化与存储期决定，非跨实现语言保证；对齐边界由 ABI 决定。
- **机械等价禁区与转换约束**：严禁用指针强转在不同类型间做物理重解释；不可假定值拷贝开销固定；**不得把 C 的指针判空与其他语言的“假值/真空值”判定互相当作等价**（见下条）。
- **官方资料依据**：[WG14-N1570 §6.5 ¶7, §6.7.3](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

### L1-C-01 判空与真值不是同一件事
1. **源码触发条件**：C 代码用 `if (p)` / `if (!p)` / `if (n)` 做判空或零值判断，且 `p` 是指针、`n` 是整数。
2. **冻结版本/运行时/API 前提**：ISO C11；空指针常量与指针比较语义见 [WG14-N1570 §6.3.2.3](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)。
3. **原可观察行为**：`if (p)` 判的是“`p` 是否为**空指针**”；`if (n)` 判的是“`n` 是否非零”。C 中**不存在**“空字符串为空”“空容器为空”的隐式真值语义——`""` 是合法的非空指针，恒为真。
4. **目标可选写法和不适用条件**：
   - *C 作为源*：把判空显式落到目标语言的“null/nil/None”检查，把零值检查落到数值比较；不要在目标语言里用其真值规则“顺手简化”。
   - *C 作为目标*：源语言的真值判定必须**显式重建为比较**（`if (len == 0)`、`if (p != NULL)`），不得写成裸 `if (x)`。
   - *不适用条件*：若源语言的类型系统已排除空值（如 Go `int`），该判定不是判空，不要加 NULL 检查。
5. **错误机械替换反例**：
   ```c
   /* 错误：把源语言的空串/零值为假的判定当成指针判空 */
   if (pwsz) { use(pwsz); }              /* C 中 "" 的指针非 NULL，这里恒真 */
   /* 正确：分别表达“指针为空”和“内容为空” */
   if (pwsz == NULL) { return -1; }
   if (pwsz[0] == '\0') { /* 空串分支，源中另行判定 */ }
   ```
6. **信息不足或实现相关时的处理**：无法确定源的 `!x` 表达的是“未设置”还是“值为零”时，标为“判空与零值语义待确认”，不得用统一真值判断合并两者。
7. **直接官方 HTTPS 依据链接**：[WG14-N1570 §6.3.2.3, §6.5.3.3](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

### L1-C-05 程序实参的计数基准与解析器语义必须显式重建

1. **源码触发条件**：源码从 `main(int argc, char* argv[])` 取用命令行实参，或用 `getopt`/`getopt_long`/手写循环解析，或把 `argv` 交给下游解析器/子进程。
2. **冻结版本/运行时/API 前提**：ISO C11（[WG14-N1570 §5.1.2.2.1](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)）；`getopt` 的具体行为取决于 **libc 实现**（glibc / BSD / musl 在参数置换、前导 `+`、诊断输出上互不相同）。
3. **原可观察行为**：
   - 当 `argc > 0` 时，`argv[0]` 表示程序名或空字符串，`argv[1]` 才是第一个用户实参；标准允许 `argc == 0`。`argv[argc]` 保证为空指针。
   - "没有用户实参"由 `argc < 2` 判断；不能仅由 `argv[0] == NULL` 判断，该条件可能只说明 `argc == 0`。
   - 解析器的**匹配规则**（精确名 / 唯一前缀 / 缩写）、**是否置换**（`prog <operand> -q` 与 `prog -q <operand>` 是否等价）、**未知选项的诊断输出**都是可观察行为。
4. **目标可选写法和不适用条件**：
   - *C 作为源*：目标语言的实参序列若**不含程序名**（C#、Ruby 的 `ARGV` 都不含），必须把源的 `argv[1..]` 映射到目标的 `[0..]`，并显式处理 `argc == 1` 的空实参情形；目标若**含程序名**（Go `os.Args`、Python `sys.argv`），则需保留偏移。
   - *C 作为目标*：源的"无用户实参"重建为 `argc < 2`；不得把源的无实参判定写成 `argv[0] == NULL`。
   - *不适用条件*：源码完全未使用命令行实参（如纯库代码、固定输入）时不适用；此时不要凭空加入实参解析。
5. **错误机械替换反例**：
   ```c
   /* 错误一：把目标语言的“实参数组不含程序名”直接套到 C 的 argv */
   if (argc > 0) { path = argv[0]; }     /* 实际取到的是程序名，不是第一个实参 */
   /* 错误二：用 argv[0] 判空来表达“没给参数” */
   if (argv[0] == NULL) { usage(); }     /* argc 才是用户实参数；此处不能判断是否有用户实参 */
   /* 错误三：假定 getopt 会置换（换成 BSD/musl 后不成立） */
   /* 正确 */
   if (argc < 2) { usage(); }
   path = argv[1];
   ```
6. **信息不足或实现相关时的处理**：无法确认源运行时的 libc 实现、或无法确认源是否依赖唯一前缀/置换时，标为“实参绑定与解析器语义待确认”；**不得**默认 glibc 行为，也不得以目标库的默认解析行为直接替代。
7. **直接官方 HTTPS 依据链接**：[WG14-N1570 §5.1.2.2.1](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)；[POSIX `getopt`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/getopt.html)；[glibc `getopt`（置换与 `POSIXLY_CORRECT`）](https://www.gnu.org/software/libc/manual/html_node/Using-Getopt.html)。

## 二、整数宽度、溢出、符号性与转换

- **整数宽度规范**：`[语言规范保证]` `short` $\ge 16$, `int` $\ge 16$, `long` $\ge 32$, `long long` $\ge 64$ 位；精确宽度见 `<stdint.h>`。
- **有符号溢出行为**：`[语言规范保证]` **未定义行为（Undefined Behavior, UB）**；编译器假定不溢出并优化代码。
- **无符号溢出行为**：`[语言规范保证]` **按模截断回绕**（Modulo $2^n$），属于严格合法的确定性行为。
- **隐式提升与转换陷阱**：`[语言规范保证]` 整型提升（Integer Promotion）按 `int` 能否表示原类型全部值选择 `int` 或 `unsigned int`；有/无符号混算按通常算术转换，由类型等级与可表示范围决定，不是一律转无符号。
- **官方资料依据**：[WG14-N1570 §6.2.5, §6.3.1.1, §6.5 ¶5](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

### L1-C-02 定宽输出必须用宽度正确的格式说明符与缓冲预算
1. **源码触发条件**：源码用格式化输出整数，尤其是 64 位量（文件大小、偏移、计数器）与有界缓冲区（`snprintf(buf, sizeof buf, fmt, v)`）。
2. **冻结版本/运行时/API 前提**：ISO C11；`<inttypes.h>` 的 `PRI*` 宏与 `<stdint.h>` 定宽类型见 [WG14-N1570 §7.8, §7.20](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)；MSVC 历史格式见 [Microsoft `printf` 宽度规格](https://learn.microsoft.com/en-us/cpp/c-runtime-library/format-specification-syntax-printf-and-wprintf-functions)。
3. **原可观察行为**：`%lld`/`%llu` 对 `long long` 有效，但把 `long long` 传给 `%d` 是未定义行为；`PRIu64` 会按目标平台展开为正确长度修饰符。`snprintf` **截断而不溢出**，返回**本应写入的字符数**（不含结尾 `\0`），因此返回值 ≥ 缓冲区大小即表示已截断。
4. **目标可选写法和不适用条件**：
   - *C 作为源*：目标语言若用格式化函数，须核对目标说明符宽度（如 MSVC 的 `%I64u` vs C99 的 `%llu`/`PRIu64`），不能假定同名说明符同义。
   - *C 作为目标*：把源语言的格式化重建为定宽类型 + 匹配说明符；有界缓冲区必须同时复核**容量预算**，并按 `snprintf` 返回值判断是否截断。
   - *不适用条件*：源使用无限长字符串拼接、目标为自动扩容字符串类型（Go `string`、Python `str`、Ruby `String`）时，不存在说明符宽度问题；此时改按第三节核对编码与字节语义。
5. **错误机械替换反例**：
   ```c
   /* 错误一：把 long long 交给 %d，且假定缓冲区够大 */
   char buf[5];
   snprintf(buf, sizeof(buf), "%lldB", bytes);   /* "1023B" 需要 6 字节，已截断 */
   /* 错误二：说明符与实参宽度不匹配 */
   printf("%d\n", (long long)size);              /* UB */
   /* 正确：用 PRI 宏并按返回值判断截断 */
   char buf[32];
   int n = snprintf(buf, sizeof(buf), "%" PRId64 "B", (int64_t)bytes);
   if (n < 0 || (size_t)n >= sizeof(buf)) { /* 按源语义处理截断/换用更大缓冲 */ }
   ```
6. **信息不足或实现相关时的处理**：无法确定目标 CRT 的说明符集时，写“格式说明符宽度待按目标 CRT 核对”，并用 `PRI*` 宏降低不确定性；不得靠加大缓冲区掩盖宽度不匹配。
7. **直接官方 HTTPS 依据链接**：[WG14-N1570 §7.8, §7.21.6.5](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)；[Microsoft 格式说明符语法](https://learn.microsoft.com/en-us/cpp/c-runtime-library/format-specification-syntax-printf-and-wprintf-functions)。

## 三、字符串、字节、NUL、Unicode 与编码

- **字符串数据结构**：`[语言规范保证]` `char*` / `char[]` 以 `\0` 字节结尾的序列；无内置长度记录字段。
- **字节序列数据结构**：`[语言规范保证]` `unsigned char[]` / `uint8_t[]`；必须外部显式传递长度。
- **NUL (`\0`) 字符语义与处理**：`[语言规范保证]` **`\0` 是字符串的唯一终止标记**；中间出现 `\0` 将导致截断；若末尾缺少 `\0` 导致越界读取 UB。
- **编码假设与转换陷阱**：`[语言规范保证]` C 语言本身不假设编码（视平台/终端为 ASCII/UTF-8/GBK 等本地代码页）；宽字符由 `wchar_t` 支持。
- **官方资料依据**：[WG14-N1570 §7.1.1, §7.24](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

### L1-C-03 字节进必须字节出，不得经过字符编解码层
1. **源码触发条件**：源码以**字节**为单位读写并处理数据：`fread`/`fwrite`/`read`/`write`、对字节数组求哈希或摘要、Base64/压缩/二进制协议帧、以及对长度按字节计量的操作。
2. **冻结版本/运行时/API 前提**：ISO C11；`fopen` 的文本/二进制模式与 `setvbuf` 见 [WG14-N1570 §7.21.5](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)，Windows CRT 的文本模式翻译见 [Microsoft `fopen`](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/fopen-wfopen)。
3. **原可观察行为**：C 以 `char`/`unsigned char` 序列处理数据，**没有字符编解码层**；`fread`/`fwrite` 的计数单位是字节。但在 Windows CRT 的**文本模式**下，写出的 `\n` 会被翻译为 CRLF、读入的 CRLF 会被折叠为 `\n`，且 Ctrl-Z (`0x1A`) 可能被当作 EOF。
4. **目标可选写法和不适用条件**：
   - *C 作为源*：目标语言的字节层（`bytes`/`[]byte`/`byte[]`）必须承接这些数据；只有在明确需要文本时才显式解码，且解码失败的处理须与源一致。对 Windows 目标，字节路径必须使用二进制模式（`"rb"`/`"wb"`），否则静默改写字节。
   - *C 作为目标*：源语言若为文本类型，必须显式选定编码并在边界处一次转换；不得让 `fopen` 的默认文本模式把源里不存在的 CRLF 翻译引入进来。
   - *不适用条件*：源用途确为**终端文本行输出**且换行翻译本身是可观察行为时，文本模式是要**保留**的行为，不是缺陷；此时应在冻结记录中登记该差异而非消除它。
5. **错误机械替换反例**：
   ```c
   /* 错误：二进制内容走了文本模式，Windows 上被 CRLF 翻译与 Ctrl-Z 截断 */
   FILE *f = fopen(path, "w");
   fwrite(blob, 1, len, f);            /* 字节已被改写，长度随之变化 */
   /* 正确：字节进字节出 */
   FILE *f = fopen(path, "wb");
   fwrite(blob, 1, len, f);
   ```
   反向错误同样成立：把本应做文本行翻译的输出改成 `"wb"` 并手写 `\n`，会在 Windows 目标上丢掉源程序真实产生的 CRLF。
6. **信息不足或实现相关时的处理**：无法确认源数据是文本还是字节、或无法确认目标是否处于文本模式时，写“编码与文本/二进制模式待确认”，并**禁止**用替换字符（`scrub`、`invalid: :replace`、U+FFFD）掩盖差异——替换会改变长度与内容，属不可逆的信息丢失。
7. **直接官方 HTTPS 依据链接**：[WG14-N1570 §7.21.5](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)；[Microsoft `fopen`（文本/二进制模式）](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/fopen-wfopen)。

## 四、数组、容器、切片、迭代和顺序

- **数组/切片连续性与扩容**：`[语言规范保证]` 静态原生数组物理连续；动态数组依赖 `malloc`/`realloc` 手工管理，扩容可能迁移地址并使外部旧指针失效。
- **键值映射（Map/Dict）实现**：`[语言规范保证]` 无语言内建映射容器；必须依赖第三方库或手工哈希表。
- **Map 遍历迭代顺序保证**：`[语言规范保证]` 无原生规范；完全取决于手写实现。
- **迭代期间修改（Fail-Fast）**：`[语言规范保证]` 手写遍历中若发生重分配，旧迭代指针立即悬挂（UB）。
- **官方资料依据**：[WG14-N1570 §6.2.5, §7.22.3](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

## 五、异常、错误、退出码与可观察失败

- **语言级错误表示机制**：`[语言规范保证]` 返回值整数错误码（`int`）、输出参数或全局 `errno`（正整数，宏展开为线程局部左值）；无语言级异常。
- **异常展开与性能模型**：`[语言规范保证]` 无异常展开；`setjmp`/`longjmp` 仅做非局部长跳转（不调用析构/清理）。
- **进程退出码回传机制**：`[语言规范保证]` `exit(int status)` 或 `main` 返回值回传进程退出码；`[指定运行时的实现相关事实]` 操作系统对退出状态位宽的处理属于平台环境范畴。
- **跨语言映射关键风险**：严禁将 C 返回值机械替换为异常（会改变调用方控制流拓扑与执行开销）；`errno` 易受后续调用覆盖。
- **官方资料依据**：[WG14-N1570 §7.5, §7.22.4.4](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

### L1-C-04 源端被丢弃的错误不得在目标变成终止，源端主动失败不得被静默吞掉
1. **源码触发条件**：源码对可失败调用的返回值**有意忽略**（未检查 `errno`/返回值、忽略部分成功），**或**在失败时显式 `return` 非零、`exit(非零)`、`abort()`、`err()`/`errx()`。
2. **冻结版本/运行时/API 前提**：ISO C11；`errno` 为线程局部左值且**会被后续库调用覆盖**（[WG14-N1570 §7.5 ¶3](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)）。
3. **原可观察行为**：
   - 忽略错误的路径：C 不会自动终止，程序继续执行并以**当时能达到的结果**结束（可能写出空结果、部分结果或状态码 0）。错误本身不产生可观察信号，除非源另有诊断输出。
   - 主动失败的路径：以确定的非零退出码结束，调用方/脚本可据此判定失败。
4. **目标可选写法和不适用条件**（两个方向都必须覆盖）：
   - *源丢弃错误 → 目标不得变成异常终止*：目标语言的“抛错”必须在**源确实忽略该错误**的位置被显式转成非致命路径（返回值/`nil`/`Option`），保留后续执行与最终退出码语义。
   - *源主动失败 → 目标不得静默继续*：目标必须保留失败分支并传播非零退出状态；不得用宽泛的 `rescue`/`catch`/`except` 把它吞成成功。
   - *不适用条件*：若源**确实检查**错误并据此返回失败，则不得套用“忽略并继续”；此时应保留源既有失败分支。两类形态的判断依据是源码的实际检查行为，不是错误是否“看起来重要”。
5. **错误机械替换反例**：
   ```c
   /* 源：忽略 open 失败，后续仍产出空结果并以 0 退出 */
   FILE *f = fopen(path, "r");          /* 返回值未检查 */
   if (f) { while (fgets(buf, sizeof buf, f)) consume(buf); }
   /* 目标（错误）：让抛出的异常直接终止进程，改变了控制流 */
   /* target.py:  f = open(path)        # FileNotFoundError 未处理 → 提前终止 */
   /* 目标（错误之二）：把源里显式 return 非零的失败分支吞掉 */
   /* target.py:  try: ... except Exception: pass   # 静默继续 */
   ```
6. **信息不足或实现相关时的处理**：无法确认源是否检查返回值、是否输出诊断、或失败后是否继续时，把该错误路径单列为待验证 oracle，**不得**用“看起来无害”推断可忽略，也不得用“看起来严重”推断应终止。
7. **直接官方 HTTPS 依据链接**：[WG14-N1570 §7.5, §7.21.10.4, §7.22.4.4](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)。

## 六、内存、资源所有权、析构、GC 与终结

- **内存管理模型**：`[语言规范保证]` 手动显式管理（`malloc`/`calloc`/`realloc`/`free`）；无析构函数；无垃圾收集。
- **资源确定性释放机制**：`[语言规范保证]` **无语言级确定性作用域释放**；必须在每个函数出口、`goto cleanup` 或提前返回时手工释放。
- **垃圾收集（GC）停顿与机制**：`[语言规范保证]` 无 GC。
- **悬垂与泄漏防范**：`free` 后指针成为野指针（Dangling Pointer）；重复释放（Double Free）属于未定义行为（UB）。
- **官方资料依据**：[WG14-N1570 §7.22.3](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

## 七、异步、并发、取消与阻塞

- **语言内建并发原语**：`[语言规范保证]` C11 `<threads.h>`（可选支持，多平台缺失）；C11 `<stdatomic.h>` 提供语言级原子操作与内存序。
- **线程/调度实体映射关系**：`[语言规范保证]` 语言规范抽象执行线程；底层 OS 线程映射属于平台实现，规范不作映射保证。
- **级联取消与超时机制**：`[语言规范保证]` 无语言内建取消；依赖显式全局标志位、原子变量或条件变量广播唤醒。
- **内存模型与数据竞争**：`[语言规范保证]` C11 `<stdatomic.h>` 提供严格内存序（Acquire/Release/SeqCst）；无保护共享写属 UB。
- **官方资料依据**：[WG14-N1570 §7.17, §7.26](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)
