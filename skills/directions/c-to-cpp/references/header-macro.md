# 头文件与宏可用性：C → C++ 决策参考

本文件在 C 源依赖“隐式可见”的名字、而目标 C++ 构建下这些名字需要显式包含或限定时读取（典型触发：`min` / `max`，以及其他经平台头文件间接引入的宏或声明）。它是**规则与风险说明**，不保证目标代码可编译或行为等价；名字的真实来源头文件因 C 库/平台而异，须逐例核对源构建的实际包含链，不靠猜测补 `#include`。

`std::min` / `std::max` 位于 `<algorithm>` 是语言标准事实；具体任务还须核对源的实际包含链、目标版本和第三方诊断。模型自审结论不能代替编译证据。

## 1. 识别触发：C 隐式可见、C++ 需显式

- **触发条件**：C 源使用了本翻译单元未显式声明、又非语言关键字的名字（如 `min` / `max` / `MIN` / `MAX`，或 `bzero`、`strlcpy` 等），它们在源平台经某个被间接包含的头文件可见；到目标 C++ 构建（不同标准库、平台头链或标准）出现“未声明标识符 / 未定义”类诊断。
- **前提**：源与目标的头文件包含链、C 库实现、平台可能不同；同一名字在一侧是宏、另一侧可能是函数、模板或根本不可见。
- **映射边界**：用“C 源能用、目标报未声明”作为触发提示，逐例定位名字的**真实来源**（读源码 `#include` 链或该平台头文档），再决定补显式包含还是改用标准设施；不逐一穷举头文件，也不凭名字相似直接补一个 `#include` 就宣称修好。
- **未知处理**：来源头或其语义未核实时记为待确认，不静默替换。

## 2. `min` / `max`：从宏到 `std::min` / `std::max`

- **触发条件**：C 源使用 `min` / `max`，常来自 BSD 系 `<sys/param.h>` 等**平台头的宏**（非 ISO C 标准库；具体是否为宏、来自哪个头取决于平台，须核对）。
- **映射**：C++ 侧显式 `#include <algorithm>`，改用 `std::min` / `std::max`（`<algorithm>`，C++98 起；C++14 起为 `constexpr`）。[S1]
- **反例与风险**：
  - 宏 `min(a,b)` 展开为 `((a)<(b)?(a):(b))`，**两次求值**参数。`min(a++, b)` 在宏下自增两次；改成 `std::min(a++, b)`（函数模板，按引用取参、只求值一次）会改变可观察行为。先确认参数有无副作用，再判断能否等价替换。
  - `std::min` / `std::max` 是模板，两实参需**同类型**；C 宏对混合类型宽松。混合有符号/无符号或不同宽度时，改用 `std::min` 可能编译失败或需显式模板实参/先统一类型，并要保留原有算术转换与符号语义。
  - `std::min` / `std::max` 返回 `const T&`；对临时量取结果再延用可能悬垂。原宏得到的是值或表达式，生命周期语义不同。
- **前提**：目标 C++ 标准与标准库确定；`<algorithm>` 可用。

## 3. `<windows.h>` 的 `min` / `max` 宏冲突与 `NOMINMAX`

- **触发条件**：目标或某目标分支包含 `<windows.h>`（经 `windef.h` / `minwindef.h` 间接引入）。Windows SDK 头默认把 `min` / `max` 定义为**函数式宏**（形如 `#define max(a,b) (((a)>(b))?(a):(b))`），除非在包含前定义 `NOMINMAX`。[S2]
- **表现**：该宏会改写 `std::min` / `std::max`、`std::numeric_limits<T>::max()` 及任何名为 `min` / `max` 的成员/模板处的记号，典型是这些调用点报出“意外的标识符 / 语法错误”。
- **取舍**：
  - 需要标准设施且包含 `<windows.h>` 时，在包含前 `#define NOMINMAX`；或对调用点加括号 `(std::min)(a, b)`（函数式宏仅在名字后紧跟 `(` 时展开，加括号即抑制）；或局部 `#undef min` / `#undef max`。
  - `NOMINMAX` 是**项目级取舍**：定义后，凡依赖 Windows `min` / `max` 宏的其它代码都会受影响。跨 OS 目标要统一策略并在交付中记录；纯 POSIX 目标不涉及本条。
- **前提**：目标或分支为 Windows 且（直接或间接）包含 `<windows.h>`。

## 4. 整头缺失：平台专有系统头在目标构建不存在

前几节讲“名字隐式可见”，本节讲更硬的一类——**整个系统头在目标平台根本不存在**，`#include` 处直接 fatal error，命令行特性测试宏无法补齐：

- **触发条件**：源依赖某平台专有系统头（典型 FreeBSD-base：`<libutil.h>`、`<fts.h>`、`<sys/queue.h>`、`<sysexits.h>` 等），目标 glibc/MinGW 缺该头或其符号。
- **诊断依据**：只有实际目标工具链在对应 `#include` 处报告缺头，才判该环境缺失；`-D_POSIX_C_SOURCE` 等特性宏不能凭空提供未安装的头文件。
- **处理**：记录源侧和目标侧各自的真实 build 状态，核对可用依赖与源契约；目标侧若确需替换，应先查 API 语义与任务 oracle，不将 `humanize_number`、`fts` 或 `sys/queue` 机械改成表面相近的 C++ API。跨 OS 细节见系统方向 [`posix-windows-filesystem` §2](../../../systems/posix-windows-filesystem/SKILL.md)。
- **定序后果**：源基线失败若使 Controller 跳过目标 build，目标语法结论为 `UNVERIFIED`；若目标 build 独立返回证据，仍按该目标版本与命令据实判读。不得把源失败归因于目标转换。

## 5. 交付时的最小说明

涉及本主题时，指出：为哪些名字补了显式 `#include` 或限定、来源头是否已核实、是否存在参数副作用导致“宏 → 函数模板”替换改变求值次数、是否设置 `NOMINMAX` 及其影响范围。没有第三方编译证据前，只能说**据语言标准与已核来源作了静态修正，尚未验证**；不得据此写 `syntaxPassed`。

## 依据与适用边界

- [S1：WG21 N4950，C++23 最终工作草案](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2023/n4950.pdf)：`[algorithm.syn]`、`[alg.min.max]`（`std::min` / `std::max` 在 `<algorithm>`）。目标是其他 C++ 版本时须核对相应标准。
- **S2：Windows SDK 头 `minwindef.h`（`<windows.h>` 经 `windef.h` 间接包含）** 定义 `min` / `max` 宏与 `NOMINMAX` 开关——以本机 SDK 头实际内容为准逐例核对，不同 SDK 版本可能不同；社区问答仅作发现线索，不作权威依据。

`<sys/param.h>` 的 `min` / `max` 属平台/实现扩展，非 ISO C；来源与是否为宏须按源实际 C 库与平台文档逐例核对。以上是语言与平台规则依据，不是特定编译结果的验证记录。
