# 类型、接口与 C ABI：C → C++ 决策参考

本文件在转换涉及共享头文件、C 对外接口、二进制数据布局、整数/指针类型或 C 风格初始化时读取；普通内部逻辑不必加载。它是**规则与风险说明**，不是“C 与 C++ ABI 总能兼容”的保证。先问清源 C 标准、目标 C++ 标准、平台/编译器，以及哪些对象或符号会被 C 代码、外部库或二进制格式使用。

## 1. 判断边界在哪里

| 条件 | 处理 | 不要做 |
|---|---|---|
| 只是同一 C++ 程序内的实现细节 | 保留原类型语义即可；可在明确所有权和调用方后重构 | 为了“更像 C++”强加 C ABI 约束 |
| C 编译单元、已有 C 库或外部调用方仍要链接 | 逐一盘点导出函数、全局对象、回调类型和共享头文件；保持接口声明与实际实现一致 | 只给定义补 `extern "C"`，却让调用方看到不同声明 |
| 结构体、枚举、缓冲区直接跨边界或写入二进制格式 | 保留字段类型、顺序与约定；将布局/对齐、位域、打包和目标 ABI 记为待确认条件 | 仅凭字段名一样或 `standard-layout` 就宣称二进制兼容 |

`extern "C"` 指定 **C 语言链接**：涉及有外部链接的函数/变量名称和函数类型；具体名称表示、调用约定等属性取决于实现。它不自动规定共享结构体布局、第三方库 ABI、参数的所有权或异常边界。不要把 C 接口函数改成重载或成员函数后仍宣称旧调用方可无改动链接。参见下方 [S1] 的 `[dcl.link]`。

如果共享头文件同时由 C 与 C++ 编译器读取，按已有项目约定用 `#ifdef __cplusplus` 限定 C++ 侧的 `extern "C"` 声明；不要把 C 不认识的 C++ 类型放进该接口。回调参数的函数类型也要检查，不能只看外层函数名。[S1]

## 2. 数据布局不是类型名字的同义词

- C++ 的 `standard-layout` 类型适合与其他语言沟通，但这个性质**不是**“任意 C 编译器下相同布局”的跨实现承诺。特别留意虚函数、基类、访问控制、非标准布局成员；位域、填充、对齐、编译器打包选项和目标 ABI 仍需另外确认。[S1: `class.prop`, `class.mem`]
- 如果旧接口使用 `sizeof(T)`、`offsetof(T, field)`、把结构体按字节序列化，不能为了封装加入 `std::string`、虚函数或改变字段顺序。C++ 中对非 `standard-layout` 类使用 `offsetof` 仅为有条件支持；更不能据此证明 C 一侧的布局相同。[S1: `support.types.layout`]
- 若源类型或目标 ABI 尚未明确，将布局兼容写为**未确认**，保留原始共享声明或要求目标平台资料。不要通过添加强制类型转换来掩盖布局风险。

## 3. 整数与字符类型

- 不自动把 C 的 `int`、`long` 或 `char` 改成看似“固定宽度”的类型。先核对字段/参数是否为外部契约、目标实现的范围与宽度、符号性及溢出路径；C++ 标准整型宽度除最低要求外由实现确定，`char` 的底层符号性也由实现选择。[S1: `basic.fundamental`]
- 如果某个整数参与二进制格式、位运算或数组长度，保留其有符号/无符号约定，并在缺乏平台信息时说明不能确认数值范围等价。强行替换类型可能同时改变布局、算术转换和外部接口。
- 不将 `bool`、枚举或位域在 C/C++ 边界上简单视为 `int`；只有接口契约和目标 ABI 给出表示依据时才作此映射。

## 4. `void*` 与初始化语法

- C 允许对象指针与 `void*` 的相关转换；在 C++ 中，对象指针可隐式转到 `void*`，反向通常需要**显式**转换。若已确认原指针确实指向/承载适合目标类型的对象，并保持 cv 限定与对齐要求，可考虑 `static_cast<T*>(p)`；显式转换只解决类型检查，不证明对象生存期、真实类型或释放方式正确。[S2: §6.3.2.3；S1: `conv.ptr`, `expr.static.cast`]
- 当 `p` 来源于 `malloc` 时，增加必要转换不意味着要把 `free` 换成 `delete`。分配/释放配对与对象生存期应在所有权专题单独判断，不能以“现在编译得过”为依据。
- C 的初始化语法不能不看目标 C++ 标准直接复制。若目标是 C++20 及以后，指定成员初始化的成员顺序需符合声明顺序；旧目标标准或其他 C 指定形式须另行处理。不要只为通过语法检查调整初始化顺序，却忽略各初始化表达式的副作用。[S1: `dcl.init.list`, `dcl.init.aggr`]

## 5. 标识符与系统类型/符号名冲突

C 源在 C++ 与目标平台头下可能因名字冲突阻断；先定位声明、作用域、真实诊断及内外接口，再决定修订，不以名称相同直接改名：

- **本地 `typedef` 与系统类型冲突**：例如 `typedef long long off_t;`，先核目标包含链、声明与作用域；已确认仅内部别名且冲突时，可由配置模型改独立别名并核全量引用，保持原类型语义。名称相同本身不证明冲突。
- **本地函数/变量与库符号冲突或遮蔽**：例如名为 `realpath` 的本地包装，先核实际查找结果与内外接口；已确认内部冲突时可消歧，不将系统符号与所有同名局部量一律改名。
- **自定义状态声明顺序问题**：如 getopt 状态副本的使用点先于所需声明，定位后可调整声明安排；必须同时保持作用域、初始化时机、重复调用状态与可观察副作用，不无条件上移。

上述条目只作风险线索，不是本任务的编译证据或无条件改名授权。仅内部符号且冲突已定位时，配置模型可消歧并核所有使用点；公开 ABI、导出名称、序列化字段和输出文本须先核外部契约，不机械改名。声明上移另核初始化时机、可见性与副作用；本任务是否构建通过仍以精确版本的真实编译诊断定案，改动按既有有限修复流程调度。

## 6. 交付时的最小说明

涉及跨边界内容时，指出：保留了哪些 C 接口、哪些数据布局假设未确认、目标标准与编译器/ABI 假设、哪些类型转换只是语法修复而非行为证明。没有编译与动态证据时，只能说**根据已知约束作了静态转换，尚未验证**。

## 依据与适用边界

- S1：WG21 N4950，C++23 最终工作草案：`[dcl.link]`、`[class.prop]`、`[class.mem]`、`[support.types.layout]`、`[basic.fundamental]`、`[conv.ptr]`、`[expr.static.cast]`、`[dcl.init.list]`。文中指出的是 C++23 草案依据；目标是其他版本时须核对相应标准与实现文档。
- S2：WG14 N1570，C11 委员会草案：§6.3.2.3 指针转换。它不是所有 C 方言或 C23 行为的通用替身；遇到版本相关语法应重新核对源标准。
