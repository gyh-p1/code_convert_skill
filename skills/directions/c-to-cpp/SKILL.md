# C → C++ 转换

## 适用范围与前提

用于将已有 C 代码转换为 C++，优先保持行为，再考虑惯用写法。先确认目标 C++ 标准、目标平台/编译器、调用方是否依赖 C ABI、是否允许引入 C++ 标准库与异常；用户未指定时不要假设可以改变接口、错误模型或分配方式。不能仅凭本 Skill 保证目标代码编译或行为等价。

## 转换时优先守住的行为

- **接口与数据布局**：保留公开函数签名、返回值约定、结构体布局、整数宽度及符号性假设。跨 C/C++ 边界暴露的符号要判断是否需要 `extern "C"`；它指定语言链接（具体名称表示和调用约定取决于实现），不自动保证对象布局或整体 ABI 兼容。
- **控制流与错误**：保留提前返回、错误码、`errno` 的读写时机、清理分支和部分成功状态。不要未经授权将错误码改为异常，也不要让异常跨越 C ABI 边界。
- **资源与副作用**：保持文件/句柄关闭、内存释放、锁释放和回调调用的时机及顺序；不要为了换成 RAII 而改变共享所有权、生命周期或失败路径。标准输出、文件、环境变量、进程等外部可见行为同样属于转换范围。
- **边界条件**：检查空指针、零长度、溢出/截断、缓冲区边界、字符编码以及未定义或实现定义行为。源程序本身没有确定语义的地方，不宣称存在唯一等价转换。

## 按需专题

遇到共享头文件、C ABI、结构体/整数布局、`void*` 或指定成员初始化时，读取 [类型、接口与 C ABI](references/type-abi.md)。若源码实际执行 socket 或协议 I/O，再共同阅读 [网络 I/O 场景](../../scenes/network-io/SKILL.md)；其中套接字调用还跨越 Linux/POSIX 与 Windows 时，加读 [POSIX ↔ Winsock 套接字系统方向](../../systems/posix-winsock/SKILL.md)。源码确有文件系统操作时，共同阅读 [文件 I/O 场景](../../scenes/file-io/SKILL.md)。这里只保留入口提醒，具体适用条件和依据在专题文件中。

## 常见映射的决策条件

| C 写法 | C++ 选择 | 不应机械替换的原因 |
|---|---|---|
| `malloc` / `free` | 可先保留，明确独占所有权后才考虑容器或 RAII | 
ew` / `delete` 不是其配对替代；初始化、失败处理和释放约定不同 |
| `char*` + 长度 | 保留指针与长度，或在明确所有权、编码和嵌入 NUL 语义后使用 `std::string` | C 字符串、二进制缓冲区和 `std::string` 的接口及生命周期不同 |
| 指针数组 / 手工容量 | 必要时先保留；确认扩容、别名和对外暴露约定后才用 `std::vector` | 容器重分配可能使外部保存的指针失效 |
| `FILE*` / 文件描述符 | 先保持原 API；所有权独立且关闭时机允许变化时才封装 | 异常、缓冲、关闭错误和平台差异可能改变可观察结果 |
| 宏与回调 | 根据求值次数、作用域及调用约定选择保留或改写 | 内联函数、模板和 lambda 不自动复制宏展开语义或 C 回调 ABI |

## 模型转换后自检与 repair 预判（非独立语法评估）

转换模型返回代码后，可以让模型按源/目标差异做一次**自评**，用于发现可能遗漏、类型/API 不匹配、分支丢失、占位/截断、错误路径和资源生命周期等疑点，并建议是否需要 repair。此步骤是**模型自评/预检**，不独立、不客观，不能充当语法正确率、编译通过或第三方评估结论；模型说“没有问题”也不等于无缺陷。不得给该结果贴 `TEXT-REVIEWED`、`syntaxPassed` 或类似客观检查标签。

自检至少核对：

1. 目标源码是否完整，关键声明/定义/入口是否保留，是否有省略、占位或意外的目标平台分支遗漏；
2. C++ 类型/声明风险：`void*`、内存分配返回值、限定符、回调/调用约定、宏冲突、初始化形式和声明/定义/调用点一致性；
3. 目标 OS API 的调用签名、参数宽度、错误返回处理是否与任务要求和已选系统 Skill 一致；未知 SDK 细节记作待核，不伪装成确定错误；
4. 对照源代码区分转换引入的问题和源代码已有的问题。修复仅针对可定位的转换缺陷；源缺陷不得静默改写，行为重构需明确授权；
5. 记录发现、证据位置、影响、置信度和建议动作。由模型判断 `REPAIR-RECOMMENDED` 或 `NO-REPAIR-IDENTIFIED`，前者仅表示值得修订，不表示已经客观确认编译失败；修订后可再做一次模型自检。 `NO-REPAIR-IDENTIFIED` 只允许进入[闭环工作流](../../../references/conversion-evaluation-loop.md)的评估准备，不是语法结论；独立编译器返回诊断后，先分清环境/工具链/代码来源，再将可定位代码错误和工具链上下文交给配置模型决定是否 repair；Agent 不得自行发明修复并冒称来自模型。

**语法结论来源：**按用户指定的评估契约，由第三方评估机构在匹配的目标 OS、架构、编译器/SDK 和 C++ 标准下执行编译。若契约将成功编译作为静态语法正确标准，则只把第三方的真实编译成功记录为该配置下的语法通过；编译失败按诊断记录。模型自检、文本检查和 API 名称相似性都不能写成 `syntaxPassed`。未取得第三方结果时记 `AWAITING-THIRD-PARTY-COMPILE` / `UNVERIFIED`。编译通过仍不证明行为等价或安全。 编译失败后必须保留失败稿、诊断、模型补丁建议和重试证据；在同一冻结工具链上重编译修订变体，只能把通过归给该变体，不能回写成原始稿通过。若用宏或命令探查区分工具链噪音与源码诊断，必须单独记录；不得用 `-D_MSC_VER` 等宏伪造编译器身份来代替真实 MSVC/Pelles 工具链。

本机不得为项目样例编译、运行、调用构建脚本或触发代码生成；第三方评估证据与模型自检记录必须分开存放、分开汇报。 经逐例取得用户明确授权后，可以把 comparison capsule 提交到隔离的第三方 Runner；第三方证据必须与模型自评分开保存、分开汇报。
## 操作方式

1. 找出对外入口、共享数据、可观察副作用和各条失败路径；针对用户给定的片段，不推断未提供的调用方约定。
2. 以最小语义改动形成可读的 C++ 代码。C 代码能在目标 C++ 环境中成立的部分可以保留，不为了展示现代语法而全面重写。
3. 在交付说明中指出关键转换选择、仍依赖的标准/平台假设，以及需要用户确认的接口或未定义行为。模型自检/repair 预判、第三方编译语法结果、行为结果分开报告；没有第三方编译结果时写 `AWAITING-THIRD-PARTY-COMPILE` / `UNVERIFIED`，不得把模型自评写成语法通过。

本项目现阶段只编写和审阅 Skill 文本；不在本机运行转换样本，若逐例获批则可交给隔离第三方 Runner。请同时遵守根入口和 [安全边界](../../../references/safety-boundary.md)。
