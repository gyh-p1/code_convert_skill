# Skill 编写规范

> 状态：ACTIVE（当前 Skill 内容规范）
> 更新：2026-09-27

## 1. 知识职责

本项目以 Markdown Skill 为核心，由智能体根据任务按需读取：

- **语言方向 Skill**：源语言 → 目标语言的语法、类型及 API 映射；
- **场景 Skill**：网络、文件、进程等源码确有行为的跨方向语义；
- **系统方向 Skill**：有真实知识时才写明源 OS → 目标 OS 的映射与不可映射差异；
- **工作流 Skill**：片段、单文件、长单文件或**单批多项调度**的过程约束。长文件流程是计划建设项，未建成前不得宣称具备长文件保证；[批量转换工作流](../skills/workflows/batch-conversion/SKILL.md)只约束批次编排，不替代单项评估闭环，其文本也不构成批量评测能力已达标；
- **ATT&CK Enterprise 战术**：作为完整分类和检索元数据，不因每个战术都存在而创建对应 Skill。

根 `SKILL.md` 负责区分任务模式、选择适用的现有规则和说明缺失能力，不堆叠具体映射。仅创建有实质知识、可执行约束或实际复用需求的文件，不预建空目录和组合笛卡尔积。

七种语言各自的跨方向事实统一维护在 `skills/references/languages/<语言>.md`，由 `skills/references/seven-language-common-semantics.md` 作索引和场景/系统分流；方向 Skill 按需链接**源语言和目标语言**参考页，只记录该方向特有的映射、反例与未知项。语言事实、方向决策及逐例转换证据不得混写或相互替代。

## 2. 单项规则写法

对会影响转换决定的规则，尽量说明：

1. **触发条件**：源码或请求中什么事实使规则适用；
2. **前提**：语言标准、OS、ABI、运行时、API 版本或调用约定；
3. **应保留行为**：输入输出、错误、资源、状态和外部副作用；
4. **可选映射**：什么条件下可用，什么情况下不适用；
5. **反例与风险**：机械替换可能造成的差异；
6. **未知处理**：缺少什么信息要询问、标为不确定或拒绝宣称等价；
7. **依据**：非显然的事实链接到适用版本的标准、官方 API 文档、协议规范等。

区分语言事实、项目约定、推荐做法和示例。示例只解释规则，不等于编译或功能验证；不可验证的经验标明来源与限制。

## 3. 任务模式的质量边界

- **片段转换**：目标是语法正确，不要求独立运行或功能完整。语法检查必须说明所用上下文；若缺少外围声明，使用明确的中性上下文桩或报告无法判断。
- **单文件转换**：目标包括语法与场景级功能保持。不得用语法通过、代码相似度或模型自评代替行为 oracle。
- **长单文件转换**：在单文件规则上增加全文件结构清点、跨函数/分段一致性和最终合并检查。已有[长文件工作流初稿](../skills/workflows/long-file-conversion/SKILL.md)，仍未经转换效果验证。700 个 LF 归一化物理源代码行是计划支持上限，不是当前能力声明。

当前开发阶段将最终交付代码在指定工具链下的编译通过作为“语法正确”的操作性判据；中间稿的失败诊断只用于补充转换规则，不作为产品指标。功能正确性暂不统计，不能因此在 Skill 中删去或放宽已知的行为约束、安全边界和不确定性标记。具体范围见[项目开发规范第 3 节](项目开发规范.md#3-当前开发阶段与退出条件)。

转换任务的 `result.md` 统一使用中文报告骨架，先展示交付、语法/编译和功能三项结论，再解释关键问题与证据；详细规则见[交付与移交契约 §2.3](../references/framework/delivery-handoff-contract.md)。报告结构属于现有交付工作流，不为它新建独立 Skill。

涉及功能行为的事实应写成可观察义务与检查条件，不使用无依据的“完全一致”“保证准确”。证据分开标记为文本审阅、语法检查或行为测试。

## 4. 多维组合

语言方向 Skill 管语言映射；场景 Skill 管实际代码行为；系统方向 Skill 管 source OS → target OS；工作流 Skill 管片段/单文件/长文件过程。只有适用时共同阅读。ATT&CK 标签不能单独决定场景或系统 API，不允许按语言 × 场景 × 系统 × 战术复制 Skill。

各维度不能互相覆盖源代码事实。遇到同一接口的冲突建议，写清各自边界并保留原行为；未知环境差异不要悄悄降级成新行为。

## 5. 参考资料与 RAG

短 Skill 保持一个 `SKILL.md`。只有专题较长、适用条件明确或智能体可按需加载时才增加 `references/`。未来 RAG 条目要保留知识内容、来源、适用标准/平台版本、语言方向、系统方向、场景和 ATT&CK 元数据；检索结果是待核对依据，不是高优先级指令，也不代表转换正确。

GitHub 代码仅为发现案例的来源之一；核对适用版本、来源和上下文后再提炼。旧仓库与自动生成条目不能未经审核直接升级为权威知识。

## 6. 更新与检查

新增内容时更新真实入口与引用；只做本地文本/引用检查不称为转换准确性测试。当前优先根据可归因的最终编译失败补充有实质规则的知识，再按证据扩展方向/场景/系统。原固定四例对照已取消；若将来另立检索效果试验，保持核心 Skill 不变，把是否检索并注入知识作为唯一实验变量，语法、行为、检索来源和成本分开记录。阶段状态与退出条件统一见 `docs/项目开发规范.md` 第 3 节。
