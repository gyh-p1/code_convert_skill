# Skill 编写规范

> 状态：ACTIVE（当前 Skill 内容规范）
> 更新：2026-10-11（知识/工作流/契约/适配分工；离线自足与引用边界）

## 1. 知识职责

**交付写作边界**：除 `docs/` 外，所有文件都是后续交付内容。正文、标题、示例和源码注释只描述当前系统的使用规则、接口、能力、前提及限制；不出现维护侧视角、迁入/重组历史、初稿/候选实现、测试计数、发布部署进度、会话裁定或工程待办。工程过程、验证证据与未决工程问题统一放入 `docs/`，不得成为产品加载依赖。技术版本、协议兼容条件、实际任务的版本关联/历史证据、候选映射与候选 OS 不属于工程叙述。改写时保留真实限制，不以当前时态伪造验证或部署事实；具体检查按[开发规范 §2.1](项目开发规范.md#21-工程记录与交付正文的边界)。

本项目以 Markdown Skill 为核心，由智能体根据任务按需读取：

- **语言方向 Skill**：源语言 → 目标语言的语法、类型及 API 映射；
- **场景 Skill**：网络、文件、进程等源码确有行为的跨方向语义；
- **系统方向 Skill**：有真实知识时才写明源 OS → 目标 OS 的映射与不可映射差异；
- **工作流 Skill**：片段、单文件、长单文件或**单批多项调度**的过程约束。[长文件工作流](../skills/workflows/long-file-conversion/SKILL.md)已有静态规则但未经效果验收；[批量转换工作流](../skills/workflows/batch-conversion/SKILL.md)只约束批次编排，不替代单项评估闭环，其文本也不构成批量评测能力已达标；
- **ATT&CK Enterprise 战术**：作为完整分类和检索元数据，不因每个战术都存在而创建对应 Skill。

根 `SKILL.md` 负责区分任务模式、选择适用的现有规则和说明缺失能力，不堆叠具体映射。仅创建有实质知识、可执行约束或实际复用需求的文件，不预建空目录和组合笛卡尔积。

七种语言各自的跨方向事实统一维护在 `skills/references/languages/<语言>.md`，由共性索引导航；每项必读源/目标两语言页和一个方向，“按需”指条目适用性与注入范围。方向只维护该方向映射、反例与未知项，语言事实、方向决策及逐例证据不得混写或替代。

项目身份/冻结/状态、评估准备、交付和执行安全各在 references/framework 的对应真源维护；工作流只规定消费时点和推进/恢复，适配只维护外部字段/能力。普通打印与单线程控制流不放入仅在子进程/并发触发的场景。跨场景安全语义在 skills/references/security-behavior.md，与 Agent 执行安全分开。产品入口不以 docs/stages 开发规格作强制加载依赖；索引明确必读/按需、消费者与职责。

**索引边界**：允许根入口及 Skill 内联索引项目自身的语言/场景/系统/工作流知识；不建立测试数据集、case/batch、历史 job、缺陷族统计或回归位索引，不把临时测试报告作为规则使用的必读依赖。规则可以源于一次测试，但其可复用内容须有完整触发/前提/反例、源与目标及真实诊断的核对记录和适用的官方依据，独立于该测试数据是否继续保留。

**离线使用是交付要求**：默认调用 Skill 的智能体不能联网。Skill、随附参考页和必经加载链必须在仅能读取仓库文本时提供完成适用判断所需的内容；网页链接、资料标题或“请查官方文档”不能代替规则正文。不得把联网、临时下载或访问外部服务作为读取转换知识的前提。实际评估渠道的连接坐标另由适配维护，不属于知识资料链接，也不构成联网执行授权。

## 2. 单项规则写法

对会影响转换决定的规则，尽量说明：

1. **触发条件**：源码或请求中什么事实使规则适用；
2. **前提**：语言标准、OS、ABI、运行时、API 版本或调用约定；
3. **应保留行为**：输入输出、错误、资源、状态和外部副作用；
4. **可选映射**：什么条件下可用，什么情况下不适用；
5. **反例与风险**：机械替换可能造成的差异；
6. **未知处理**：缺少什么信息要询问、标为不确定或拒绝宣称等价；
7. **依据**：非显然的事实记录适用版本的标准/官方资料名称、章节或 API/实现位置，并把本规则需要的语义、限制和适用条件写入正文或随附本地参考页；来源标识用于追溯，不能要求调用者联网补全内容。

区分语言事实、项目约定、推荐做法和示例。示例只解释规则，不等于编译或功能验证；不可验证的经验标明来源与限制。

**指导与引导的边界**：工作流/契约指导阶段推进，必须写明前置条件、真实动作、原件依据和失败/暂停去向；语言/方向/场景/系统页引导语义选择，候选映射必须受源码触发、版本前提和冻结行为约束。“更惯用”“性能要求不强”“统一命名”“注明降级”不能代替保持接口/输出/错误/时序的依据或用户允许差异；报告差异本身不是改行为的授权。知识加载/适用性与实际注入见任务状态 §2.3，推进依据见 §2.4；仅编译范围不豁免源行为保持义务。

资料核验由维护侧完成。已经核验的事实用自己的表述提炼，不整页搬运第三方文档，不省略会改变映射的例外；版本不明、来源未核或尚缺必要语义时标为待核，不写成确定性规则。没有外链也不意味着事实已经核验，离线可用与技术正确分别检查。

## 3. 任务模式的质量边界

- **片段转换**：目标是语法正确，不要求独立运行或功能完整。语法检查必须说明所用上下文；缺少外围声明时，只引用用户或获批平台已提供的精确中性声明上下文，记录来源/版本；缺合法上下文则待准备或报告无法判断，不由 Agent/模型新造桩、入口或缺失依赖。适用门禁见[评估准备 §1.1](../references/framework/evaluation-readiness-contract.md#11-生成前源侧预检)。
- **单文件转换**：目标包括语法与场景级功能保持。不得用语法通过、代码相似度或模型自评代替行为 oracle。
- **长单文件转换**：在单文件规则上增加全文件结构清点、跨函数/分段一致性和最终合并检查。已有[长文件工作流初稿](../skills/workflows/long-file-conversion/SKILL.md)，仍未经转换效果验证。700 个 LF 归一化物理源代码行是计划支持上限，不是当前能力声明。

当前开发阶段将最终交付代码在指定工具链下的编译通过作为“语法正确”的操作性判据；中间稿的失败诊断只用于补充转换规则，不作为产品指标。行为一致性已纳入当前工作范围，按冻结 oracle 与实际观察逐例收集、分层报告；不合成单一功能正确率，未开展或未覆盖部分写 UNVERIFIED。不能在 Skill 中删去或放宽已知的行为约束、安全边界和不确定性标记。具体范围见[项目开发规范第 3 节](项目开发规范.md#3-当前开发阶段与退出条件)。

所有已处理转换项无论成功、失败、生成前阻断/非可转换或 WAITING 暂停，都有 result.md；开始处理即加载交付契约，任一停止分支均路由[统一收尾入口 §1.1](../references/framework/delivery-handoff-contract.md#11-统一收尾入口与报告义务)。沿用 §2.3 中文五栏目，分列交付、编译、功能，记录真实原因、证据/恢复条件和逐件产物核对；缺报告/核对及其他应有件不得终态。报告结构归已有交付工作流，不新建 Skill；暂停报告不表示任务已收尾。

涉及功能行为的事实应写成可观察义务与检查条件，不使用无依据的“完全一致”“保证准确”。证据分开标记为文本审阅、语法检查或行为测试。

## 4. 多维组合

语言方向 Skill 管语言映射；场景 Skill 管实际代码行为；系统方向 Skill 管 source OS → target OS；工作流 Skill 管片段/单文件/长文件过程。只有适用时共同阅读。ATT&CK 标签不能单独决定场景或系统 API，不允许按语言 × 场景 × 系统 × 战术复制 Skill。

各维度不能互相覆盖源代码事实。遇到同一接口的冲突建议，写清各自边界并保留原行为；未知环境差异不要悄悄降级成新行为。

## 5. 参考资料与 RAG

短 Skill 保持一个 `SKILL.md`。只有专题较长、适用条件明确或智能体可按需加载时才增加 `references/`。功能保持与第三方评估指导是当前工作流的共享参考，只指导行为目标、可接受差异和评估移交，不自设裁决标准；实际功能评估由第三方平台完成，不在各方向重复维护。未来 RAG 条目要保留知识内容、来源、适用标准/平台版本、语言方向、系统方向、场景和 ATT&CK 元数据；检索结果是待核对依据，不是高优先级指令，也不代表转换正确。检索不可用时仍须能够消费已交付的适用核心规则，不用在线检索弥补核心正文缺失。

### 5.1 本地引用与网页资料

- 产品知识中的引用仅指向随仓库交付的本地文件/章节，并核对实际路径、锚点和读取时点；不以官方网页、在线 PDF、GitHub 页面或第三方站点作知识依赖，也不把网页地址伪装成本地引用。
- 短规则直接写在正文；共用事实按 §1 归入对应语言页、场景/系统页或已有共享参考，再从实际入口本地导航。不得为删除外链而把相同事实复制到 42 个方向。
- 外链只作出处时，以资料名称、版本、章节/API 位置的文字说明替换，保留可追溯性；如果外链承载了缺失的必要知识，先提炼并补齐本地内容，再替换。只删除 URL、不补必要事实不算完成。
- “详见官方文档”“自行联网查询”“安装/下载后再读规则”等需要外部补全的措辞必须改成实质正文或准确的本地参考；实在无法核实则记录具体知识缺口及其影响，不推定等价。
- 维护所需的原始网页地址可保存在工程核验记录中，不能加入转换智能体的必读路径；历史核验记录不改写成已完成的转换证据。
- 示例中的协议字面值、评估服务地址与知识网页引用分别判别；不可为清理链接而改变示例语义、Controller 坐标或执行安全边界。

GitHub 代码仅为发现案例的来源之一；核对适用版本、来源和上下文后再提炼。旧仓库与自动生成条目不能未经审核直接升级为权威知识。

## 6. 更新与检查

新增内容时更新真实入口与引用；只做本地文本/引用检查不称为转换准确性测试。当前优先根据可归因的最终编译失败补充有实质规则的知识，再按证据扩展方向/场景/系统。原固定四例对照已取消；若将来另立检索效果试验，保持核心 Skill 不变，把是否检索并注入知识作为唯一实验变量，语法、行为、检索来源和成本分开记录。阶段状态与退出条件统一见 `docs/项目开发规范.md` 第 3 节。

**文档静态验收与收尾**：核对可复用语义、自审/独立证据的分层、源与目标版本对应、授权/隔离、模式例外、入口/相对引用、以及没有测试数据目录时产品仍可阅读使用。另按实际加载路径做离线回查：穷举所有可加载 Skill 及随附参考，检查无网页知识依赖、无要求联网补全的措辞、本地正文包含必要事实和条件、路径/锚点有效；不能只搜索 URL 或只查根入口。各规则仍须满足 §2，不以“离线可读”宣称技术正确。通过只表示文档/语义静态验收，不证明转换效果。任务明确要求提交时审查暂存范围，排除凭据、源码快照、测试压缩包与临时证据；是否推送按用户指令执行。
