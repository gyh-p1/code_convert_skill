# 项目业务文档和能力边界

> 文档类型：当前产品定位与能力边界
> 状态：ACTIVE（本项目业务范围唯一真源）
> 更新：2026-10-07
> 读者：项目开发者、接入智能体的开发者
> 失效条件：被明确确认的新业务定位替代；实现状态变化应原地更新

## 1. 最终业务定位

本项目建设**面向网络攻防相关代码的转换知识 Skill**，由智能体接收指令、读取适用知识，并在本工作区调度 `.env` 配置的外部模型生成目标代码。智能体负责画像、Skill 选择、请求、静态核对和移交，不自行冒称模型输出。Skill 提供语言、行为场景、系统迁移和长代码工作流知识；Skill 本身不是独立转换程序，不负责模型服务或正式等价裁决。

输入任务先区分两种交付模式：

| 模式 | 目标质量 | 不承诺 |
|---|---|---|
| **片段转换** | 在用户给定或明确声明的上下文中，目标片段语法正确 | 可独立运行、完整功能或与完整程序行为等价 |
| **单文件转换** | 目标文件语法正确，并按给定场景与检查依据尽可能保持功能行为 | 未经测试/证据支持的普遍等价保证 |

长单文件是单文件模式的规模子类，需要额外的结构清点和分段一致性工作流。**交付要求至少完成一次不低于 600 行的等价转换；原 700 个 LF 归一化物理源代码行是既有计划上限目标，二者都不是当前已实现或已验收能力。**行数是规模/容量边界，不是性能指标；性能若要纳入需求，须另行定义时延、资源或成本测量。未来验证该范围时须先冻结 LOC 计数口径，另记录有效代码行、token 数和逻辑密度，避免用填充行凑规模。

### 交付目标冻结（2026-09-29）

以下是本次交付的**需求基线**，不是当前实现或验收通过的声明；优先级高于此前仅围绕 C → C++ 和最终编译质量的阶段计划。验收须提供逐项证据，不以 Skill 文件数量或标签数量代替转换效果。

| 维度 | 冻结的目标 | 验收时须区分 |
|---|---|---|
| 语言 | C、C++、C#、Python、Golang（Go）、PowerShell、Ruby 七种语言，所有不同语言的源→目标双向转换，共 7 × 6 = 42 个有向方向 | 逐方向记录标准/运行时、适用条件、知识与转换证据；一条方向的案例不外推为普遍等价 |
| 战术场景 | 覆盖不少于 10 个不同的 ATT&CK Enterprise 战术类别，每类均有代码案例和转换证据 | 战术 ID 与源码实际行为证据、所用语义规则和逐例结果分开记录；不以标签覆盖冒充转换能力 |
| 目标操作系统 | Windows、Linux、macOS 等不少于 3 类；历史登记过三类 runner | 逐任务核对当时可用性、源/目标 OS、工具链和适用 API；runner 就绪也不等于隔离通过或转换通过 |
| 长代码 | 一次性代码等价转换不低于 600 行 | 冻结源文件的 LF 归一化物理行数及有效代码行、token/逻辑密度；同一任务的最终完整目标、编译及预先定义的行为 oracle 分别留证，不能以编译通过代替等价 |
| 自动化评测 | 一次提交不少于 40 个代码转换任务，允许排队，自动调度并完成逐任务评测 | 不要求 40 路并发；须记录提交批次、队列/状态、隔离与资源限制、逐任务结果及汇总；人工逐项触发或 40 条静态记录不算 |

**已确认的计数口径**：C 与 C++ 分开，42 个方向均需显式覆盖；至少 10 个不同战术 ID 各有源码行为依据、案例和转换证据；40 项是单次提交、允许队列执行，不是 40 路并发。单个任务固定一个源→目标方向，因此若逐方向至少一例，候选任务池至少需 42 项；可在同一批次提交 42 项来同时验证方向覆盖与“≥40 项批量调度”，但逐方向案例只构成最低覆盖证据，不等于该方向普遍可靠。三个维度可由同一任务共同覆盖，不要求预生成 42 × 10 × 3 种组合；只有实际适用的组合才按源码行为与目标环境验证。等价以冻结任务的可观察行为义务与 oracle 为准，不能从语法/编译通过推断。

这些目标扩大了现有阶段 1 的边界，特别是功能等价与 40 任务自动化评测；当前实现与证据仍以下文“当前真实能力”和[项目开发规范](项目开发规范.md#3-当前开发阶段与退出条件)为准。两周交付窗口内应先做差距/资源核验，再分批补知识与取得反馈，最后回归封版；若证据无法覆盖目标，明确报告未达标项，不降低指标或用规划代替交付。

## 2. 知识维度与组合架构

任务可组合以下维度；不为维度组合预生成笛卡尔积文件：

1. **任务模式/工作流**：片段、单文件、长单文件；决定转换与审阅流程，不是语言知识。
2. **语言方向**：源语言 → 目标语言，例如 C → C++。
3. **实际语义场景**：源码确有的网络 I/O、文件、进程、凭证接口等行为；可多选，以行为证据为准。
4. **系统方向**：源 OS → 目标 OS，例如 Linux → Windows；同平台与跨平台必须区分。架构、ABI、编译器、运行时/API 版本是相关时的附加条件。
5. **ATT&CK Enterprise 战术**：完整分类/检索元数据；不代替代码行为判断，也不要求每个战术都有专属转换 Skill。
6. **可选知识检索**：未来 RAG 为已选知识补充带来源的候选片段，不凌驾于核心约束。

```text
用户指令与源码
  → 冻结任务契约（源码快照、任务模式、语言/系统方向、架构/工具链、禁止副作用）
  → 静态解读源码并形成画像/符号与行为地图
  → 依据源码证据标记语言、实际场景、source OS → target OS 与 ATT&CK（无证据则 none）
  → 按标签选择语言 + 场景 + 系统 + 工作流 Skill，并记录知识缺口
  → 长文件先完成依赖/资源/行为地图，再调度配置模型转换 → 结构化自审 → 有限模型自修/复审 → 静态核对 →（获批时）第三方编译/行为评估 → 按诊断有限 repair
  → 产出目标代码、result.md 与适用的 evaluator_manifest.json
  → 在审批后的隔离环境分别取得语法/行为证据；未审批时保持 UNVERIFIED
```

知识组合可以作为本次任务的 prompt 上下文供大模型使用，但不保存每种组合的永久合成 Skill。方向负责语言/API 映射，场景负责跨方向行为语义，系统规则负责平台差异，长文件工作流负责全文件一致性；规则冲突或无法映射时指出差异，不把“相似 API”直接称作等价。

## 3. 质量与试验口径

### 3.1 片段

语法正确率需说明检查上下文：完整函数/可独立片段可用目标编译器或解析器的语法检查；依赖外部声明的片段需以用户提供或中性声明桩补足。上下文不足时结果为“无法判定”，不能把不可独立编译的片段判成语法错误，也不能由语法通过推导功能正确。

### 3.2 单文件

记录语法/编译结果与场景级行为检查，分开报告通过、失败和不确定。功能检查依据应在转换前写成可观察行为约束，例如输入输出、协议字节/状态、文件结果、退出码或错误路径；代码相似度或模型自评不能单独充当功能正确 oracle。

**当前阶段的质量焦点**是最终交付版本的编译结果：在声明的目标标准、OS/架构、编译器/SDK、依赖及检查上下文下，编译成功作为本阶段“语法正确”的操作性判据。一次任务只按最终交付代码计结果；中间失败、修订次数及其后通过仅用于开发期定位 Skill 缺口，不作为产品质量指标。编译、链接和启动原因应分开记录；编译成功不证明可运行、功能或安全正确。当前暂不统计功能正确率，单文件的长期功能保持目标未取消，未观测部分明确写 `UNVERIFIED`。后续验证须按场景设计真实行为路径和可观察 oracle；受控样例的有限输入不代表完整攻击链或生产环境效果。当前阶段、纳入范围和退出条件见[项目开发规范第 3 节](项目开发规范.md#3-当前开发阶段与退出条件)。

### 3.3 长单文件

计划上限为 700 个 LF 归一化物理源代码行；未来若验证此上限，需用未通过填充降低密度的范围内真实源，预先记录 LOC、有效代码行与 token 数。除单文件指标外，检查函数/类型/符号覆盖、跨函数状态与接口、依赖及调用关系、跨段引用、遗漏/重复代码、合并结果和副作用。长文件 Skill 是减少语义漂移的过程性约束，不构成正确性保证。

### 3.4 一次性试验材料

开发试验可从实际源码、目标版本和第三方诊断中提炼可复用规则；原始材料在该次执行与验收期间可追溯，保留与清理由任务约定决定。一次试验的样本清单、历史 job 和回归位不进入产品 Skill 索引。RAG 尚未实现；如另立检索效果试验，须先冻结问题、样本和独立判据。

## 4. 当前真实能力

| 维度 | 当前状态 | 不得宣称 |
|---|---|---|
| 任务模式 | 根入口可区分片段/单文件；长文件工作流初稿已写、未经转换效果验证 | 片段语法率或单文件功能率已达标 |
| 语言方向 | 七语言共性事实由[项目知识导航](../skills/references/seven-language-common-semantics.md)与[7 份单语言参考页](../skills/references/languages/)维护；另有 42 个按源→目标归档的方向 Skill，各有静态规则文本；**这不是转换效果覆盖** | 42 个方向已编译/运行/功能等价，或编译通过等于功能正确 |
| 语义场景 | 网络 I/O、文件 I/O、并发、进程执行知识已写；注册表/服务属系统方向而非场景；场景功能整体未验收 | 已覆盖所有攻防场景或已验证完整攻击链行为 |
| 系统迁移 | POSIX ↔ Winsock、POSIX ↔ Windows 文件路径、进程创建与身份/权限、线程，以及 Windows 注册表与服务子系统知识已写，均需行为验证；PE 解析、Linux 内核接口与 macOS 专有子系统仍无 Skill | 跨 OS 功能已验收或 macOS 专有子系统已有等价知识 |
| 长文件 | 计划上限为 700 个物理源代码行；尚无范围内长例能力验收 | ≥600 LOC 等价转换或整体 700 行能力已达标 |
| 智能体接入 | Codex 仓库 Skill 有显式发现路由；其他平台未接入 | Codex 自动触发、其他 Agent 已验收或模型输出普遍可靠 |
| RAG | 尚未实现，当前无 RAG 试验任务 | 已有检索能力或 RAG 已提高准确率 |

冻结契约应包含源快照与哈希、源/目标 OS 和 runner、工具链、可观察义务、安全边界与待补齐项；目标配置与[Runner 能力矩阵](../references/adapter/controller/runner-capability-matrix.md)的部署记录分列，并在执行前复核实时状态。冻结**不等于**已编译、已通过或功能等价。测试输入须有实际源码；许可正文、版本号、上游 commit 和仓库 URL 不作转换冻结的硬阻断项，但对外分发另行核对来源。新增试验逐例核对安全、方向、场景与行为证据。

## 5. ATT&CK、知识来源与安全范围

ATT&CK Enterprise 完整分类是索引，不是覆盖承诺；名称和 ID 以 [MITRE 官方列表](https://attack.mitre.org/tactics/enterprise/) 为准。语言/平台/协议事实优先查标准、官方 API 文档与 RFC；GitHub 用于发现公开案例，知识规则需核对适用上下文，不把 README 或自动生成输出直接当作规范。

试验样例只进入经审阅、获准且与隔离环境匹配的范围。**安全可控不等于把攻防行为简化为空桩**：优先选有真实行为路径的源码，以假数据、受控目标和隔离观察保持其关键决策与错误路径。目录名或 ATT&CK 标签不能替代源码行为审阅。网络类行为使用 loopback stub/mock 或无外联 fixture；不连接真实目标、不使用真实凭证、不通过转换新增攻击能力。动态行为试验若需扩大网络/进程副作用，须另行确定授权和隔离条件。细节以[安全边界](../references/framework/safety-boundary.md)为准。

## 6. 非目标与启用条件

当前仍不建设独立转换服务或本地构建/评测运行时；闭环由 Markdown Skill 规定确定性门槛、由获批第三方返回权威证据。**已授权单文件转换的标准执行形态为双侧执行**：comparison capsule 在获批隔离 VM 构建并运行源、目标两侧，本阶段只取其 **build 证据**用于当前编译指标，execution/comparison 结果不计入功能率、不将有限行为匹配外推；源无可运行入口时按契约补写最小中性入口/驱动。已确认的运行授权无需逐次询问；到评估步骤逐例核对工具链、真实入口、网络/数据隔离及服务状态后直接提交，不能把旧 READY 记录当作当前隔离证明。编译结论在 Controller 回传 build 证据前记 `UNVERIFIED`，实际基础设施/环境故障凭诊断归因并在恢复后重提，不改用本机编译。当前不建设完整 RAG 平台、通用 Registry、固定输出 Schema、hash/升级系统或完整评测平台。最小实验能够回答问题时优先用智能体原生能力和静态文档；出现真实瓶颈后再加薄代码。业务阶段与交付顺序见[项目开发规范](项目开发规范.md)第 3 节。
