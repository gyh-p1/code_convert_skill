# 统一测试与后续评测协议

本文件定义测试预期，未执行任何转换或评测。每个主用例包含正常与异常两个必测情景；每例 README 另外列出边界扩展输入。八类各一例指八个源程序，不表示每个程序只运行一次。

## 需求与观察映射

| 需求 | 必查材料／信号 | 判定边界 |
|---|---|---|
| 八类战术 | 各源的 TACTIC／TACTIC_ID、业务状态机及 README | 标签描述仿真主题，不是准入结论 |
| 逻辑行为等价 | 同一 stdin／argv 的两侧完整 JSON、退出码、stderr、受控副作用 | 核心断言通过仍不足以证明完整程序等价 |
| 原始命名 | 模块文件基名、关键类／函数／字段、战术词汇与映射表 | 目标语法不允许的标识符必须给出具体理由和一一映射 |
| 模块划分 | 输入验证、领域模型、操作分派、报告／入口四层 | 单文件源码保留逻辑模块，不伪称覆盖多文件包迁移 |
| 编译／语法 | 精确目标版本的真实工具输出与退出码 | 不从静态审阅或平台总 verdict 推断 |
| 直接启动 | 编译产物或解释器入口可接收 stdin 并在 EOF 后结束 | 不依赖人工替换 TODO、未交付模块或动态下载 |
| 非直接概念映射 | 每例 E 情景＋源定位＋目标实现＋差异说明 | 替代实现不能吞错、漏清理或改回滚范围 |
| 初始访问分流 | routing-cases.json 中分支预期＋实际分类原件 | 受控注入只能验路由，不能证明检测准确率 |
| 等价性通过／不通过 | 原比较报告、最终目标版本、修订来源及停止原因 | 编译失败、装置无效不能伪装为功能不等价 |

## 数据与比较规则

1. UTF-8 输入，原始字节不带 BOM。每次独立启动消费一个文件，必须传完 stdin 并关闭输入；不把文件路径作为业务 argv。所有命令不需要应用参数。
2. stdout 应恰含一个 JSON 文档及末尾 LF。以解析后的完整对象比较，忽略对象键序和 JSON 的等价字符转义。数组顺序、null／空数组／空对象、数值类型、字节十六进制、计数器、错误 code／field、审计顺序不得忽略。
3. `expected.json` 中每个键是从输出根开始的 JSON Pointer；应存在并等于所列值。该文件不是平台原生 oracle，不假设平台可直接导入此结构；由获批平台现有工具消费，或人工比对真实输出。不得临时生成辅助评测驱动。
4. 核心输入全部为合法 JSON且无重复键。追加边界输入时保留各源的实际解析语义：Python 和 C# 样本拒绝重复键，Go／Ruby 的默认解析保留最后一个同名键，PowerShell 采用被冻结版本的 `ConvertFrom-Json` 行为。不能跨样本强行统一输入语义；无独立证据的解析器边界记 UNVERIFIED。
5. 同一输入在两侧使用同样虚拟时间、限额、排序、哈希和失败注入点。真实机器名、时钟、随机数和网络均不参与样本逻辑。正常成功输出不含宿主路径，不存在必要的环境消噪项。
6. 发生预期操作异常后仍比较最终状态；特别区分 01 的事务回滚、02 的身份恢复但已完成写入保留、06 的可选原子回滚、08 的已确认包保留。
7. 03 的压缩字节若因依赖版本不同产生差异，应先尝试对齐依赖；若未来计划使用语义比较，须在冻结前明确压缩格式、解码等价和哪些输出允许不同，不能看到失败后临时忽略散列。核心输入不使用压缩。
8. 资源指标只是业务模型的虚拟计数器。其归零不证明实际操作系统资源、物理内存清除或网络隔离。实际隔离和清理由外部环境证据核验。

## 正常／异常执行计划

每项先按仓库契约完成可达性检查、冻结和分类 ALLOWED，再进入适用源构建／基线。输入、源码、工具链、依赖、系统镜像、比较范围必须关联精确版本。此时才生成目标及自审；本轮没有提前执行这些阶段。

未来行为评估由已授权平台的现有驱动完成：启动指定入口，提供并关闭 stdin，等待该有限程序输出及结束，采集 stdout／stderr／退出码／允许目录变化，最后终止残留进程并收尾。建议单次 10 秒、内存 256 MiB；最终限额由平台冻结，并确认语言启动开销适用。超时保留真实诊断，不直接归因语言转换。

本数据集不读写业务文件。构建／解释器缓存只能存在获批的临时目录；清理时只处置平台声明的临时资源。无网络需求，应在两侧禁用外联。

## 原始命名和模块检查

保留 `*_lab` 文件基名，只改变语言扩展名。C# 的命名空间、Go 的 `package main` 以及目标工程入口按合法语言规则映射。源的四层职责必须有可定位目标符号，禁止把整个程序压成无法追踪的单个函数。

各例 README 列出关键符号。逐个填写以下报告字段，不用一句“已保留命名”代替核验：

| 源文件／符号 | 目标文件／符号 | 是否原名 | 必要改名依据 | 模块职责与调用对应 |
|---|---|---|---|---|
| 待转换后填写 | 待生成 | UNVERIFIED | 待核 | 待核 |

例如 Ruby `terminal?` 在 C 中不可作为函数名，可映射 `Task_terminal_p`；PowerShell `Get-Chunk` 在 Go 中不可包含减号，可映射 `Get_Chunk`。保留可合法保留的语义词根并记录理由，不能将这种必要映射报告为逐字符原名保留。

## 非直接对等概念报告要求

每例至少报告一个具体映射：源符号及使用点、目标语言缺失的直接语法／API、替代算法、资源／状态时序、允许的实现差异、禁止的行为差异、N/E 两个情景的实际观察指针。异常测试应同时检查错误传播与后续恢复能力。

02 的 Python `contextmanager` 和 C# `using` 都能管理作用域，但语法、生成器协议和异常传播不是逐字替换；04 的 Ruby Enumerator 也不能直接视作 Python 可关闭生成器；08 的 Go slice 不会发生 PowerShell 管道的隐式解包。报告须解释这些具体差异，不能笼统写“两种语言不兼容”。

## 分类及等价性分支

八个主样本的业务期望均走“非初始访问／通用代码”分支；源文本中的 TACTIC 常量仅是样本描述，真实路由仍取正式分类结果。不能看到字符串 `TA0001` 就宣称检测到初始访问。

`routing-cases.json` 将用户期望描述为“初始访问专用生成策略”和“通用生成策略”。这只是验收名称，**没有假定仓库已经存在两个实现或对应平台字段**。正式系统应将测试名映射至其真实策略标识；缺实现时报告需求缺口。

等价性通过：保留被验证的那个目标版本和原件，生成交付报告；不为凑流程重新生成未验证目标。不通过：先辨明差异来源，只有定位到转换引入问题才按仓库有限修订预算修复；保留原失败目标、输入／输出、父版本及复测原件。预算耗尽时交付已有目标并清楚标记失败／未验证，不冒充可直接使用的等价目标。

观察无效、源问题、环境失败、比较器故障单列，不能将它们当成功能 `mismatched` 来要求模型修改业务逻辑。若未获得功能证据，记 `UNVERIFIED`。本轮不选择一个虚构的“通过／不通过”终态。

## 报告字段

后续每项报告至少分别记录：交付完整性、源／目标语法或构建、链接、启动、正常情景、异常情景、功能比较有效性、命名映射、模块映射、战术词汇、替代实现、系统差异、安全／清理及精确版本证据。没有证据的维度记 UNVERIFIED；仅编译分支不能宣布功能等价。
