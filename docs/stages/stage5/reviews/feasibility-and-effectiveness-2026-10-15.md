# 载入核对方案：可行性与有效性评估

> 日期：2026-10-15
> 评估性质：当前仓库文本静态审阅；未实现或运行拟议检查器，未观察真实 Agent 转换任务。
> 原评估结论：收窄到 7 份必读契约与适用工作流后，文本预检可实现；实际载入不能由仓库扫描独立证明。
> 后续决策：用户已允许系统登记脚本并采用三职责设计，第三方仍禁辅助脚本。下文保留设计评估背景；后续实现与实际接入验收见 §6，不将早期状态当作当前状态。

## 1. 核对到的当前事实

- 根 [SKILL.md](../../../../SKILL.md#必经执行链与契约)已有 7 项必读真源表，步骤 1 要求先读必读契约；[发现入口](../../../../.agents/skills/code-convert/SKILL.md)指向根入口，并未维护另一张逐项清单。因此以根表为唯一清单可行，三表逐字一致检查没有现有对象。
- [批量工作流](../../../../skills/workflows/batch-conversion/SKILL.md)按多项请求触发并要求首项前加载；[长单文件工作流](../../../../skills/workflows/long-file-conversion/SKILL.md)在地图/分段前加载。是否适用依赖任务事实，纯仓库扫描无法定案。
- [任务状态 §2.2](../../../../references/framework/task-state-contract.md#22-冻结落盘门禁)已要求 `frozen-inputs.md` 分类前落盘、回读；§2.3 将“可达”“Agent 已读”“模型已注入”“效果已验证”分开，但现有必读契约尚无统一逐项读取凭证字段。[交付 §1.1](../../../../references/framework/delivery-handoff-contract.md#11-统一收尾入口与报告义务)覆盖提前停止和 WAITING。
- 原审阅时 [AGENTS.md §1](../../../../AGENTS.md#1-系统脚本与逐项调度边界)及[安全边界 §1](../../../../references/framework/safety-boundary.md#1-本机不执行最硬红线)明定分类器为唯一许可常驻脚本；现已按 §5 的用户澄清修订系统/第三方角色，旧限制不作为系统维护授权仍缺失的依据。
- 工作树已有未提交改动，单独记录仓库 commit 不能确定检查时读取的实际正文；计划中的摘要必须对应文件字节和检查原件。

## 2. 可行性判定

| 能力 | 判定 | 依据与限制 |
|---|---|---|
| 检查根表 7 项、入口路由和限定路径/锚点 | 技术上可行 | 断言 7 个精确文件身份，才能检出同数误换；根表结构变化必须明确失败，不能静默漏项。合法变更真源时需审阅断言；复杂 Markdown 解析先用 fixture 验证。 |
| 判断批量/长文件是否适用 | 需 Agent 按任务事实决定 | 静态工具只能检查两份工作流可读及触发规则存在，不能从仓库文本推出某次任务形态。 |
| 确认某次 Agent 实际完整读取 | 仅可审计，不能独立证明 | 逐项记录路径、摘要、覆盖范围和原生读取依据可查缺项；自填记录可能错误，且读取不保证理解或上下文持续保留。 |
| 分类前阻断缺项 | 文本流程可行，尚未接入 | 需在冻结契约中定义 `FAIL`、`UNAVAILABLE`、人工等效核对及历史 job 例外；不是 Controller 的技术拦截。 |
| 维护检查器运行 | 需先修改执行约束 | 当前唯一常驻脚本规则与新设施冲突；未修订前不能写出、运行或称其已被准入。 |

## 3. 载入检查的有效性边界

有效的成功信号应分别报告：**静态结构 PASS**（清单与限定路由完整、路径/锚点有效、关键顺序无已知冲突）和**本项读取记录 COMPLETE**（7 份及触发工作流对应当前正文、有完整读取范围、可回读）。只有两者在同一文本版本上成立，才支持 Agent 按拟议门禁记 `FROZEN`。这仍不等于“全面理解”或“门禁由平台强制执行”。

静态检查最大的漏报是正文语义换词后仍自相矛盾；最大的误报是把历史反例、代码区或非必读参考页当作现行命令。因此不把 `skills/**` 与 `references/**` 全部设为直链检查对象，也不使用全库废弃词黑名单。规则变更仍须按 [AGENTS.md §10](../../../../AGENTS.md#10-加载路径与规则一致性) 人工核加载路径及语义一致性。静态工具减少可机械复核的部分，不能取代人工回查。

批次共享读取记录可以减少重复，但跨 Agent、跨会话、上下文丢失或正文变动时不能继续宣称已加载。缺原生读取依据时标记未证实并重读；历史记录不能事后由现行正文补齐。

## 4. 最小验证与停止条件

先用同一组隔离文本 fixture 做单变量对照：基线完整时预检通过；只删除根表一个必读链接时必须失败，恢复后通过。随后分别只改变一个条件：以存在的其他文件替换一项并保持 7 行、损坏适用工作流锚点、截断一份必读契约的实际读取记录、把历史反例词放进引述。预期是替换/坏锚点/截断阻断对应层，历史引述不产生阻断。记录每次输入字节、原始输出、退出码及人工预期；出现漏报或误报就修解析和判据，不扩大扫描范围掩盖问题。

再用四个无样本执行的纸面任务核适用集合：单项、批量、长文件、批量且长文件。人工回退与工具预检应对相同仓库文本得出同一阻断/通过结论。最后抽样检查真实 Agent 会话的原生读取与冻结记录是否对应；此步骤未做前只可宣称方案和 fixture 层有效，不能宣称使用者遵守率。

若根表无法解析、工作流触发依据不清、读取凭证缺正文覆盖、检查结果版本与冻结版本不符，停止新增分类并走既有收尾/暂停路径；已发生 job 的查询取证与清理不因此停止。未进行转换效果、模型注入、编译/行为、安全隔离或平台拦截验证。

## 5. 用户采用三职责设计后的增量评估

2026-10-15，用户采用一个小工具承担“检查仓库结构、记录正文提供情况、核对下一动作前置条件”，并进一步明确仅转换系统本身允许执行已登记脚本。第三方智能体加载 Skill 后仍不得使用辅助脚本，必须通过原生工具手工逐项调度；系统提供原件时读取/核对/引用，无系统支持时保留人工核对及证据限制。[实施方案](../plans/required-loading-integrity.md)与产品入口据此修订，系统维护授权不再重复申请。

相较原方案，改进在于由真实工具返回记录正文范围与版本，并在既有动作发生前核对，减少自填凭证和冻结时补读造成的错误。允许直接将不可覆盖的原件保存到约定证据目录，冻结和阶段记录引用它们，不另建任务状态机。

可行性仍分层：结构解析、哈希和分段覆盖在工程上可实现；独立提供证据依赖宿主实际暴露的工具返回、截断与会话事件，必须先做最小接入实验。后台读完、自填调用标识或已生成正文包均不证明 Agent 收到；未知字段不能合成。提供过正文也不证明理解、当前上下文保有、模型注入或转换效果。

下一动作核对覆盖既有契约加载时点，不只在冻结前查文件是否齐备；补读不能追认历史时序合规。正文快照变化、跨会话和已知上下文恢复均需重新核依据。首版仍只覆盖 7 份契约及两个适用工作流，其他知识与渠道加载义务不变，不报告全面加载完整。

更新后的验收矩阵见方案 §6，新增中段遗漏、最终返回截断、版本混用、迟读、会话复用、证据降级及原件写入失败。当前仅完成设计文本核对，未实现脚本、未取得宿主接入证据、未执行这些验收实验，不能声称它们已经通过。
