# 必读契约与适用工作流载入核对方案

> 状态：待实现方案，依据用户 2026-10-15 的范围确认
> 范围：仓库 Markdown 的静态一致性、逐项实际读取凭证及冻结前核对；本页不改变现行转换门禁或脚本禁令。

## 1. 目标与边界

问题是：当前[根入口必读表](../../../../SKILL.md#必经执行链与契约)规定了 7 份真源和消费时点，[根步骤 1](../../../../SKILL.md#按以下顺序执行)要求先读全部必读规则，但任务记录尚不能统一说明本项实际读了哪些契约、哪一版正文，以及适用工作流是否读到。

目标分两层：维护侧可重复检查必读清单、入口路由、适用工作流的本地路径/锚点及有限门禁摘要；执行侧在分类前留下本项实际读取的可复核记录。前者只能证明仓库文本的结构状态，后者是 Agent 读取动作的审计痕迹；两者都不能独立证明理解、上下文持续保留、模型注入、转换效果或平台强制拦截。

检查器不审查 42 个方向、语言页、场景/系统 Skill、共享知识参考及其回链，也不取消它们按源码触发的原有加载义务。不要求每个 Markdown 页面都直接链接根入口和安全边界，不把开发期 `docs/stages/` 加入产品必读链。Controller 适配等渠道材料仍按根步骤 1 的既有条件读取，本版不宣称对其载入完整性提供检查。

## 2. 唯一清单与适用集合

7 份必读契约以根 `SKILL.md` 的“必读真源”表为唯一供 Agent 消费的清单：任务状态、分类准入、构建前提、单项闭环、评估准备、交付、安全边界。发现入口和 `AGENTS.md` 只需可靠地导向根入口并保留不冲突的门禁摘要，不增建第二、第三张 7 项表。检查器须断言这 7 个精确文件身份与数量，避免同数替换漏报；这些断言是对根表的验收约束，不是另一份供 Agent 加载的清单。合法更换真源须同步审阅断言及其测试。若无法解析根表，应报“清单形制未知”，不能退回旧清单并报告通过。

适用工作流只包括：请求含多项时，在处理首项前读 `skills/workflows/batch-conversion/SKILL.md`；长或复杂单文件在建立地图/分段前读 `skills/workflows/long-file-conversion/SKILL.md`。两者可同时适用。是否触发由本项或本批真实任务形态决定，不能由静态仓库检查器猜测；冻结记录写触发依据或不适用理由。单项闭环已列入 7 份必读项，不重复计为第三个条件工作流。

## 3. 两层核对

| 层 | 输入与检查 | 产出与界限 |
|---|---|---|
| 仓库静态预检 | 只读发现入口、`AGENTS.md`、根入口、7 个目标文件与两个条件工作流。解析根表并核 7 个精确身份、文件存在、本范围内引用的锚点、根步骤 1 的加载时点、发现入口到根入口的路由、批量/长文件触发描述及必要门禁节点顺序。相对链接先排除围栏和行内代码；无法可靠解析时明确报错。 | 逐项 finding、被读文件的路径与内容摘要、检查器版本和 `PASS`/`FAIL`/`UNAVAILABLE`。只表示限定范围内的文本检查，不表示 Agent 已读。 |
| 单项载入核对 | 在本 run 的 `01-frozen/frozen-inputs.md` 中记录 7 份契约与本项适用工作流的实际读取范围、精确文件版本/内容摘要、读取时点、未截断依据；条件工作流记录触发事实或不适用理由。引用静态预检的原件路径及摘要。 | Agent 的可审计读取声明。路径/标题/勾选、单独的 Git commit 或预检 `PASS` 均不能代替实际读取记录；该声明也不是独立的理解证明。 |

必读文件应通过原生读取工具取得完整正文；分段读取须记录覆盖范围，避免截断输出被写作“已读全文”。进入新 Agent、新会话或上下文无法继续保有已读正文时，重新读取并更新本项记录。同一连续上下文内、文件字节不变且可回读前次读取依据时，批次后续项可引用批次开始的共同读取记录；每项仍在自己的冻结记录中确认适用集合和版本。仓库正文改变后，重新静态预检并重读受影响的文件，旧凭证保留，不拿当前正文补称历史已读。

静态预检原件若按批次共享，放在批次索引的批次级记录位置；单项记录仅引用路径与摘要，不在批次根另设逐项状态。单项任务可在本 run 的 `01-frozen/` 保存该次原件。原件用递增或不可变身份保存，重跑不覆盖旧版。内容摘要对应实际工作树文件字节；当前仓库有未提交改动，`HEAD` 只能辅助定位，不能单独标识检查所见正文。

## 4. 冻结前判据与失败去向

本方案拟在[任务状态 §2.2](../../../../references/framework/task-state-contract.md#22-冻结落盘门禁)的既有人工回读中增加载入核对，不增加 Controller 字段。分类前同时满足：静态预检在对应文本版本上 `PASS`，或有相同范围的逐项人工静态核对及依据；本项 7 份契约与适用工作流读取记录完整；`frozen-inputs.md` 已落盘、回读且身份/源集合/其余适用字段合格。缺一则不记 `FROZEN`、不新增分类或后续动作，按[交付 §1.1](../../../../references/framework/delivery-handoff-contract.md#11-统一收尾入口与报告义务)记录停止/暂停与恢复条件。

`FAIL`、解析错误、输入不可读不能记为通过。无命令能力时可用原生工具逐项执行同范围人工核对并保存路径/锚点、版本和结果；未完成则记 `UNAVAILABLE`，不得以“已填模板”放行。检查器 finding 须区分必读路由/文件/锚点/顺序的阻断问题与历史引述等提示问题；提示不改变既有转换安全门禁。已发生 job 的查询、取证、终止/清理仍按任务状态 §2.2 的例外继续，不能因载入凭证缺失而放任未决执行。

这是一道 Agent 文本执行门禁，不是宿主 hook、分类器或 Controller 服务端拦截。记录可以证明某次审查留下了什么材料；没有独立读取日志时，不能据自填凭证断言任意 Agent 一定读过。

## 5. 拟议检查器的最小形状

维护侧可拟议 `tools/loading_preflight.py` 与其隔离文本 fixture 回归，但**当前仓库仍只允许安全分类器作为常驻脚本**。实施检查器前须将用户已确认的设施与逐项调度脚本边界同步到 `AGENTS.md`、根入口、安全边界、任务状态、交付契约及开发规范；仅保存本 Stage 5 方案不构成现行规则已修改。检查器只读指定仓库 Markdown，不读样本源码、不执行构建/转换/请求、不直接写 run 产物；由 Agent 手工调度单次预检，不成为流程编排器。

计划接口为 `--repo`、`--brief`、`--json <path>`；退出码 `0` 为限定检查全部通过，`1` 为阻断 finding，`2` 为用法、读取或解析失败。JSON 先写到获准的临时文本位置，由 Agent 核对后手工保存到本项或批次记录位置；检查器本身不写 run 产物。JSON 保留检查项、严重度、文件字节摘要和原始诊断；简报不宣称实际载入。仓库文本变动后重跑；同一文本版本的批次可引用一次原件。不得用宽泛的“废弃词黑名单”扫描历史反例，也不以三个入口各有相同清单为验收条件。门禁长链只检查限定的关键节点及顺序，语义矛盾仍按 `AGENTS.md` §10 人工回查。

## 6. 实施与验收顺序

1. 先将已确认的维护设施边界写入执行真源，明确检查器调用位置、人工回退、阻断/提示分层和不新增执行授权；按实际加载路径回查根入口、发现入口、批量与长文件工作流及适用契约。旧文档中的“唯一常驻脚本”须同步修订，不能留互相矛盾的操作指令。
2. 实现限定范围的只读检查器及文本 fixture 回归。先固定当前工作树的文件版本，保留首轮原始发现；不要以当前 `HEAD` 或预期“9 页缺链”当作结果。
3. 在真实转换前的纸面单项、批量、长文件及两者叠加四种形态中核适用集合和冻结记录形制；分别注入一个缺项、一个坏锚点、一次读取截断，确认对应阻断且修复后恢复。人工回退按相同验收用例检查。
4. 只在文本验收通过后，按交付契约回查所有停止路径、历史 job 例外、批次共享原件与逐项版本指针。再考虑真实 Agent 会话抽样；任何文本通过都不声明转换、编译、行为、隔离或平台拦截已验证。

本阶段若仅完成方案文档，实施与验证状态保持 `NOT_IMPLEMENTED` / `UNVERIFIED`。
