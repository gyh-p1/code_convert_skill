# 阶段 04：RAG 配对对照

> 状态：待启动（有条件批准的探索性比较）  
> 前置：阶段 03 基线完整、四例和评分表冻结；无 RAG 闭环的自审/repair/第三方分流已先跑通

## 是否值得引入的前置判断

RAG 不应作为当前默认开关。只有在无 RAG 流程已经稳定、且失败样本显示为“缺少或检索错误的平台事实/标准依据”而不是模型上下文、工具链或 oracle 缺陷时，才进入本阶段。RAG 的目标是补充可核验知识，不是替代结构化自审、第三方编译或行为评估。

至少满足以下门槛才做 RAG 配对：

- 无 RAG 的同条件基线已冻结，包含模型返回完整性、预检发现、第三方 build/行为证据和 repair 次数；
- 为每个 RAG 条目固定来源、版本、平台/标准适用范围和失效日期；
- 每条检索片段可追溯到官方 API/标准/RFC 或已审阅内部知识，不直接把旧仓库生成代码当权威；
- RAG 注入不会携带其他 run 的目标代码，避免样例泄漏；
- 只把“是否检索/注入”作为变量，不同时改变提示、Skill、模型、工具链或 oracle。

## 实验变量

RAG 组在相同基础提示和 Skill 上增加经过审阅、带来源的检索片段；控制组不检索。两组固定样例、模型标识、参数、核心提示、Skill 内容、目标 OS/架构、工具条件及行为 oracle，**只改变是否检索/注入知识**。如更新知识内容或提示，应另起实验版本，不能与 RAG 效果混为一谈。

## 分层记录

- **检索层**：每例相关依据的 Recall@k/Precision@k（若有人工标注），来源和版本是否匹配、误引/过期内容、注入 token；
- **转换层**：语法/编译、逐项行为 oracle、长文件结构完整性；按相同口径对照无 RAG 基线；
- **成本层**：检索延迟、额外 token、总耗时/成本；
- **稳定性**：若重复运行，次数与参数两组一致，展示逐次结果和方差，不挑最好结果。

## 结论规则

RAG 只有在不降低编译/行为结果、不引入来源错误或样例泄漏，并且额外 token/延迟可接受时才值得默认采用；仅提高检索命中率、减少模型疑问或让报告更长，不足以证明转换质量改善。

四例仅是试点，结论限定于这四例和当前知识范围。报告每例改善、退化和无变化；区分“检索命中改善”和“输出行为改善”。若检索指标提高但转换结果无提升，不能据此宣称 RAG 提高转换准确率。明显错误来源、质量退化或安全问题应阻止采用；结果不确定时先改进知识/问题集，再作决定。

本阶段不要求上线 RAG、不绑定向量数据库/供应商，也不构建完整检索服务。试验执行遵守 `docs/安全边界.md`。
