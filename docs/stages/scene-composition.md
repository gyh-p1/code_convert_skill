# 语言方向 × 语义场景 × 系统方向

> 状态：三维组合原则已确认；系统方向仅有套接字层 POSIX ↔ Winsock 初稿，未经验证  
> 更新：2026-09-25

## 最小组合

智能体依据请求与源码，按需阅读**一个已存在的语言方向 Skill + 零个或多个实际相关的语义场景 Skill + 匹配的源 OS → 目标 OS 规则**。目前有 C → C++ 与网络 I/O 场景初稿，系统方向仅有套接字层 [POSIX ↔ Winsock](../../skills/systems/posix-winsock/SKILL.md) 初稿（未验证），文件/进程等其余系统方向仍无 Skill；已有长文件工作流初稿，尚未验证。片段/单文件质量边界见 [业务文档](../项目业务文档和能力边界.md)。源/目标 OS、架构、编译器、运行时不明且会影响决策时先询问或明确未决假设，不把目标平台标签当作系统迁移已解决。

例如 `C/Linux → C++/Windows + 网络 I/O` 同时触及三个维度：现有语言、网络场景与套接字系统方向可组合覆盖套接字层，但套接字之外的 Linux → Windows 系统迁移（文件路径、进程、线程等）仍无知识，不能被默认 Linux 或 Windows 提示替代。缺失的映射要暴露出来，不默默把路径、权限、进程、服务或系统 API 改成”看起来相近”的功能。

组合是本次任务的阅读上下文，不预生成语言 × 场景 × 系统 × 战术的文件笛卡尔积，也不建设选择器或输出校验器。冲突时先守住安全边界和源代码实际行为；方向、场景、系统分别说明自己的适用范围，不让示例压过已知约束。

## 战术是完整分类维度，不是固定十份规则

ATT&CK Enterprise 的全部当前战术用于分类、检索与风险提示；名称和 ID 以 [MITRE 官方列表](https://attack.mitre.org/tactics/enterprise/) 为准，当前范围快照见 [业务与能力边界](../项目业务文档和能力边界.md)。同一场景可关联多个战术，同一战术也可能跨多个语义场景和系统。只有某战术确有独特、可解释的转换约束时，才按需增加独立知识，而不是为每个战术预建空 Skill。

不能从 ATT&CK 标签直接推断具体 API、目标系统或已有转换能力；旧库的 9 个战术文件和旧采购材料中的”10 类”仅为历史范围，不是当前分类真源。

需要按战术检索现有知识时，用 [战术检索索引](../../skills/attack-tactic-index/SKILL.md)：它把 15 个 Enterprise 战术映射到已有语言/场景/系统知识并标出缺口，是索引入口，不为每个战术建独立转换 Skill，也不改变”按实际行为判断场景”的规则。

## 来源与未来 RAG

语言/平台语义以标准、官方 API 文档、协议规范为主；ATT&CK 用于行为分类，不代替 API 依据。GitHub 是带来源、版本与许可的边界案例发现渠道，不将示例或自动生成规则直接升级为权威。旧库候选见 [审阅记录](legacy-knowledge-review.md)。

未来若另立检索试验，条目至少保留源/目标语言、源/目标 OS、架构或 API 条件、场景、ATT&CK ID、出处及适用版本。RAG 命中只能表示找到了资料，不能代替转换结果的编译和行为证据；原固定四例配对方案已[取消](four-case-cancellation.md)，当前没有 RAG 测试任务。
