## 2. 一致性问题与暂行处置

### P1：分类器独立产出，工作流与提交端没有消费者

分类器能够产出阻断结果，不代表平台会拒收对应任务。新增[分类结果准入](../../../../references/workflow/classifier-agent-gate.md)，让本工作流的调用者按当前分类结果决定是否提交；身份/哈希不匹配或分类缺失时先修正引用或重新分类。平台层的不可绕过拒收与正式负向验收留给 T01-d。

**同日晚修订**：用户裁定分类 `ALLOWED` 即准入通过、允许运行，不由 Agent 再作主观判断。原六条人工判断与 `agentGateDecision` 已收敛为两类机械核对（提交内容与分类输入的身份/哈希一致、独立授权/隔离记录齐备），全部满足即提交，不再产出第二决策值。

### P1：Spec05 解除公网阻断的伪代码可能漏掉凭证阻断

[分类器规则2](../../../../tools/safety_classifier_v2.py)先返回 `public_network_unverified`，但 `details.files[].credentialFindings` 仍保留同时命中的凭证线索。Spec05 §3.3 在授权 configured=true 时会跳过公网分支；旧 blockingReason 又不是 real_credential_suspected，最终可能落入 `allowed(task)`。

本次合成 both 项实际产生了上述输出形态：主阻断为公网，credentialFindingCount=1。分类准入规则禁止直接解除旧 BLOCKED；隔离条件变化必须重分类并复核全部阻断/凭证线索。Spec05 伪代码尚未改成平台实现，不能按它直接放行缓存结果。

### P2：输出枚举和同名字段需要区分

分类器状态是 ALLOWED/BLOCKED；Spec05 AllowedTask 却写 APPROVED，且兜底 `else: allowed` 没有拒绝未知状态/原因。后续平台实现须统一准入枚举并默认拒绝无效结果。

分类 JSON 的 executionApproved 表示分类 ALLOWED；交付 manifest 的同名字段按[交付契约](../../../../references/framework/delivery-handoff-contract.md)表示 Controller 接收并取得 jobId。分类准入规则明确禁止复制这两个字段，不虚构平台接收证据。

### P2：平台健康与授权/隔离存在不同验收边界

Spec05 原“当前三 runner 契约不匹配”的限制已过时，本次同步为 1.0.26 契约一致的事实。该修正没有补齐批次授权或网络隔离证明；分类 `ALLOWED` 只表示允许运行，引用完整性核对仍须确认实际边界，不能仅凭 READY、私网地址或 CLI 开关冒充隔离证据。
