# 平台提交端准入闭环接入（Spec05 / T01-d）

> 日期：2026-10-10（北京时间）
> 范围：平台仓库 `third-party-evaluation-system`（evaluation-core + remote-controller 契约/服务/端点）与 code_convert 的 Spec05/清单文档。
> 用户裁定：今晚将**重新部署最新版 Controller 与 VM Agent**，因此做**最完整**接入——服务端硬门禁、不可绕过。
> 结论：平台提交端准入消费器已落地并接成 `POST /api/jobs` 硬门禁；Spec05 §3.3 的凭证漏判与未知态默认放行缺陷已修正；三套件 **497 passed**。真实样本提交与部署验收仍在隔离环境。

## 1. 为什么做这次接入

[上一轮一致性审查](分类器一致性审查与Agent暂行接入-2026-10-09.md)确认：分类器已被 **Agent 工作流**消费（根入口、批量、提交适配），但**平台侧无消费器**——`POST /api/jobs` 直收 capsule，`prepare_submission()` 只在 Spec05 以伪代码存在，任何直连 API 的客户端都能绕过准入。且 Spec05 §3.3 伪代码本身有缺陷。

## 2. 落地内容

### 2.1 准入消费器（evaluation-core）

新增 `packages/evaluation-core/evaluation_core/submission_admission.py`：
- 数据模型 `Task/Batch/Classification/AllowedTask/BlockedTask/SubmissionPlan`。
- `parse_classification()`：解析分类器输出行，缺字段/类型错→默认拒绝（不抛）。
- `validate_batch_authorization()`：按 Spec05 §2.2 逐字段 + 时间 + batchId + 契约哈希校验；任一不成立整批拒绝。
- `admit_task()` / `prepare_submission()` / `admit_single()`。

### 2.2 判定逻辑（二元 3 规则 + 完整性，与分类器 v2.4 一致）

参照用户确认的准则——**二元 ALLOWED/BLOCKED，只有 3 条分类阻断**（`input_error`、`public_network_unverified`、`real_credential_suspected`），理念是"证明危险才阻断"、安全由 VM 隔离兜底：

1. 批次授权整体无效 → 全批 `batch_authorization_invalid`。
2. 缺分类 → `missing_classification`。
3. 身份/哈希不符（taskId/direction/caseId 或源文件 sha256 与提交 capsule 不一致）→ `identity_mismatch`。
4. 分类器 SHA 不在许可集合（默认钉 v2.4 `009a6f31…f3a4`）→ `untrusted_classifier`。
5. `admissionStatus!=ALLOWED` 或 `blockingReason!=null` → 原因取分类器的 `blockingReason`，缺失记 `unknown_status`（**默认拒绝未知态**）。
6. 带**公网/hostname** 网络目标的 ALLOWED 项，批次授权须 `networkIsolation.configured=true`，否则 `public_network_unverified`；**private/loopback 不设此门**（敏感/副作用/私网默认 ALLOWED）。
7. 任一 `credentialFindings` 非空 → `real_credential_suspected`（纵深防御，即便状态被误置 ALLOWED）。
8. 否则 → `APPROVED`。

> 第 3、4 项是**提交完整性/真实性**核对（不是风险分级），用于保证"提交的正是被分类的那份、且出自许可分类器"，这正是硬门禁不可绕过的基础；与二元理念不冲突。

### 2.3 修正 Spec05 §3.3 缺陷

旧伪代码在 `configured=true` 时跳过规则2，使"公网阻断 + 同时命中凭证线索"的项落入 `else: allowed`，漏掉凭证；`else` 也不拒绝未知态。本实现：**平台不 lift 任何 BLOCKED**（公网解除只能靠重新分类产出新 ALLOWED，Spec05 §3.4）、**凭证纵深**、**未知态默认拒绝**。回归锁定：`test_bypass_blocked_public_with_configured_isolation_is_still_blocked`、`test_allowed_status_with_credential_findings_is_blocked`、`test_unknown_admission_status_defaults_to_blocked`。

### 2.4 服务端硬门禁（remote-controller）

- `app/api/jobs.py`：`POST /api/jobs` 增 `classification` 与 `batchAuthorization` 两个**必需**表单字段（JSON）；JSON 非法→400，缺字段→422，未准入→**403**（body 含 `blockingReason/reason/action`）。
- `app/services/job_service.py`：`submit_comparison_capsule` 增 `classification`/`batch_auth` 参数；`validate_comparison_identity` 之后、staging 之前经 `_enforce_admission_gate` 调用 `admit_single()`；阻断即清理 `job_dir` 并抛 `AdmissionBlockedError`。源文件哈希由 capsule 的 `source/` 树计算后与分类绑定。许可分类器 SHA 可经 `JobService(accepted_classifier_sha256=...)` 覆盖，默认钉 v2.4。
- 报告契约 3.0/3.1 的可选 `isolation` 块等其余字段不受影响。

## 4. 边界与未决

- 本机只编辑并跑平台 pytest，**未部署、未跑真实转换样本**；真实 capsule 提交、拒收、其他客户端无法绕过的最终验收，由用户今晚重新部署后在隔离环境进行。
- 批次授权字段校验只证明"证据已填写"，不证明隔离真实存在（Spec05 §6）；现场隔离实证由 C7 attestation/人工签署与 VM 施加。
- 分类器脚本未改（SHA 钉定不变）；平台许可 SHA 默认 v2.4，分类器升级时须同步该集合。
- Agent 侧提交须随 capsule 附上 `classification` 与 `batchAuthorization` 两份；适配页与门禁页已更新该口径（重新部署后生效）。
