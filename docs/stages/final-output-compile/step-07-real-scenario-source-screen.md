# step-07：真实攻防源码的首轮准入审查

> 状态：已完成（首轮三份旧候选均有明确准入结论；未导入源或执行样本）
> 归属：[阶段 index](index.md)

## 目标

从旧用例候选池中核实至少一份实际攻防行为的 C 源，判断其是否具备进入下一次 C→C++ 转换 run 的来源、许可、编译上下文、安全和可观察条件。避免把目录标签、单文件改写或编译成功当成真实场景有效性。

## 纳入与非目标

- 先审旧目录的 `ApiSetMap.c`、`ReflectiveLoader.c`、`http_upload.c`，必要时只读核对官方上游仓库和许可证；逐份区分上游原件与旧目录改写件。
- 对每份记录源文件 SHA-256、物理行数、实际行为、依赖、潜在副作用、可在现有 Controller 观察的义务与缺口；给出 `可进入下一步方案`、`需补条件` 或 `不采用` 的结论。
- 不把旧源码复制进本项目的 `sources/`，除非一份候选通过逐文件来源/许可与隔离前提；本步骤不调用配置模型、不编译/运行源码或转换产物、不提交 Controller job。
- 不把高风险行为改成空桩换取“可用”；如果现有隔离/Collector 无法证明关键行为，功能保持维持 `UNVERIFIED`。

## 依赖与前置

1. 使用[旧候选索引](../../test/dataset/legacy-candidates.md)及外部只读目录；当前工作树在上一轮提交推送后应为干净状态。
2. 外部上游信息只作为来源核验，优先链接发布方仓库、固定提交与许可证；搜索结果或文件头自称作者不能单独证明本地副本未经改写。
3. 现有 Windows same-runner `baselineReference.artifactHash` 故障、network/registry 观察缺口先视为取证限制；不以本机编译绕过。

- `docs/test/dataset/legacy-candidates.md`：回填已审候选状态，指向审阅记录。

## 验收依据

- 至少三份候选有可追溯的本地 SHA-256、源/改写区分和各自的准入/否决理由；上游可定位的候选记录固定提交或明确“未核实”。
- 至少一份候选列出可观察正常路径、失败路径、禁止副作用、所需 Collector 和当前缺口；若没有合格首例，明确下一轮选源条件及阻断点，不伪称已选定。
- 所有结论明确证据等级为静态审阅；未执行样本，未新增转换效果验证。

## 风险与停止条件

- 上游版本/许可无法绑定本地副本，或改写范围无法说明：不得晋级为冻结源。
- 样例包含真实外联、命令执行、进程注入或持久化而缺可控隔离/观察：只留静态候选，不运行；需另立安全与评估方案。
- 目标编译/功能判断若被 same-runner 或 Collector 缺口阻断：先记录环境/证据问题，不把它归因于模型或转换知识。
