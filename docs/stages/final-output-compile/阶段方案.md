## 阶段目标

把**转换系统最终交付版本**在指定目标环境和工具链下的编译通过，作为本阶段“语法正确”的操作性判据。只评价最终交付的目标代码；此前各稿是开发诊断材料，不分别进入阶段质量指标。长期目标仍是目标代码可运行且功能准确，但本阶段不统计功能正确率，也不扩充行为 oracle。

“编译通过”必须附目标语言标准、OS/架构、编译器/SDK、依赖、编译命令及目标文件版本。片段在用户给定或明确声明的中性上下文中检查；上下文不足记为无法判定，不要求片段独立运行。若本次单文件契约包含链接，则记录完整构建结果；编译、链接、启动的失败原因分开保存，不把启动或行为匹配并入语法判据。编译通过不证明功能、网络行为、安全属性或生产可用性。

## 工作顺序

1. **选窄范围并冻结条件**：先围绕已有 C → C++ 方向，选择有明确来源、许可和静态安全边界的不同源码；逐项声明源/目标 OS、编译器与标准、依赖、片段上下文或单文件构建方式。C01 是超出 700 物理行规划范围、且源中自带 Windows 分支的探索例，不作为独立跨 OS 移植或 700 行支持能力证据。
2. **围绕真实失败补知识**：优先检查类型与声明/定义、头文件和宏、回调与调用约定、平台 API/依赖、长文件内部引用等可导致编译失败的知识缺口。每条新规则写明触发条件、版本/平台前提、映射边界、反例及依据；不为尚无消费者的方向建空 Skill。
3. **按现有闭环产出最终版本**：使用 `.env` 配置模型生成和必要的有限修订；可以用获批的隔离编译诊断指导修订，保存各稿及诊断以定位 Skill 缺口。中间轮次和首次生成通过率可以内部分析，但不是产品指标，也不把修订后的成功回写成原稿成功。
4. **只按最终版本计分**：编译可发生在有限修订的中间阶段，但每项任务只取最终交付版本的结论进入阶段指标。**标准执行形态统一为双侧执行**：交获批隔离 VM 的 comparison capsule 构建并运行源、目标两侧，源侧 build 作对照基线，本阶段只读取其 **build 证据**（execution/comparison 不计入功能率）。源无可运行入口（如库翻译单元无 `main`）时默认补写最小入口/驱动使其可运行，并在冻结记录标注补写内容；不再逐次询问 compile-only/comparison 或是否补入口。隔离与外联安全边界不变；远端 Controller/隔离 VM 恒就绪且已授权，到评估步骤直接提交执行、不逐次确认可达性或询问是否评估，最终版本在 Controller 回传 build 证据前标 `UNVERIFIED`，仅当 Controller 真实返回基础设施/环境故障才记环境失败；任何情况不得在本机编译或在边界外擅自运行样本。
5. **按失败类别更新 Skill 并扩展**：先在已覆盖方向内修复可归因的重复失败，再逐次拓展语言方向、真实场景或系统方向；每次明确新增维度与适用样例。保留先前样例作同条件复查，但不把不同工具链、提示或 Skill 版本的结果混成同一个通过率。

## 记录与判定

- **当前阶段结果指标**：最终交付版本编译通过率 = 在冻结目标条件下取得“编译通过”证据的有效任务数 / 取得可判定编译结果的有效任务数；同时公开总任务数、失败数、环境/依赖故障数及未验证数，避免通过排除困难任务抬高比率。样本不足时只报告逐例结果，不宣称总体准确率。
- **开发诊断**：保留原始编译诊断、失败类别、模型修订前后差异、Skill 命中/缺口、耗时和 token（可得时）。这些数据只用于解释问题和改进 Skill，不作为用户关心的最终代码质量指标。为保证不同批次可比，模型/提示、修订停止规则和编译契约应记录并在同批保持一致。
- **功能与安全**：本阶段功能正确性记为未评估；不复用 `1/1 output` 或五个固定 HTTP 请求的匹配结论外推功能。静态审阅和执行安全边界照常适用，获准编译不自动授权运行。
- **交付报告**：最终 `result.md` 按[中文报告骨架](../../../references/delivery-handoff-contract.md)先回答交付、语法/编译、功能三项结论，再说明关键修订与证据范围；中间诊断放入过程文件，正文只保留影响最终判断的事实。
