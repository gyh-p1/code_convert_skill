# 项目开发规范

> 文档类型：项目协作与开发规范
> 状态：ACTIVE（当前项目规范）
> 更新：2026-09-29
> 适用范围：根文档、Markdown Skill、`references/` 知识、`docs/test/dataset/` 历史数据与必要的辅助工具

## 1. 项目定位与文档职责

本项目以轻量 Markdown 转换 Skill 为知识主体，不预建独立转换运行时或通用评测平台；2026-09-29 冻结的交付目标另要求单批不少于 40 个任务、允许排队的自动化评测能力，应优先复用现有隔离评估链路实现最小可用调度，不把“无通用平台”误读成“无需实现自动化评测”。业务定位、能力边界和当前事实以[项目业务文档和能力边界](项目业务文档和能力边界.md)为唯一真源；根 `README.md` 负责导航；根 `SKILL.md` 是产品知识入口；本文件规定项目协作、阶段与证据口径；[Skill 编写规范](Skill编写规范.md)规定知识内容的写法；[安全边界](安全边界.md)规定开发期样例和执行约束。

`.agents/skills/code-convert/SKILL.md` 只负责发现并链接根入口，不复制转换规则。语言方向、语义场景、源/目标系统方向和任务模式各负其责；ATT&CK 只作分类元数据，不自动生成专属转换规则。

当前七语言共性事实由 `skills/references/seven-language-common-semantics.md` 导航至 `skills/references/languages/` 的单语言参考页；`skills/directions/<源>-to-<目标>/SKILL.md` 维护该有向方向的映射并链接源、目标语言页。修改共享事实时只改对应语言页，不在 42 个方向重复；修改方向差异时不回写成所有语言共同保证。目录和规则文本仅证明知识可检索，不代替逐例转换证据。

## 2. 开发总原则

- 改动前先核对当前文件、真实入口、引用、来源和未提交改动；不把历史文档、空目录或拟议方向当作已实现能力。
- 每项改动明确目标、范围、非目标、依赖、验收依据和停止条件；区分当前事实、目标设计、计划和验证证据。
- 只有出现真实消费者、可归因失败或明确的知识缺口，才新增 Skill、目录或机制；不预建完整运行时、注册表、评测平台或空壳结构。
- Skill 只提供转换决策依据。文本审阅、语法/编译证据、功能行为证据和检索效果证据必须分开记录；模型自评、代码相似度和本地链接检查不能冒充转换验证。
- 长文件遵循根 `SKILL.md` 指向的长文件工作流；700 个 LF 归一化物理源代码行是计划上限，不是已经验收的能力。

## 3. 当前开发阶段与退出条件

阶段不再单独维护 `stages/` 文档树。以下表格是阶段状态、工作边界和退出条件的唯一入口；历史数据只作为证据归档，不改变阶段状态。

### 交付基线与阶段差距（2026-09-29 冻结）

交付需求基线见[业务文档“交付目标冻结”](项目业务文档和能力边界.md#交付目标冻结2026-09-29)：C、C++、C#、Python、Go、PowerShell、Ruby 七种语言的 42 个有向转换方向，至少 10 个不同 ATT&CK Enterprise 战术类别各有案例与转换证据，至少 Windows/Linux/macOS 三类目标 OS，一次性不低于 600 行等价转换，以及单批提交不少于 40 项、允许排队的自动化评测。此处仅冻结目标，**不将阶段 1 现有编译证据升级成等价或批量评测验收**。

本阶段既有状态仍如以下 3.1–3.4 所记：2026-10-02 交接的 42 方向知识是静态规则文本，只有 C → C++ 保留部分逐例编译证据，不能据此视为全部语言、战术及 OS 的转换效果覆盖；长文件范围内尚无能力验收；40 任务单批自动化评测尚无实现与批量证据。原阶段 2“未启动”和阶段 3“候选”的事实不因交付目标冻结而变更。交付冲刺需先核验目标工具链、模型额度、隔离评估容量、可授权案例与行为 oracle 是否齐备；知识增补与逐例评估交错进行，留足回归/移交时间。若依赖缺失或两周内无法取得证据，及时标为交付风险并提出范围/期限/资源取舍，不能自行降低冻结指标。

验收材料至少包括：明确的方向和战术/行为覆盖表、三类目标系统的工具链证据、≥600 行单次完整转换的最终版本及可观察等价证据、单批 ≥40 项自动化评测的队列与逐任务/汇总记录（含失败、阻塞和重跑口径）。静态文档检查、历史探索 run、模型自评或编译 PASS 均不能单独满足这些新目标；测试仍须遵循[安全边界](安全边界.md)。

### 3.1 阶段 0：基础入口与规范（已完成，进入维护）

- **目标**：建立根入口、Codex 发现薄入口、知识维度边界、交付和安全规则。
- **已交付**：根 `SKILL.md`、`.agents/skills/code-convert/SKILL.md`、语言/场景/系统/工作流知识及四份开发期规范文档。
- **不包含**：转换正确性承诺、独立运行时、自动评测框架。
- **完成依据**：入口可追踪到根 `SKILL.md`，规范与业务边界没有互相覆盖或暗示未实现能力。

### 3.2 阶段 1：最终交付编译质量与 Skill 拓展（当前进行中）

- **目标**：围绕真实消费者和可归因失败，审阅/修订已有与新交接的实质规则；以冻结目标工具链返回的**最终交付版本编译证据**作为当前“语法正确”的操作性判据。42 方向规则覆盖仅为知识状态，新增方向尚待逐项案例与证据。
- **纳入**：C → C++ 已覆盖方向的规则修订；网络、文件、并发和 POSIX ↔ Windows 方向的缺口补充；有明确来源、许可和安全边界的真实源码案例；最终 run 结果与失败归因归档到 `docs/test/dataset/`。
- **每个案例必须冻结**：源码快照/许可、任务模式、源与目标语言及 OS、架构/ABI、编译器/标准/SDK、依赖、检查上下文、禁止副作用、目标文件版本和报告口径。
- **执行规则**：按现有转换—自审—第三方评估闭环工作；配置模型生成后允许有限同模型修订。获批时统一由隔离环境双侧构建源和目标，当前只读取 build 证据；源无入口时补写最小入口并在冻结记录中说明。不得用本机编译或运行替代第三方证据。
- **当前指标**：只按最终交付版本记录编译 `PASS`、编译失败、环境/依赖故障和 `UNVERIFIED`。中间稿失败、修订次数、模型自审和有限行为匹配只作开发诊断。
- **明确不做**：本阶段不统计功能正确率，不由编译通过推断功能/安全等价，不恢复固定 C01–C04 无 RAG/RAG 配对，不建设本地转换或评测运行时。
- **退出条件**：当前纳入方向的规则缺口已按真实失败完成一轮可追溯修订；每个新增案例都有冻结记录、最终版本和可核对的编译结论；剩余问题已被明确标为 `UNVERIFIED`、环境阻塞或下一阶段候选。未满足时保持本阶段进行中，不用样本不足宣称总体准确率。

### 3.3 阶段 2：功能行为验证（未启动）

- **进入条件**：阶段 1 的目标环境、样本入口和编译证据稳定，并为每个案例先冻结可观察行为义务、输入输出和安全隔离条件。
- **目标**：在获批隔离环境中按案例验证场景级行为保持；编译、链接、启动、行为和安全结论分开报告。
- **不包含**：把有限 loopback 结果外推为完整攻击链，把历史探索稿倒填为正式基线。
- **退出条件**：至少有与案例义务一一对应的可复核 oracle、成功/失败/未覆盖解释和安全边界记录；否则停留在“未启动/未验证”。

### 3.4 阶段 3：检索/RAG 试验（候选，未立项）

固定四例无 RAG/RAG 对照已取消，不能通过补文档或复用旧 run 恢复。只有提出新的问题、样本、单一变量、成本口径和安全边界后，才可另立试验；在此之前不得声称 RAG 已实现或提升质量。

#### A｜语言知识负责人：可直接转发的任务卡

**任务目标**：让 Agent 在七种语言的任意不同源→目标方向都能找到适用的语言决策依据、知道不能机械等价的地方；研究与写知识，不负责替项目负责人宣称 42 个方向已转换成功。

1. **D1–D2 先交范围表**：列出 C、C++、C#、Python、Go、PowerShell、Ruby 的本次标准/解释器/运行时及版本候选，逐一确认可获目标工具链；生成 42 行有向矩阵，每行写 `源→目标｜来源规则｜目标规则｜至少三个高风险差异｜适用案例 ID｜资料依据｜状态`。版本由项目负责人冻结，不能个人悄悄换版本。
2. **先写共性，再写方向差异**：搜集官方语言/运行时资料，梳理值与引用、整数溢出、字符串与字节/编码、容器迭代、异常/错误与退出码、资源生命周期、异步/并发、文件与网络库的语言层调用。源语言和目标语言各自的事实尽量复用，只有映射确实依赖方向时才写专向规则；不建 42 个空 `SKILL.md`。需要新目录时先说明当前由哪个任务消费。
3. **每条交付规则的固定结构**：源码什么条件触发；适用语言版本/运行时；原可观察行为；目标可选写法与不适用条件；一个错误机械替换的反例；遇到不确定性怎么处理；官方标准或文档链接。代码短例仅帮助理解，不能声称通过编译。跨 OS/API 与战术部分只引用 B 的规则，不在 A 处维护第二份。
4. **交接顺序**：D3–D6 优先交已有消费者相关的 C/C++、文件/网络与 Python/Go 等高风险映射，供 C 选例及项目负责人早测；D7–D9 交剩余方向差异和 42 行矩阵缺口；D10–D12 按冻结案例的可归因编译/行为诊断修订，不按模型印象修规则；D13–D14 停写新方向，提交一致性核对与未验证清单。
5. **交付验收**：42 行无缺项、版本与依据可追溯、确有内容的规则可被根入口按需发现、与 B 的 OS/场景规则不冲突；每行区分 `已编写规则`、`仅研究材料`、`有转换证据`、`未验证/阻断`。项目负责人逐项静态审阅；42 行矩阵或规则文本本身不能算 42 方向验收通过。

**必须及时回报**：某方向无目标工具链、库映射可能改变外部副作用、版本资料彼此冲突，或需要 C 提供特定源行为才能判断时，当天写出所需信息及可验证的最小案例，不用猜测补齐。

#### B｜战术行为与目标系统负责人：可直接转发的任务卡

**任务目标**：用真实代码行为支撑 10 个不同 ATT&CK Enterprise 战术类别，并为三个目标 OS 提供按实际消费者触发的系统差异知识；不把战术分类当作 API 映射。

1. **D1–D2 提名与核验**：从官方 ATT&CK Enterprise 分类选择至少 10 个不同战术 ID 的候选，逐类指出何种源码行为能支撑分类、C 能否找到有许可且安全可观察的案例、A 的语言方向是否有消费者。项目负责人据此冻结首批类别；缺实际行为的类别立即替换候选，不写空战术 Skill。
2. **逐战术交付一行行为契约**：`战术 ID/官方名称｜案例/符号或行段｜真实行为而非标签推断｜输入/输出、状态、错误及资源义务｜可隔离观察方式｜关联的场景 Skill｜当前缺口｜转换证据状态`。同一案例可支持多个战术，但每个战术都要独立说明行为依据；危险能力不因分类需要而新增。
3. **逐 OS 交付系统清单**：对 Windows、Linux、macOS 的真实候选任务，冻结目标工具链/SDK 与 API 版本；按网络、文件/路径、进程/权限、线程等**源码确有**行为记录源 OS→目标 OS 的语义差异、错误码/资源处理、可用替代和不可映射处。macOS 与 Linux 即使共享部分 POSIX 接口也分别核对；三类目标各需关联至少一个可评估任务，不预生成全部 OS 组合。
4. **写 Skill 的边界**：优先补现有 `skills/scenes/` 和 `skills/systems/` 的真实缺口；新场景或系统 Skill 要有具体消费案例和可执行规则，依[Skill 编写规范](Skill编写规范.md)写前提、行为、反例、未知和权威依据。ATT&CK 索引只放分类/检索线索，不复制行为映射；资料搜索和规则撰写不意味着攻击行为已获运行许可。
5. **节拍与验收**：D3–D6 与 C 完成首批战术/OS 案例对齐并交高风险规则；D7–D9 完成 10 行战术证据链和三类目标 OS 差异矩阵的候选版；D10–D12 仅据项目负责人反馈的可归因诊断修订；D13–D14 核对每类是否真有代码案例和转换证据。缺证据者保持缺口，不能以 10 个分类标签计达标。

**必须及时回报**：战术分类无源码证据、场景需要新的高风险副作用、macOS 工具链/API 无法取得、源 OS 分支不明或可观察 oracle 不成立时，当天给项目负责人和 C 一条具体替代案例或阻断原因。

#### C｜测试集负责人：可直接转发的任务卡

**任务目标**：交可冻结、可授权、可评估的候选任务，不负责运行不可信代码、调度模型或填写虚构的 PASS。逐项字段与入选门槛以[测试集征集要求](test/dataset/README.md#本次交付的测试集征集要求2026-09-29)为准。

1. **先画覆盖矩阵再找源码**：42 行按七种语言的源→目标有向方向编号；另外建 10 个战术 ID 与 Windows/Linux/macOS 三列，标明案例 ID、源文件真实行为、目标环境与证据状态。可复用已获许可的同一上游源码到多个不同目标方向，但不能把同一个 C 源文件冒充 Python/Ruby 源任务；一个任务仅计一个方向。
2. **筛选顺序**：先找可固定上游提交/许可、依赖少、入口与目标工具链可用、有真实输入/输出/错误路径的素材；再确认安全隔离可审批及行为 oracle；最后才看是否同时覆盖缺失战术/OS/方向。不要为凑数选来源不明、需要真实目标/凭证、仅有无关填充行或无法检查目标的样本。
3. **≥600 行长例单列**：优先选一个来源清楚、600–700 个 LF 物理源代码行的完整单文件（兼顾既有 700 行计划上限），冻结行数、有效行和 token/逻辑密度；若只有超 700 行候选，单列超计划范围，不据此宣称 700 行范围已验收；列入口、函数/类型/状态依赖、外部依赖及至少一组正常和一组错误路径的可观察义务。600 行只是规模门槛；最终等价结论由项目负责人在授权环境取证，C 不把候选当等价成功。
4. **D1–D2 交首批可行性包**：优先找覆盖七种源语言的起始样本、三类目标 OS 的评估路径和长例候选；把依赖/许可/macOS 可用性风险前置。D3–D6 交首批可冻结任务给项目负责人早测；D7–D9 交齐 42 方向候选、10 战术和 3 OS 覆盖矩阵及 ≥40 项批次清单；D10–D12 按实际阻断替换低质量案例；D13–D14 锁定版本/哈希并移交未覆盖项。
5. **逐项交接**：固定源快照/许可、源目标语言与 OS、任务模式、源码行为位置、ATT&CK 依据、工具链/依赖、输入/预期结果/oracle、安全与隔离、适用 Skill、状态与负责人。至少用 `候选→审阅通过→已冻结→已评估/阻断` 区分准备和证据；已有历史 run 只作线索，未经重新核对不可计数。

**验收**：候选池至少 42 个**不同方向**的有效任务，10 个战术各有行为依据和案例，三类目标 OS 各有明确检查环境，长例符合长度/行为门槛，≥40 项可组成同一批次。候选数量与最终转换成功数分开；由项目负责人统一批准冻结与执行。

#### 项目负责人｜本体、集成和最终验收任务卡

1. **D1–D2 冻结运行契约**：确定各语言标准/运行时与 Windows/Linux/macOS 目标工具链，核验 macOS 和双侧隔离 Controller 是否真可用、模型配额/时限与一次提交 ≥40 项的预算；审核 B 的战术提名和 C 的样本安全/许可。资源不具备时立即标阻断及所需替代资源，不等候文档完成。
2. **明确交接入口**：A/B 交规则候选和矩阵，C 交任务候选；你审阅后才纳入根 `SKILL.md` 可见的知识与冻结任务。按任务画像选择语言+场景+系统+工作流，不因 42 个方向预建 42 个空目录；日终回传具体案例诊断及规则缺口给相应负责人。
3. **最小批量调度**：使用现有模型与第三方隔离评估链路；为批次和每项任务分配稳定 ID，记录排队/开始/完成/代码失败/环境阻断、输入和最终产物版本、重试次数、诊断/证据位置与汇总。控制并发与额度，支持中断后识别已完成项且不无声丢失或重复执行；一次提交 ≥40 项后不得再人工逐项触发。Agent 可负责调度，但要留可复核的持久记录，无需建通用评测平台。
4. **两条验收线分开**：先用 3–5 项经授权任务验证队列闭环，再做单批 ≥40 项的批量试验；方向/战术/OS 转换效果逐例记录语法/编译、功能和安全结论。≥600 行单次完整转换另冻结源、目标及正常/错误路径 oracle，在授权环境取证，不能拿队列完成或编译 PASS 冒充行为等价。
5. **最终输出**：42 方向、10 战术、3 OS、长例、批量能力五张覆盖/证据汇总；每一格说明 `PASS/FAIL/UNVERIFIED/环境阻断`、适用条件和证据位置。D10–D12 优先修真实阻断与高价值规则，D13–D14 封版并移交范围外问题。任一门槛缺证据即写未达标，不自行降低目标。

**日常协调**：每天收 A/B/C 的新增条目、待决策事项、阻断和次日计划；只把可归因诊断派回对应负责人。争议以[业务真源](项目业务文档和能力边界.md)、[Skill 编写规范](Skill编写规范.md)和[安全边界](安全边界.md)为准；不要同时改动同一文件而覆盖未提交工作。

**交接节拍**：D1–D2 三位负责人先交矩阵表头、来源/依赖核验和首批高风险缺口；D3–D9 每日交可审阅的规则或候选任务，项目负责人同日反馈真实编译/行为诊断（仅在已获准隔离环境）；D10–D12 对覆盖矩阵和批量队列做缺口回归，不再为凑数创建空规则；D13–D14 冻结输入与最终版本，整理逐项证据及未达标风险。每次交接以“已验证／仅文本审阅／未验证／阻断”分层，依赖或额度不足当天升级，不等第二周末才发现。

**最小可证伪试验**：先用小批量（例如 3–5 个来源/语言/OS 各异的授权任务）试通同一提交→排队→评估→归档链路，只改变批次任务数扩至 ≥40；成功信号是有效任务均由自动链路进入有评估证据的终态（可有明确的代码失败）、无无声丢失/重复执行，且批次报告可复核；环境阻断须单列并恢复后重提，不能把大批未评估的阻断当作 ≥40 项能力通过。失败则先修调度/环境，不扩写知识冒充系统可用。转换质量另按固定案例与冻结工具链逐例验证，不把容量试验当等价试验。

## 4. 证据与交付规则

- 片段任务关注声明上下文中的语法；单文件任务还应记录场景级功能目标，但当前阶段功能结论写 `UNVERIFIED`，除非另有正式行为证据。
- 最终报告先给出交付、语法/编译、功能三项结论，再说明关键修订、证据范围和未决项。中间诊断不能回写成原始稿通过。
- 有效任务、可判定编译结果、失败、环境/依赖故障和未验证数应分别列出；样本不足时只报告逐例结果。
- 新知识条目必须写明触发条件、适用平台/版本、映射边界、反例或未知项以及依据。不得用相似 API、目录名或 ATT&CK 标签暗示等价。

## 5. 数据与文件布局

- `docs/` 根目录只保留开发期规范性文档；不再建立 `docs/stages/`。
- `docs/test/dataset/` 是唯一保留的测试/历史数据区，包含逐例 case、冻结输入、模型产物和第三方返回证据；共享来源快照不再单独保留，历史 run 仅使用各自 capsule 内的冻结副本。
- 不再保留 `docs/test/candidates/`、单独的 `docs/test/sources/` 或 `docs/test/README.md`。新增数据必须先满足来源/许可/安全边界和当前阶段入口要求。
- 文件名清晰；Skill 目录使用小写连字符。不要提交凭证、个人信息、受限源代码或环境状态。

## 6. 安全与中断处理

涉及执行、删除、难恢复副作用或外部模型调度时，先核对精确目标和授权；风险超出[安全边界](安全边界.md)时停止并说明。开发文档删除后，以本文件第 3 节为阶段状态真源；恢复工作时先读业务真源、本文件当前阶段、相关 Skill 和数据集案例，不依赖聊天上下文或已删除的历史索引。

## 7. 完成说明

每次交付说明：实际改动文件、人工检查范围、执行过的命令或静态检查、未运行的代码/样本，以及尚未验证的编译、功能、外部环境和安全结论。只做文本、结构或引用检查时，明确写“未进行转换效果验证”。
