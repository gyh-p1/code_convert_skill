# Controller 作业阻塞与维护恢复适配

> 状态：条件适用。转换智能体可在获得管理者独立维护授权后执行维护，无须管理者亲自操作；尚无适用维护授权时只做普通查询／恢复与交接。本文不是某次具体恢复的授权，不授予安装目录/jobs 访问或样本执行权限。

角色政策按用户 2026-10-20 最新澄清：可以采用管理者授权的方式让智能体维护，不要求管理者亲自执行。因此不沿用来源文档对“转换 Agent 不调用维护接口”的绝对身份限制；维护权限、接口技术约束和精确影响范围仍分别核对。这是本项目执行授权口径的调整，不是服务端 API 已升级或凭据已配置的证明。

先核本项实际平台实现／发布身份、健康资料及合法部署说明。未证实支持时，不调用猜测的管理员路由；404/503 不自动等于无阻塞或服务可安全重启。没有维护授权的 Agent 按现有[回执恢复](remote-controller-adapter.md#提交结果未知时的恢复)和查询接口行动，不绕过角色边界。维护者可以是管理者本人或其授权的智能体；具备独立维护授权后执行 §3–5，转换授权、batchAuthorization 和普通 API 凭据不自动包含维护权限。

在既有维护／attempt 记录关联真实授权来源、被授权操作者、Controller／job 或受限的批次范围、允许动作及有效条件。授权须覆盖 plan 的实际 VM scope、可能中断的任务与恢复动作；可为有边界的持续授权，不强制每个 job／每次 GET 重新申请。已有授权仍覆盖本次动作时直接沿用；仅超出范围、到期或来源不明时补充相应授权。管理员凭据通过受保护环境或秘密注入提供给获授权执行通道，记录引用及适用性，不要求用户在聊天粘贴或回显令牌。允许调度恢复不自动包含产品部署、服务重启或整体归档，这些动作按已有实际授权范围判断。

## 2. 普通转换 Agent 的诊断与交接

| 现场事实 | 可做的恢复／诊断 | 停止和交接条件 |
|---|---|---|
| 提交断连，缺回执 | 保留原 submissionId、原 capsule 字节哈希、请求身份／时间及传输诊断；按已支持的精确材料规则找回原 job | 不用新 ID 掩盖未知提交；无法确认接收／清理时 WAITING |
| 持续 409 controller_busy，明确 jobCreated=false | 保存 health、runners 和 409 的原 HTTP/body；已支持时消费 submissionReadiness／blockingJobs，关联已知精确 job | 无声明字段就记缺口，不猜阻塞 job；不无限重投、不把 busy 当传输不可达 |
| 阻塞 job 仍有活动调用、排队执行、CLEANING 或清理未知 | 按原 job 查询／逐件取证；记录当前角色、阶段及可得清理资料 | 不因超时到点、runner READY 或 ready=true 解锁；维护也不得绕过活动互斥 |
| 历史 job 损坏、RECOVERY_REQUIRED、恢复后仍 busy | 保存精确 ID、原响应、已取得证据及缺件；交维护者诊断受理身份、scope、磁盘／ACL／VM 状态 | 不读取／编辑 jobs；状态损坏不等于从未执行 |
| Controller 健康端点不可达 | 保留登记端点的有界传输诊断；未决执行仍沿原恢复规则；无未决提交的新项按既有可达性分支 | 本页不是服务启动手册；只能引用已授权的实际部署／服务操作说明，不猜服务名、PID、启停命令或新实例 |

交接包放在本项既有记录中，包含：受影响 job／submissionId、端点与实际实现身份、时间范围、精确请求／capsule 摘要、状态／409／health／runners 原件、已知活动／清理／缺件及待确认问题。无原件的字段写未知；不复制密钥、样本载荷或源码全文。批次中只推进确实不受该阻塞影响的工作，不占用清理未知的环境。

“请求维护”须走用户已授权的渠道；没有消息授权时只形成可交付的交接记录，不自动向管理员或其他任务发送消息。

## 3. 维护者：诊断、权限与 plan 审阅

以下是所核源码版本的维护契约，须先确认当前部署支持。获授权维护者（包括获管理者授权的智能体）按部署允许的原生工具逐条调用，不写包装脚本或自动轮询。不能仅因执行者是智能体就强制改由人工操作，也不能在没有覆盖本次动作的授权时代行。

| 路由／资料 | 维护者消费方式 |
|---|---|
| GET /api/maintenance/blockers | 核精确阻塞集合、活动执行及维护操作；共享 jobs 只由一个 Controller 进程管理，不开多 worker／并行实例绕 busy |
| GET /api/maintenance/jobs/{jobId} | 取得 plan：受理／状态可读性、原清理证据、VM scope、已有 operations、releaseEligible、recoveryEligible 和 reviewToken；先审阅后选择动作 |
| 权限 | 独立 Authorization Bearer；CODECONVERT_MAINTENANCE_TOKEN 必须已通过受保护机制注入 Controller 进程，至少 32 字符强随机。只在客户端设置不能启用服务端；未配置／过短可返回 503，错误凭据 403。获授权智能体可通过受保护执行通道使用，令牌不交无维护权限的提交者、不入仓库／作业／日志／命令记录 |
| scope | 新 job 核受理时完整配置身份，VMX／快照／Agent 地址不符则拒绝。旧 job 须有原 runner assignments，维护者还须确认其所指当前配置与合法 VM 映射；plan 显示当前 scope 不证明历史物理身份，映射无法确认时不执行。不能按 OS／READY 猜 VM |

受理身份缺失／损坏，或没有可验证 scope 时不恢复放行；先由获授权维护者处理底层缺口，不清锁。新 job 的保守 scope 可能覆盖受理时所有 runner，包括三台 VM，必须按实际 plan 审阅影响；不能默认仅恢复报错的一侧。

## 4. 维护者：选择动作与处理结果

| action | 必需条件和实际动作 |
|---|---|
| release-cleaned | 仅 releaseEligible=true。原状态已终止、没有 current role／cleanup unknown；已 acquired／attempted 角色、call 身份及真实清理均可验证，已有真实回滚、无污染且 READY。用于实际清理完成但报告／metadata 完整性仍阻塞的情况；READY 本身不够 |
| restore-and-release | 仅 recoveryEligible=true。按审阅的精确 scope 实际 stop→revert snapshot→start→Agent health／契约核验；全部成功才释放，任一失败／污染／写盘失败继续阻塞；源／目标程序不重放 |

POST /api/maintenance/jobs/{jobId}/recover 的请求只有 action、reviewToken、operator、reason 四个字段。operator/reason 是真实维护身份及依据，不含秘密；reviewToken 绑定当前审阅，过期 409 须重新 GET plan 并审阅，不能循环重试旧请求。运行中、准备中或已有维护操作也可为 409，不能把它们当已受理的新维护。

2026-10-21 候选审查修订后，reviewToken 同时绑定原件指纹和 plan 的精确恢复 scope／scope 缺口，evidenceFingerprint 单独给出原件身份。旧 job 的文件未变而快照／VMX／Agent 地址变更时，旧审阅也失效；后台排队后及逐台恢复前后仍复核，失败继续阻塞。先核实际部署支持，不能从文档假定现役已有修订；不添加 POST 字段。

HTTP 202/PENDING 仅表示排入维护；HTTP 200 仍须读业务 status。逐次手工 GET 原 plan 的 operations，按实际约定间隔跟进，保留精确 operationId／回执。只有真实 SUCCEEDED 才是该维护操作成功；HTTP 超时／断连时先找回原 operation 的状态，不盲目重复回滚。

## 5. 验证恢复和继续转换

维护成功后同时核该 plan 的维护记录、普通 job 查询、health 与 runners，保留原件：操作 SUCCEEDED、cleanupConfirmed=true、schedulingReleased=true，且 blockers 已不含该精确 job；其他阻塞逐项核对，不因一个成功就宣布 Controller 全面可提交。任务和 runner 恢复与维护互斥，不跳过原隔离／清理要求。

原 state／closure／失败／缺件保留，调度释放不是功能通过，也不自动将转换端 WAITING 改为 DONE。状态损坏时普通 GET job 可返回 409 job_state_unreadable，维护者用 plan 与原可读证据核对，不宣称旧状态已修复。普通 Agent 收到合法回执后只沿现有证据／终态门禁继续。

需要新评估时先修正真实原因，按[任务状态](../../framework/task-state-contract.md)核冻结、版本、预算及受影响源基线，重新核准入／授权／隔离后记录新 attempt；使用 submissionId 时用新 ID。旧 ID 仍返回原 job，损坏状态可返回 RECOVERY_REQUIRED，不重放样本。不要把精确 ID 恢复原回执与申请新执行混成一次重试。

## 6. 中断、失败与不能恢复的情况

成功释放依赖已持久化的操作记录和绑定哈希／受理／执行／清理摘要的 release 回执；缺失、损坏或原记录变化继续阻塞。PENDING 时进程中断不会自动放行或自动重放恢复；部署恢复后由维护者重新取 plan、审阅并判断新操作。成功回执完整且未变化时，受支持的新进程应重新验证并保留释放事实，不重写旧 job。以上是待核部署的持久化语义，普通 Agent 不直接检查磁盘文件。

新修订回执使用记录中的已审阅 scope 与原件指纹验证已成功事实，不因日后 runner 配置变化重新回滚历史 VM。旧成功格式仍核其原件指纹及记录摘要，不追改；未完成旧操作不自动消费旧令牌执行。

受理身份丢失、旧 scope 不可证、磁盘／ACL 故障或 VM 不能回滚时，本 API 不能安全放行。整体归档只能由获授权维护者作为另行处置，在备份精确 job、逐件摘要和维护回执齐备后进行；不能删文件、改终态、造 closure 或清空 jobs。归档会移出 API／去重集合，必须通知提交端；已知维护迁移后的 404 不证明从未接收。

维护接口、合法恢复能力和管理者授权均齐备时，智能体可在授权内直接完成诊断、plan 审阅、恢复及验证，不以“必须管理员亲自操作”为停止理由。缺接口／权限／合法 scope 时保留具体缺口与已有证据；需要实际授权或平台修复的部分才交接。文档存在不能代替实际部署、受保护权限和隔离恢复验收。
