# 转换—自审—第三方评估闭环（探索工作流）

> 状态：工作流规则；不证明转换效果，不提供本地构建许可。适用于已有目标代码、配置模型和获准第三方评估渠道的转换任务。业务边界以 `docs/项目业务文档和能力边界.md` 为准。片段任务无独立运行义务；单文件做功能比较时另需冻结行为 oracle。当前开发阶段、评估范围和退出条件见 `docs/项目开发规范.md` 第 3 节。

> **标准执行形态（本项目既定，不再逐次询问）**：所有转换 run 统一采用**双侧执行**——由 Agent 读取本工作流并严格按阶段门槛调度，用 `.env` 配置模型完成转换，交获批隔离 VM（loopback／无真实外联／可回滚快照）用 comparison capsule 构建并运行源、目标两侧，源侧 build 作对照基线。源无可运行入口（如库翻译单元无 `main`）时，**默认补写最小入口／驱动**使其可运行，并在冻结记录中标注补写内容；不再逐次询问 compile-only／comparison 或是否补入口。**远端 Controller／隔离 VM 恒为就绪且已获授权**，是**既定常备前提**——不逐次确认其可达性、不就“是否评估”询问用户；run 到达评估步骤即**直接组装并提交双侧 capsule 执行**，只有 Controller 真实返回基础设施故障时才按 §3① 记环境失败并在恢复后重提。隔离与外联安全边界不变；本阶段只把 **build 证据**计入指标，execution／comparison 结果不用于功能正确率。

## 1. 确定性边界与冻结输入

确定的是**阶段顺序、输入快照、重试上限、分流和证据判读**，不是大模型逐 token 输出或跨平台语义等价。在首次请求前记录：源码快照与哈希、语言/OS/ABI、实际条件编译分支、目标编译器与 SDK/标准、已选 Skill 的内容快照、提示主体、`.env` 的非敏感模型标识/API host/温度及请求参数、RAG 开关、目标文件命名、可观察 oracle、隔离/审批范围。密钥不进入提示、日志或交付。

正式编译质量试验必须先冻结目标编译器、工具链与检查上下文；功能比较还须冻结行为 oracle。不满足对应条件时只做标明假设的探索，不能事后把探索稿升级为正式基线。模型配置在同一 run 中改变或切换编译器/SDK，不属于同条件重试：另起 run/探查记录，不能合并统计。模型提供方若不支持可复现快照，记录实际返回模型名与非确定性限制。

## 2. 阶段及门槛

| 阶段 | Agent 的确定性动作 | 可前进条件 / 否则动作 |
|---|---|---|
| `FROZEN` | 核对来源、安全、边界、Skill、模型与目标环境；长文件形成源码/符号/行为地图 | 输入足够且不越权才请求配置模型；否则暂停或标明探索假设 |
| `GENERATED` | 保存原始响应及参数/用量；检查是否截断、是否完整单文件、关键符号/分支是否缺失 | 响应完整才进入自审；空响应、`finish_reason=length`、解析失败不能冒充自审通过 |
| `SELF_REVIEWED` | 将源/目标、任务契约和已选知识交给配置模型做一次结构化自审；每个问题需位置、来源（转换引入/源已存在/工具链未知）、证据、建议修改 | 只有**没有未解决、可定位的转换引入缺陷**且响应完整，才能作为“可交第三方”的内部预检；不是语法 verdict |
| `SELF_REPAIRED` | 把明确缺陷、约束和同一 run 的上一稿交回配置模型；保存完整新稿或可机械应用的确定性补丁及差异，再重新自审 | 默认最多 **2 次自修轮**；同一问题重复、产生无法解释的新副作用、模型持续矛盾/截断或仍有明确缺陷则停止，报告 `SELF_REVIEW_UNRESOLVED`，不无限循环。仅有“可能问题”但无定位时保留为风险，不伪造缺陷 |
| `EVALUATION_READY` | 预检状态可交评估后：双侧执行授权与隔离 VM/runner READY 为**常备前提，不逐次确认或询问**，此步只冻结本 run 专属项——评估契约、源码/目标哈希、冻结编译命令（含为可运行而补写的入口/驱动）、限时与清理；功能比较另确认最小行为 oracle；生成独立评估输入并**直接提交执行** | 仅本 run 专属冻结项缺失才 `BLOCKED`；模型声称“无问题”只是提交门槛，绝非第三方结果 |
| `EVALUATED` | 保存 Controller job ID、canonical report、source/target build 和 execution、comparison、清理/环境状态；优先从**build 证据**读取编译结论，再读行为证据 | 区分环境/工具链失败、代码编译失败、执行失败、行为差异与不确定；每个结论附到准确版本与工具链 |
| `REPAIR_AFTER_EVAL` | 仅将可定位的代码诊断/行为差异连同工具链、oracle 交回配置模型；生成新变体，重复内部自审，再在**相同冻结工具链和 oracle**上重新提交获准评估 | 默认最多 **2 次外部失败 repair 轮**。若失败无变化、证据不足、超预算或安全边界变化，停止并回报；不得反复盲投或把变体通过归给原稿 |
| `CLOSED` | 交付最终稿、原始稿/失败稿、模型自审与修订记录、第三方证据和分层结论 | 当前阶段只按最终交付版本统计编译结果；中间诊断供 Skill 改进。行为未评估时写 `UNVERIFIED`；环境、完整性与安全未覆盖部分分别记录 |

数字 2 是本探索工作流的默认上限，不是质量保证；正式试验在冻结契约中可另定相同的两组预算。任何模型请求不完整均不计为有效的”无问题”判断；为恢复传输可按相同输入重试一次，并保存失败尝试和实际参数，不能偷偷换模型或将失败重试当作 repair 成功。

各阶段产物的固定落点与命名（`01-frozen/`、`02-conversion/`、`03-self-review/`、`04-evaluation/job-<NN>-<用途>/`，以及 `target.gen` / `target.self-repair-<N>` / `target.eval-repair-<N>` 版本命名）见[交付与移交契约 §2.2](../framework/delivery-handoff-contract.md)，本文件不重复。

## 3. 第三方结果分流

1. **基础设施/runner/清理污染**：停止当前 job，标记环境失败；不让模型修改代码，不计为语法错误。恢复环境后须重新建立可比较的评估条件。
2. **工具链/契约不匹配**：例如为让 MinGW 进入 Windows 分支而伪造 `_MSC_VER`，记为诊断探查；不能据此宣称 MSVC 失败或成功。先确定权威工具链，改变工具链须另起评估版本。
3. **源端构建或基线执行失败**：无可比源基线；先审查源/环境/oracle，禁止仅凭目标输出宣称行为匹配。
4. **目标 build 失败**：在确认为代码相关后，原样保存编译命令、退出码、完整诊断与目标哈希，再交配置模型作 repair；只用匹配工具链的第三方重编译给目标变体语法结论。
5. **build 成功而运行失败或行为有差异**：不能退化为“语法错误”；依行为 oracle 找出输入、观察维度、差异位置，区分源已有问题与转换引入的问题后再决定 repair。
6. **所有适用维度匹配**：只报告实际覆盖的输入与维度；`1/1 output` 不等于网络、文件、进程、安全或完整行为等价。

`evaluator_manifest.json` 是本项目的移交/记录清单，不是旧 Controller 可直接提交的 capsule。Controller 实际 `/api/jobs` 使用 `comparison_manifest.json`、`input_profile.json`、`metadata.json` 与 source/target 树，要求双侧 `runCommand`，故会运行两侧——这正是本项目既定的双侧执行形态。本阶段只从其返回中读取 **build 证据**作为编译结论，execution/comparison 结果不计入功能率；不因“只看 build”就把它当成 compile-only 接口或省略双侧 `runCommand`。capsule 输入与报告均须保留，且不能把启动参数写入只供说明的字段后假定 Runner 会执行。

当前编译质量阶段不要求行为比较，但标准执行形态统一为**双侧执行**（见文首）：交获批隔离 VM 的 comparison capsule 构建并运行源、目标两侧，只取其 **build 证据**作为当前指标，execution/comparison 结果不用于功能正确率。源无可运行入口时默认补写最小入口/驱动并在冻结记录标注，不再询问是否补入口或改用 compile-only。**远端 Controller/隔离 VM 恒就绪且已授权**，到评估步骤即**直接提交双侧 capsule 执行，不再询问是否评估或其可达性**；仅当 Controller 真实返回基础设施/环境故障（§3①）才记环境失败并在恢复后重提。隔离与外联安全边界不变；任何情况下不改用本机编译，也不在边界外擅自运行样本。功能行为试验或检索对照没有当前执行任务；如另立新方案，须先定义新的样本与判据。

## 4. 自审提示词的最小契约

必须回答：目标是否完整、关键声明/入口/分支是否覆盖、是否有可定位的类型/API/调用约定/平台条件/资源生命周期疑点、这些疑点是源已有还是转换引入、具体修改及风险。输出 `REPAIR-RECOMMENDED` 或 `NO-REPAIR-IDENTIFIED`、逐项证据位置及可机械应用的修订或明确“无需改动”。结论与条目互相矛盾、空输出、截断、未知编译器却断言语法通过，均不视为可交评估。

自审关注 `min/max` 等头文件/宏依赖和实际分支，但不能冒充编译器；此次 C01 模型曾给出 `NO-REPAIR-IDENTIFIED`，第三方 MinGW/UCRT64 C++17 后来仍定位到 `min` 未声明，说明独立编译不可省略。

## 5. RAG 开关与采纳门槛

RAG 在该闭环中默认关闭。原固定四例配对计划已取消；若未来针对明确知识缺口另立对照方案，先冻结新的无 RAG 基线。RAG 不得替代自审、第三方编译或行为 oracle，也不得检索和注入其他 run 的目标代码。

在另行批准的检索试验中，每个检索片段必须记录来源、版本/发布日期、适用 OS/SDK/标准、检索查询、注入位置和 token 成本；优先使用官方 API 文档、标准、RFC 或经审阅的内部知识。无 RAG 与 RAG 仅改变检索/注入，固定模型、核心提示、Skill、工具链、oracle、重复次数和 repair 预算。只有当 RAG 不降低编译/行为结果、不引入来源错误或样例泄漏，且成本可接受时，才建议默认启用；不能据少量样本外推普遍效果。

## 5. 此次 C01 的可验证后续

当前 C01 是 1,317 行超出 700 行规划范围的探索稿；源中已有 Windows 实现分支，不能用于证明独立 POSIX→Win32 迁移。成功 Job 只在 MinGW/UCRT64 `g++ -D__POCC__ -std=c++17` 下完成五个 loopback HTTP 请求与 `output` 一维匹配，未覆盖 MSVC/Pelles、并发、文件系统和网络遥测。要检验新工作流是否减少不确定性：固定一个受范围约束且不泄漏目标实现的样例、工具链/模型/提示/Skill/oracle，唯一改动为启用本闭环的结构化自审与分流；比较首次可评估率、编译失败分类、外部 repair 次数、行为覆盖、耗时/token 和人工干预点。不能拿 C01 既有修订后的结果回填为此工作流的新基线。
