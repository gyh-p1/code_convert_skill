# 构建前提与工具链适配：语言/平台转换后的编译可用性

本文件在**任何需要进入编译或运行的转换任务**中读取。它规定转换后目标代码要能进入构建阶段所需的**构建前提**（链接库、工程文件、工具链版本、环境变量），以及这些前提应当**写在哪里**才能被执行。

它是**构建可用性**规则，不是"转换正确"或"功能等价"的证明。目标代码能编译不等于行为等价；本文件只处理"构建阶段是否会因缺少前提而失败"这一类问题。

## 0. 为什么需要本文件

在 batch-01～06 的真实运行中，多次出现**源码转换正确、但构建阶段失败**的情况，原因都不是代码本身：

| 现象 | 实际根因 | 当时处理 |
|---|---|---|
| Windows C/C++ `go build`/`gcc` 链接失败 | 源使用 Winsock，需链接 `ws2_32` | 人工改构建命令补 `-lws2_32` |
| C# 目标报类型缺失 | 缺 `.csproj`，编译器无法解析 | 人工补最小中性工程文件（17 次） |
| Go 源 `go build` 失败 | runner 的 `HOME`/缓存不可写 | 人工补 `GOCACHE=` |
| Go 目标构建失败 | 源码 `go.mod` 要求 1.27，runner 为 1.26.4 | 记为 `BLOCKED_ENV` 或下发 `GOTOOLCHAIN=local` |

这些都是**逐任务人工绕过**。本文件把它们变成**可事先声明的构建前提**。

## 0.1 源侧平台契约：先取证，再写命令（2026-10-09 实证）

§0 的表格记录了逐任务人工补前提的问题。dataset-2 进一步证明：**不在冻结前做源侧平台取证，会把同一类契约错误复制到整批**。

分类前的冻结完成、源预检/提交前的再次核对须按[任务状态 §2.2](../framework/task-state-contract.md#22-冻结落盘门禁)消费本项本 run 已落盘且可回读的 `01-frozen/frozen-inputs.md`；仅口头确定命令、case.md 或分类清单存在不能替代。尚未取得的编译诊断/基线只记待取证，文件存在不证明构建或环境通过。

**必须遵守的顺序**：

1. **先静态画像源文件**：找出它实际需要的平台接口——POSIX 扩展、BSD 专有头/宏、Win32 头、外部工程头、链接库。这一步**只产出候选 `sourceOs` 与依据，不产出结论**。
2. **再提出已登记的源侧 OS 候选**：平台头/符号是依据，BSD 特征仅提示扩展依赖风险，不能凭名单断言 Linux/macOS 一定缺失，也不能登记不存在的 BSD runner。已登记组合见[能力矩阵](../adapter/controller/runner-capability-matrix.md)；候选不明记准备缺口。
3. **分类 ALLOWED 后在隔离环境源侧预检，由真实诊断定案**：冻结命令真实 build completed/0 确认可构建；正常行为分支再取有效源基线。本轮无法合法行为评估但源可构建时，按[评估准备 §1.3](../framework/evaluation-readiness-contract.md#13-lib_unobservable_compile_only-的转换与交付)记 LIB_UNOBSERVABLE_COMPILE_ONLY，继续转换、自审与目标语法/编译验证。无 ALLOWED 不预检，只凭头名不定案；源构建失败不转换，命令/组装缺陷先纠正并重预检，运行/观察缺口不混为源不可构建。
4. **本流程不设头文件探针**（用户 2026-10-09 裁定取消）：**不**通过额外提交探针样本预先枚举 runner 的头文件集合，也不把此类历史实测记录当作常驻判据。依赖未登记系统的项会走到预检才被发现，每次多一次往返但不消耗模型调用，这是可接受的代价。
5. **不伪造预定义宏或头文件桩**冒充另一工具链（§4.1）；判不出源侧平台时记准备缺口。

一次候选预检失败只证明该源快照在该 runner/命令下的结果；不能外推已登记的其他 OS 全部失败。未测试的候选单列，不把 Windows/Linux 两侧诊断写成 macOS 结论；也不为凑覆盖强制每项遍历三个 OS。BSD 特征、普通翻译单元、上游库内部单元分别按实际依赖判断，已有链接可构建基线只适用于它对应的精确源集合与工具链。

库内部单元先核准确源集合、伴随头与对象/库的真实构建形态。缺 main 不等于缺依赖，不以强行链接可执行后的缺 main 诊断认定原库单元不可构建；也不据无 main 自动判无安全观察口。行为评估是否需要合法中性入口、缺入口与仅编译例外仍按评估准备契约，Agent 不补写驱动或伪造缺失依赖。

核源构建命令/工作目录与原请求、manifest 的源身份对应：必须消费本项需验证的冻结源，不能仅编译另一个文件/包、系统内置库或不包含该文件的目录后声称本源通过。工具链按真实条件选中的文件/分支才是结论范围；命令遗漏先纠正契约/组装并重新预检，不凭摘要 PASS 补证。Go build 对显式文件、完整包及非 main 包的产物规则不同，编译检查不强迫产出可执行文件；实际支持与结论仍以精确版本诊断为准。

**三类必须分列的源侧结论**：

| 现象 | 归因 | 记录 |
|---|---|---|
| 严格模式下扩展声明不可见（如 `getopt`/`optind`） | **候选契约缺陷** | 核实际工具链、头/声明及源所需扩展；有依据时另记标准/特性宏条件重预检，不把 `-std=gnu11 -D_GNU_SOURCE` 当所有源的处方 |
| 源引用了工程内其他文件（如 `..\Release\X.h`） | **先核集合/打包** | 冻结集合内漏带先恢复精确字节；确属快照外依赖才记 SOURCE_DEPENDENCY_GAP，不补造桩 |
| 构建阶段真实诊断确认源接口与本次 runner 不匹配 | **本次源侧平台不匹配** | 记该候选 SOURCE_NOT_BUILDABLE 与构建诊断，未测候选仍未知；不把含 BSD 头/宏或运行时import失败当不可构建证明 |

三者都**不是转换失败**，不得回填成目标编译失败，也不得合成进单一成功率。

**打包完整性 ≠ 源依赖缺口（2026-10-09 D2-025 实证）**：若源文件在快照内确实存在、只是提交 capsule 时漏带（例如只带了声明的翻译单元，漏了同目录伴随头/源），源侧构建会报“找不到文件”，看着像源缺陷，实则是**打包缺口**——补齐组装（把冻结构建命令消耗的每个文件都纳入 capsule）后重测，**不记** `SOURCE_DEPENDENCY_GAP`、更不记 `SOURCE_NOT_BUILDABLE`。只有源**引用了快照根以外**的文件才是 `SOURCE_DEPENDENCY_GAP`。D2-025 的 `atoms.h` 本在数据集内，首次被误判为源缺陷，经按哈希从源快照恢复后确认只是组装漏带了伴随文件。

**逐项冻结、逐项验证**：不得一次性冻结整批再统一转换。冻结发生在任何构建证据之前，批量冻结会让上述错误一次性复制到整批（dataset-2 实测：一次性冻结 40 项 → 34 项因同一个源侧契约错误集体失效，0 项取得转换或双侧证据）。

恢复伴随文件须核实际源字节、来源和冻结集合。去 CR 或其他换行归一化后相同只证明该归一化视角相同，不能替代冻结源文件的字节 SHA。组装漏带但恢复原冻结字节与修改源字节分别记录；后者按任务状态契约登记关联变体并核重新分类，不覆盖原快照。

## 1. 核心原则：构建前提必须写进契约，不能靠事后发现

平台侧 `apps/vm-agent` 的构建命令**直接取自任务契约的 `buildCommand` 字段**
（`agent-run-request` schema 的 `manifest.buildCommand`），Agent 自身**不会**按语言或平台自动适配。

由此得出本文件最硬的一条规则：

> **凡是"没有它就构建不过"的前提，都必须在冻结阶段写进任务契约的构建命令或环境，
> 不允许留到构建失败后再逐任务人工补。**

"变更了构建命令"属于**任务契约的一部分**，应在 `01-frozen/` 阶段确定并留证；
事后补链接库或环境变量必须记录为**契约变更**及其依据，不能静默。

## 2. 语言方向的构建前提

### 2.1 C / C++ → Windows（含 C→C#/Go/Python/Ruby 中保留原生构建的情形）

| 前提 | 触发条件 | 必须做什么 |
|---|---|---|
| **Winsock 链接** | 源使用套接字（`socket`/`connect`/`bind`/`send`/`recv`/`WSAStartup` 等），或含 `<winsock2.h>`/`<ws2tcpip.h>` | 构建命令**必须链接 `ws2_32`**（MSVC `ws2_32.lib` / MinGW `-lws2_32`）；缺失会在链接阶段报未解析符号 |
| **头文件顺序** | 同时包含 `<winsock2.h>` 与 `<windows.h>` | `winsock2.h` **必须在 `windows.h` 之前**，否则与旧 `winsock.h` 冲突 |
| 其他 Windows 系统库 | 使用注册表、服务、加密、进程等 API | 按实际 API 补对应库（如 `advapi32`、`crypt32`、`user32`）；**逐项核对，不整包塞入** |

Winsock 的系统语义差异（`WSAStartup`、`SOCKET` 无符号、`closesocket`、`WSAGetLastError` 等）
见 [POSIX ↔ Winsock 套接字](../../skills/systems/posix-winsock/SKILL.md)；本文件只管**链接前提**。

### 2.2 C# / .NET（源侧或目标侧）

| 前提 | 触发条件 | 必须做什么 |
|---|---|---|
| **工程文件** | 本侧是 C# 且冻结构建目录**没有 `.csproj`**（或等效工程文件） | 补**最小中性工程文件**并留证，见 §3；源预检和目标评估分别核对，不以另一侧已有工程文件代替 |
| 目标框架 | 任何 C# 任务 | 冻结 `TargetFramework`（本项目基线 C# 12 / .NET 8）；不写则用 SDK 默认，可能与本项目基线不符 |
| 引用的程序集 | 使用 `DllImport`、`System.Management`、`System.ServiceProcess` 等 | 显式声明所需引用/包；缺引用会报类型或命名空间不存在 |
| 不安全代码 | 使用 `unsafe`、指针、`Marshal` | 在工程文件中显式开启 `AllowUnsafeBlocks` |

### 2.3 → Go

| 前提 | 触发条件 | 必须做什么 |
|---|---|---|
| **工具链版本** | 源码 `go.mod` 声明的 `go` 版本**高于** runner 实际版本 | 见 §4.1；**必须显式处理**，不能等下载失败 |
| 构建缓存可写 | 任何 Go 构建 | runner 侧 `GOCACHE`/`HOME` 必须可写；现状见 §4.2 |
| 模块/源范围与构建形态对应 | 使用模块/目录构建，或显式命名 Go 文件 | 冻结实际工具链支持的形态与需消费的源集合；模块任务保留合法原 go.mod/go.sum，缺必要模块材料待准备，不私设模块路径/版本/虚假依赖。不将 go.mod 当任何 Go 构建的统一必备件；是否可构建据本项真实诊断 |
| CGO / 外部依赖 | 源码 `import "C"` 或依赖 cgo | 需目标侧 C 工具链；不具备时记 `BLOCKED_ENV`，不静默降级 |

### 2.4 → Python / PowerShell / Ruby

目标为解释型语言时通常无链接前提，但仍须冻结：

- **解释器版本**（本项目基线：CPython 3.12、PowerShell 7.6、Ruby 3.4）；
- **依赖可用性**：源码导入的非标准库在目标侧是否存在；缺失时记 `BLOCKED_ENV` 或明确限制，
  不用空实现替代；
- **语法检查入口**：`python -m py_compile`、`ruby -c`、PowerShell 解析器入口，须与冻结契约一致。

语法/构建与加载/运行分开：py_compile成功不证明import可用，ruby -c成功不证明require可加载；已经构建通过后的ModuleNotFoundError、LoadError、加载期TypeError等按真实依赖/环境/源风险归因，不回写为源构建失败。正常行为分支的适用运行基线由评估准备契约消费，仅编译分支不为发现import问题而强制运行。PowerShell解析器调用须实际消费ParseError集合并在有错误时给出失败结果，不能把错误输出参数丢给null后将进程0当语法通过；合法解析入口只能引用获批平台已有版本，Agent不编写检查脚本。

#### 2.4.1 检查阶段与结论范围

冻结及判读时将实际命令归入下表，并记录精确文件/入口、工具版本、原诊断及真实退出；命令名或语言名称不能单独决定阶段。此表不提供可执行检查程序，不授权在本机调用任何解析器，也不增加加载/运行步骤。

| 实际阶段 | 支持的结论 | 不能替代的结论与分流 |
|---|---|---|
| 语法/编译检查 | 命令确实消费冻结的本侧文件，完成且真实 exitCode=0、适用解析错误集合为空，才支持该范围语法/编译通过 | 不证明 import/require、模块顶层初始化、链接、启动或行为；检查入口丢失 ParseError/仅检查别的文件时证据不足，不从 shell 0 补 PASS |
| 链接/工程构建 | 据本项实际工程/库/对象形态及链接诊断判读；库检查不强求 main 或可执行产物 | 链接错误与语法诊断分列，不能从缺可执行文件推源不可构建；不补业务入口或虚假依赖 |
| 模块加载/初始化 | 真实 import/require、程序集或原生库加载及初始化属于实际加载/执行范围，可能产生输出或副作用 | 不能冒充“不运行的语法检查”；仅编译分支不为证明加载而执行。已有语法证据保留，加载异常另核真实依赖、环境、源已有或转换引入 |
| 程序启动/行为 | 按冻结入口与输入到达状态，取真实退出/超时、程序流和适用副作用后，按评估准备判有效基线/比较 | 执行 completed 不证明成功或构建通过；argv=[]、stdin=null、空 stdout 和预期非零均可合法，不要求解释型源一律 build-and-run |

错误发生在构建工具自身加载、插件或环境准备时，先核是谁执行、消费了哪份文件及发生阶段，不仅凭 ModuleNotFoundError/TypeError/LoadError 名字归入样本运行或转换错误。源/目标、阶段状态、阶段结果与行为覆盖分别写；仅编译形态/合法解析入口支持未知时保留已有目标并写 UNVERIFIED/PARTIAL，不造检查脚本或借一次执行取得语法结论。生成前源构建未取得仍不能调用模型；具体分支只消费[评估准备 §1.3](../framework/evaluation-readiness-contract.md#13-lib_unobservable_compile_only-的转换与交付)。

## 3. C# `.csproj` 补齐的三个硬性要求

batch-01～04 共出现 **17 次** `AGENT_ADDED_CSPROJ`。补齐工程文件是**引入源中不存在的构建外壳**，
因此必须满足以下三条，缺一不可：

1. **最小中性**：只声明目标框架与必要引用；**不得**引入源中不存在的包、命名空间或语言特性。
2. **同时记录"原本缺什么"**：补齐会掩盖真实的类型/依赖缺口。
   必须在冻结或交付记录中显式写明：`原本无 .csproj`、`补齐内容`、`补齐后仍缺失的类型/符号`。
   把"补了工程文件"写成"环境已就绪"是禁止的。
3. **随源码一起移交**：工程文件属于构建前提，须列入比较 capsule 的构建输入，
 不能让接收方自己补一份不同的。

上述外壳仅是声明性的构建配置，不授权编写驱动、构建脚本、生成器、桩或业务实现。新增/变更源树中的工程输入须记录来源及内容，按任务状态/分类准入核关联变体、完整源集合和重新分类；目标侧配置变化也要重新核构建/评估准备。缺真实依赖不能用外壳补成存在。

**反例**：为掩盖 `SharpUp`、`pch.h`、`ICommand` 之类**真实缺失的依赖**而补工程文件，
使编译"通过"。这类缺口应按源依赖缺失处理（记阻断或另选完整源码），不得用空桩冒充。

## 4. 工具链版本与运行环境

### 4.1 版本不符：显式处理，不静默降级

源码声明的工具链版本与 runner 实际版本不符时（如 `go.mod` 写 `go 1.27`、runner 为 `1.26.4`）：

| 处置 | 说明 |
|---|---|
| **首选** | 在契约中显式声明所需版本或 `GOTOOLCHAIN=local` 等策略，并记录理由 |
| **记录** | 不符事实写入冻结输入与事件，标明"环境事实"而非代码缺陷 |
| **禁止** | 静默改用其他版本、静默改写源码的版本声明、把环境不符记成转换失败 |
| **工具链下载被拒** | 记 `BLOCKED_ENV`，不重试下载、不改源码绕过 |

**降级会改变语义**（如更低语言版本不支持新语法），因此**版本策略由人工决定**，
不在转换流程中自动选择。

改变 `-fpermissive`、诊断 pragma 或类似选项须保留原命令、诊断与契约变更理由。GCC 文档说明 `-fpermissive` 会把部分非符合代码的必需错误诊断降为警告；它不证明行为相同，源里的诊断 pragma 也不构成两者语义等价证据。源码字节不变仍可能改变被接受的程序和工具链条件，不据此宣称“只是打包修复”，不把放宽诊断设为整批默认项。

### 4.2 构建缓存与 HOME

Linux runner 曾因 `HOME` 不可写导致 `go build` 在**编译源码前**失败：

```
failed to initialize build cache at /home/d9lab/.cache/go-build: mkdir /home/d9lab: permission denied
```

该缺陷已在 runner 侧修复（`HOME`/`XDG_CACHE_HOME`/`GOCACHE` 指向可写目录，快照 `CC-Eval-Linux-8Lang-R12`）。
**现行状态以 [Runner 能力矩阵](../adapter/controller/runner-capability-matrix.md) 为准。**

处置规则：

- 编译器**在处理源码之前**因权限/缓存初始化失败 → **归因环境**，不改代码绕过；
- 环境故障不等于转换失败，按 `BLOCKED_ENV` 记录并保留原契约；
- 若确需临时指定缓存位置，须记录为**环境绕行**并注明其适用范围，不得写成"runner 已修好"。

## 5. 何时把构建问题的责任判给环境

| 证据位置 | 归因 | 记录为 |
|---|---|---|
| 源码编译前（缓存、权限、工具链解析） | 环境 | `BLOCKED_ENV` |
| 源码解析/类型检查阶段，缺的是**源自身**的依赖 | 源依赖缺口 | 阻断或另选完整源码 |
| 源码解析/类型检查阶段，缺的是**构建外壳**（工程文件、链接库） | 构建前提 | 本文件 §2/§3：补齐并留证 |
| 编译通过但链接失败，缺系统库 | 构建前提 | 本文件 §2.1 |
| 编译通过但运行失败 | 代码或环境 | 按[闭环](conversion-evaluation-loop.md)分流 |

**不得**把环境故障写成代码缺陷（会误导修复方向），
也**不得**把缺构建前提写成环境故障（会掩盖可事先声明的前提）。

## 7. 证据边界

- 本文件的规则来自真实运行中**已发生**的构建失败与处置，但**不是**对某个具体编译器/SDK 版本的验证记录。
- 目标为具体版本时消费本地已核验的适用事实与实际工具链证据；必要版本事实缺失记具体知识缺口，由维护侧核验并补入本地参考，不要求调用者联网补全。
- 本文件规定"应声明哪些前提"，**不证明**声明后一定能构建成功。
- 本机不编译、不运行；构建证据只能来自获批隔离环境。
