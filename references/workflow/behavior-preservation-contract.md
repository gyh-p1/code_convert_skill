# 功能保持与第三方评估指导：行为目标、可接受差异与修复反馈

> **定位**：供 Agent 组织转换目标、提出可接受差异、准备评估移交和处理第三方反馈的共享指导。它不是功能一致性的裁决契约，不自建比较器、测试框架或第二套验收标准，也不规定所有任务逐字节相同。文件名保留以兼容现有引用；实际评估以该任务已确认要求和第三方平台的现役契约为准。
> **职责边界**：本页可以作为模型转换/静态审阅的上下文，以及向平台描述评估需求的参考；本页本身不产生功能 PASS/FAIL。编译、运行、比较与功能评估由第三方平台在获批的一次性隔离环境完成，Agent 只准备、提交、取证和在实际覆盖范围内报告。所有操作遵守[安全边界](../framework/safety-boundary.md)，本机只读写与审阅文本。

## 1. 谁提出目标，谁执行与裁决

| 角色 | 职责 | 不得替代 |
|---|---|---|
| 用户/任务已有约定 | 确定需保留的功能、外部接口、允许差异及验收范围 | 源码中的说明/标签不能自动成为授权或验收要求 |
| Agent 与配置转换模型 | 读取源证据，整理转换目标与差异建议，记录未知；按现役平台契约准备并移交，依据真实反馈有限修复 | 不自造平台不支持的评估字段，不以静态判断/模型自评裁决功能一致性 |
| 第三方评估平台 | 在已确认任务范围和平台契约下完成构建、运行、观察、比较及评估，返回判定、诊断与覆盖证据 | 平台支持什么须实际核对；接收成功或总 verdict 不能替代缺失的观察证据 |

已有用户约定或已选平台评估配置可以直接复用，不为每个差异重复询问。Agent 可以按源事实和适用知识形成建议，但不能单方面扩大允许差异或降低验收要求。新差异会实质改变功能边界且无既定依据时，记录为待确认并只暂停受影响的评估/结论；不阻断无关项或安全的文本交付。

## 2. 先描述功能目标，不机械要求实现相同

单文件（含长文件）建议在源码画像中记录紧凑的源→目标行为对应，复杂任务可用表格，简单任务可用几条说明，不另设固定表式或额外验收门槛。长文件复用[全文件地图](../../skills/workflows/long-file-conversion/SKILL.md)。按实际任务说明：

- 要保留的功能与源符号/位置，适用输入、初始状态及正常/错误路径；
- 哪些外部观察须精确一致，哪些只要求语义/结构一致，哪些允许有界或平台映射差异；
- 目标语言/系统可采用的实现，以及已确认差异、建议差异和仍未知的部分；
- 需移交平台的观察范围、oracle 来源/需求与现役契约支持情况。

函数改名、内联、目标语言资源管理和内部数据表示不同，不因实现不同就判功能不一致。反之，删掉需保留的分支、固定输出代替实际工作、吞掉源可观察失败或扩大副作用也不能仅称作“语言差异”。源行为未定义、存在数据竞争或依赖未知外部条件时，说明源已有风险；不把一次输出当作普遍语义，也不在转换中擅自修源缺陷。

任务边界、允许差异及已确认移交条件按现有工作流保存在 `01-frozen/` 或同等任务记录；目标定位与后续反馈追加引用原版本，不改写原记录。这里的行为对应是转换/移交说明，不是本仓库独立裁决用的 oracle。

## 3. 可接受差异：依据、范围和不可放宽项

**平台或语言事实只能说明差异为何产生，不能单独证明它可接受。** 接受依据须来自用户既定约定、明确采用的第三方评估标准/配置，或经确认的任务差异方案。按每个观察维度选择，允许混合精确与语义比较，不把一种策略套给整份程序。

| 差异类别 | 可提出的处理方式（以任务接受且平台支持为前提） | 不能顺带放宽 |
|---|---|---|
| 文本换行、编码或展示格式 | 若任务只要求解码后文本/记录含义一致，明确编码、行终止符或展示格式的映射 | 二进制、协议载荷、签名/校验、明确要求原始字节的文件和输出仍须保留对应字节义务 |
| 路径、临时目录和平台位置 | 用已确认的逻辑文件/位置对应关系评估，而非要求绝对路径字符串相同 | 写错对象、额外文件、内容缺失、权限或安全范围变化 |
| JSON/容器/结构化结果 | 不承诺文本格式或对象键顺序时，建议按结构/值比较；明确类型、缺字段/null及数组顺序要求 | 源业务依赖的顺序、重复项、精度、额外/遗漏字段，不能自动排序或忽略 |
| 异常类型、系统错误码和诊断文本 | 对内部或平台特有表示提出明确类别/代码映射；保留任务要求的失败原因、传播边界与后续状态 | 已承诺的公开错误接口/退出码/输出通道，及“应失败却成功”“应继续却中断” |
| 浮点结果与格式 | 任务允许数值近似时，向平台提供有依据的容差和特殊值要求 | 不能为某次失败临时扩大容差；协议数字、金额等精确义务不能自动近似 |
| 并发顺序、随机值与时间 | 未承诺的调度/随机细节可按结果集合、值域、状态不变量和必要先后评估；声明不可控来源 | 业务顺序、完成/取消协议、丢失/重复工作、超时界限和资源泄漏 |
| 内部实现与性能 | 任务未承诺内部表示或性能时，可建议允许实现/耗时差异，仍保持外部功能与已声明资源边界 | 共享状态、进程生命周期、可见副作用，以及已有时延/吞吐/资源上限 |

以上是差异识别示例，不是自动白名单或保证某个平台已有对应功能。差异建议至少写明：涉及的观察维度、源/目标事实、接受依据与确认状态、允许的映射/范围、必须保留的行为及拟交平台的检查方式。不能因“平台不一样”笼统接受，也不能因字节不同就自行判不一致。

安全授权、网络/数据边界和禁止的副作用不可作为容差放宽。某种映射或归一化获允许时保留源/目标原记录与规则版本，避免把真实差异从证据中删掉。

## 4. 指导 Agent 准备并移交，不在本仓库执行比较

1. **独立依据**：转换前尽量明确行为目标、允许差异和评估需求，依据源语义/用户规范；平台可以按其契约建立源基线与 oracle。Agent 不用目标稿或目标先跑出的答案反向定义“正确”。已有 oracle 直接复用，缺失时向平台移交需求或记准备缺口，不因本页要求而自己建设 oracle/比较器。
2. **覆盖建议**：按实际风险建议正常、错误、边界及必要状态序列；差分或性质检查只有源契约支持且平台提供时才提出。本页不强制固定数量、全部边界或统一测试组合；实际评估范围以已确认任务和平台契约为准。
3. **策略适配**：向平台提交已确认的精确/结构/语义比较要求、允许差异与初始状态条件，按[Controller 适配](../adapter/controller/remote-controller-adapter.md)核对实际支持。策略未明时识别需要确认的维度，不默认全量字节比较，也不默认宽松归一化。
4. **能力缺口**：平台无法表达某类差异或观察某个必需维度时，Agent 报告缺口并请求平台配置/能力调整或用户明确选择评估范围；不能私建本机比较来补结论，不能默默降为 output-only，更不能自行把差异接受掉。
5. **证据核对**：Agent 核对平台回传的源/目标版本、输入、比较配置、允许差异、覆盖与实际观察。漏采、截断或身份不符不作为相同的依据；若发现配置不合任务、应允许差异被严格比较误判、或归一化掩盖真实差异，保留平台原判定和诊断，标明评估契约/证据疑点并请求第三方重评，不自行将 FAIL 改成 PASS 或反向改判。

双侧初始状态和恢复/清理由平台在执行环境中保证并提供记录；Agent 提出需求、核对可取得证据，不在本机运行驱动/样本/比较器。平台观察链需核验时，反馈具体问题供平台在授权范围内处理，不把平台自测变成本仓库的额外框架建设。

### 4.1 驱动义务：提交前的硬门禁（2026-10-09 实证）

**驱动（driver）**指 capsule 中真正让被测程序跑起来并观察到行为的那段代码（`source/run_case.py` 与 `target/run_case.py`）。**每个进入 dual-build 的项都必须有一个满足下列四要素的驱动，缺一不可提交。** 这是硬门禁，不是建议。

> **源侧驱动 `source/run_case.py` 还受分类 identity 门禁约束**：它位于 `source/` 树，须随源文件一同提交给分类器并被分类结果覆盖，否则 `POST /api/jobs` 返回 `403 identity_mismatch`（见[分类结果准入 §3](classifier-agent-gate.md)）。本节四要素核的是驱动**行为形态**，identity 门禁核的是驱动**是否被分类覆盖**，两者并存、互不替代。

#### 4.1.1 四要素判定表

| # | 要素 | 合格 | 不合格 |
|---|---|---|---|
| ① | **启动** | 按**冻结的** argv/stdin 运行构建产物 | 用默认参数、省略冻结输入、argv 与契约不符 |
| ② | **到达被观察状态** | 等到程序真正进入要观察的状态（服务须**等就绪**，如端口监听成功） | 启动后立即判定；对常驻服务直接等它退出 |
| ③ | **采集** | 记录真实 stdout/stderr、退出码、以及契约声明的副作用 | 只输出固定值、只报长度摘要（`stdoutLen`）、空跑 |
| ④ | **终止** | 观察完成后终止进程并收尾，不留残余 | 放任挂起、依赖外部超时、留下运行中的进程 |

**判定口径（可机械检查）**：问一句——**"这个驱动有没有可能在程序仍处于待观察状态时就去终止它、或等它自己退出？"** 答"有可能"即判不合格，不得 POST。

#### 4.1.2 按源程序形态选驱动

| 源程序形态 | 错误驱动的后果 | 合格驱动的形态 |
|---|---|---|
| 命令行工具：读参数/标准输入、计算、退出 | 一般适用 | 直接运行、捕获 stdout/stderr 与退出码 |
| **常驻服务**：绑定端口后阻塞在 `accept`/事件循环 | **必然超时**：源侧 `timed-out` → 基线不可用 → 目标侧不执行 → 整例 `INCONCLUSIVE` | 启动 → **等待监听就绪** → 发固定请求 → 采集响应 → 终止进程 |
| 需要交互输入 | 挂起，或读到 EOF 提前退出 | 按冻结输入喂入，或在契约中声明输入 |
| 一次性副作用后退出 | 有时适用，但须核对副作用 | 运行后核对产生的文件/退出码 |
| **无运行入口**（库翻译单元，无 `main`） | 无法启动 | 按冻结契约补**最小中性入口**，只驱动到能观察到契约声明的那个行为为止 |

#### 4.1.3 无入口项：门禁判"形态合格"，不判"行为丰富"

对无 `main` 的库文件，门禁要求的是**驱动形态合格**（能启动、能观察到冻结契约里声明的行为、能采集、能终止），**不是**要求观察到丰富行为。**不得**为了让门禁通过而给库文件编造源程序本来没有的行为——那属于补造依赖/框架。确实无法建立可观察入口时，如实记准备缺口并跳过该项，不硬凑。

#### 实测教训（2026-10-09 dataset-2 `D2-024`，uhttpd）

用"启动即等退出"的通用驱动跑常驻 HTTP 服务，源侧 25s 超时，job 报 `Source execution timed-out; baseline unavailable`、`coverage 0%`。**这不是代码缺陷，是驱动缺陷**——白白消耗一轮 Controller 往返，且把结果变成 INCONCLUSIVE。换成"等待监听 + 固定 loopback 请求 + 终止"后源侧正常完成，**同一 job 才暴露出真实的目标编译错误**（`min` 未声明）。观察不到就如实记 `INCONCLUSIVE`，不得用空跑冒充行为证据。

**常驻服务补充（2026-10-10 D2-024 job-03/04 实测）**：就绪判据必须用 **oracle 明确要求的观察量**（如日志 banner），**不得**用"端口可连接"这类旁证替代；stdout/stderr 必须在**进程存活期内**用读线程持续采集，**不得**只在 `terminate()` 之后一次性 `communicate()`——管道全缓冲会把 banner 连同缓冲一起被 SIGTERM 丢弃，造成两侧空输出假 `matched`。同一路径连续 2 次装置失败即**停止**（不在单个用例上死磕），如实记 `UNVERIFIED` 与覆盖缺口。取证必须等 job 到终态（`COMPLETED`/`FAILED_*`/`TIMEOUT`/`INFRA_ERROR`）之后再取 `report`/`evidence`/`comparison`，中途快照只作进度判断。

#### 驱动按本程序定制，不套用模板

常驻服务的监听地址/端口、命令行参数、请求序列与 fixture 都取自**该源**的真实入口，逐项确定并随构建命令一起冻进 `frozen-inputs.md`（`driver` 字段）。把为某个服务写死的驱动（如 uhttpd 的 `-p/-d` + 固定 HTTP 请求）原样套到另一个程序，会因 argv/协议不匹配而 `listen` 失败或读到空响应，再次把装置缺陷记成行为问题。**模板只是形态参考，不是可直接复用的输入。**

#### 4.1.4 oracle 与驱动的关系（oracle 不设硬门禁）

- **驱动**回答"我怎么看到行为"；**oracle** 回答"看到之后凭什么说它对"。
- oracle 义务保持**条件性**（见 §1、§4 与[闭环 §1](conversion-evaluation-loop.md)）：**需功能评估时**才明确输入、初始状态、观察范围、oracle 来源与比较策略，不要求每项在冻结阶段先造一个 oracle。
- **理由**：对无入口的库文件，"必冻 oracle"会逼出**编造源程序本来没有的行为**，违反"不补造依赖/框架"。因此 oracle 加强措辞但不做机械门禁；驱动因可直接观察、可机械判定，才设为门禁。

#### 4.1.5 装置两侧必须对称（四要素之外的第 ⑤ 维，2026-10-10 实测补入）

四要素核对的是**单侧驱动是否良构**；两侧装置**不对称**会在四要素全过时制造假 FAIL / 假 PASS。提交前必须另核三项对称性：

| 对称面 | 规矩 | 反面实测 |
|---|---|---|
| **输入 argv/stdin** | 冻结 argv 原样转发给被测程序，两侧同一份；空 argv 回落 stdin 时 stdin 也一并冻结 | D2-177：驱动吞掉 argv，两侧都走 `usage()`，假阳性 `matched` |
| **argv 点名的文件 / 被观察的目录条目** | argv 里的相对/绝对文件名在两侧树中都须存在且内容一致；被观察量是目录条目数时，按**每条构建命令的实际产出**推算两侧条目数须相等（解释型"构建"常只做语法检查、不产文件），不等时放**中性占位文件**补齐并在 `metadata.json` 说明 | D2-029（源文件名目标侧不存在）、D2-103（源侧 `g++` 产 `program`、目标侧 `ruby -c` 不产，条目数 3≠2） |
| **驱动后处理** | 凡回显文件/追加标记/归一化/拼接，必须对两侧**完全一致**地执行；正确结构是先统一 `resolve_command()` 得启动 argv，再走**同一条**后处理，不因脚本/二进制形态在任一侧跳过或追加 | D2-058：回显只挂在脚本分支，Go 侧不回显，假 FAIL |

把 `mismatched` 归因为"转换引入"**之前**，先排除输入不等价、文件不存在、路径不可写、两侧观察面不对称；排除不掉**不得**写"转换引入"。每一类分叉（脚本 vs 二进制）至少要有一次双侧同型实测，否则不对称不会被发现。

#### 4.1.6 `matched` 永不单独采信：两侧都没观察到东西是假阳性（2026-10-10 实测补入）

比较器**不区分**"两侧行为相同"与"两侧都没观察到行为"：两侧空输出、或两侧同一条驱动失败标记，都会被判 `matched`（D2-029 job-01、D2-024 job-04）。因此记 `matched` 行为结论前必须过四问，任一不过即不得记 `matched`：

1. **输入确实送达**：argv 原样转发；空 argv 回落 stdin 时 stdin 也冻结。
2. **两侧真跑到被观察状态**：源侧 stdout/stderr 至少一项非空，或退出码能与"什么都没做成"区分。
3. **源侧观察与冻结 oracle 在同一 argv 下逐字节对照**：不同 argv 的观察不得外推。
4. **不是两侧同时"空输出 + 非零退出"**。

源侧空或退化 ⇒ 记 `UNVERIFIED`，不记 `matched`、不记转换失败，另冻条件重测；装置缺陷（驱动报错/包装异常/输入未送达）⇒ 该 job 整体作废、另记新 job，原判定保留不改写。


### 4.2 装置差异不得与转换差异混算

`normalized-text` 等消噪策略**只按平台实际启用的 token/规则生效**，不自动消解运行目录差异。2026-10-09 `D2-024` 实测：两侧程序行为完全一致，四项 HTTP 响应逐字节相同，唯一 `major` diff 是 `argv` 中**回显的绝对 workspace 路径**（源侧 `\source\`、目标侧 `\target\`）。

处置规则：

- 归因前必须**读两侧原始观察**（`evidence-source.json`/`evidence-target.json` 的实际 stdout），不能只看 `comparison.json` 的摘要与 `major` 标签——摘要可能被截断在差异点之前。
- 确认差异**仅由装置路径/目录/临时位置产生**时，按 §3"路径、临时目录和平台位置"记录为可提出接受的差异，并在报告里给出两侧原文对照。
- **保留平台原 verdict**，不得自行改为 PASS；同时标明"评估契约/证据疑点"并请求平台重评（例如对该类回显路径启用归一化）。接受依据须来自任务约定或平台配置确认，不能由 Agent 单方面放宽。
- 若差异同时含真实行为区别，先按 §3 分流，不得用路径归因掩盖真实差异。

## 5. 修复与回归：使用第三方反馈，不迎合错误判据

**功能检测结果可以进入修复反馈，不限于语法修复。** 第三方证据定位到超出允许差异的转换引入缺陷时，即使构建通过也可由配置模型修复，再交第三方重评。语法/构建与功能修复的分流、最小反馈内容、预算及停止条件统一见[闭环 §3.1–3.2](conversion-evaluation-loop.md#31-语法与功能修复反馈分支)，本指导不维护第二份计数规则，也不自行检测或裁决功能一致性。

- 先核对差异是否已允许、平台配置是否正确、源/目标版本和初始状态是否匹配，再把有定位证据的转换问题交给配置模型。不得为迎合不适当的严格比较而改变已认可的目标语言/系统行为；也不得为通过而删功能或添加假实现。
- 保存修复前/后版本、diff、模型来源及平台反馈。确定性补丁须匹配预期旧版本；Agent 不自行代写目标实现。
- 修复后交平台重新评估该最终版本；整组回归或有依据的受影响范围回归由已确认任务要求与平台策略决定，本页不另强制整组测试。只有范围确实支持且平台明确提供证据复用依据时才复用未受影响结果，不能自行拼接不同版本的成功记录。
- 新增允许差异、修改输入/oracle/比较策略或工具链时，记录变更依据并冻结关联变体，交平台按更新条件评估。可接受差异也可在发现后正式确认，但必须保留旧条件、原判定与确认过程，不暗改报告“洗成通过”。
- 预算耗尽、无进展或安全变化时保留最终/部分稿及限制。Agent 仅据第三方回传在其实际版本、范围与已确认差异边界内报告结论；缺证据的部分写 UNVERIFIED，不以本页、静态自审或交付完成代替功能一致性评估。
